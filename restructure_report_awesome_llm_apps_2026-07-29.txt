STEP 2 — SIDE B: the replacement case, three named axes only
=====================================================================
Real research first (GODMODE + /scope), not an assumed baseline:

Axis 1 - shorter code: RPGACE's Oracle/taxonomy pipeline
(phylumPath._callExtractor / _callGroundWorkerJSON / _callGroundWorkerText,
Omnitrix's Fable/Opus/Sonnet dispatch) is hand-rolled fetch()+prompt-
parsing+manual JSON sanitization (_sanitizeNewSteps). A framework
(OpenAI Agents SDK, Google ADK - both in this repo's own "Framework
Crash Courses") gives tool-calling, structured-output validation, and
retry/streaming as library primitives instead of hand-written boilerplate.
REAL COUNTER-EVIDENCE: package.json is `{"type":"module"}` and nothing
else - the api/*.js serverless backend has ALREADY chosen zero
dependencies, deliberately, not by oversight. Adopting a Python agent
framework would mean a second runtime (Python) alongside Node serverless
functions - a real, larger architecture change than "shorter code," and
one this project has already rejected the shape of twice. Axis 1's
strong claim (adopt a framework wholesale) does NOT survive Step 3's
implementation sketch. A narrower claim DOES survive: agent_skills
themselves (already ADOPT-verdicted for Commit Archaeologist) are real,
already-shorter alternatives to hand-writing an equivalent capability
inside a SKILL.md from scratch - a live, small, real instance of "shorter
code" via delegation rather than reinvention.

Axis 2 - loads/responds quicker: RPGACE's OWN documented pain point (rule
11, token_cost_audit_2026-07-19.txt: "£10 burned in one test session")
is a real, live cost/latency problem. This repo's own "LLM Optimization
Tools" section (Toonify - Token Optimization via TOON format, 30-60%
reduction; Headroom - Context Optimization, 50-90% reduction) is DIRECTLY
on-topic for this exact pain point, not a generic "faster app" claim.
Smaller context sent to Claude means both lower cost AND a genuinely
faster round-trip for Oracle/taxonomy calls - a legitimate reading of
"loads quicker." REAL COUNTER-EVIDENCE: this project already runs its own
prefiltering discipline (rule 11: keyword-scan before any Oracle call,
numbered indented trees instead of full path listings, skip the call
outright when the prefilter finds nothing) - some of TOON/Headroom's
value may already be captured by hand, un-branded. This axis's claim
SURVIVES Step 3 as a real, narrower proposal: apply TOON-style structured
compression specifically to the ground-worker call sites that still send
verbose JSON/prose (not a wholesale reframing of rule 11's own already-
working discipline).

Axis 3 - more detailed/context-appropriate/meticulously picked output:
oracleTreeGrounding and oracleAppGrounding both use a keyword-score
heuristic - already self-flagged in a PRIOR Aintergration pass (Worked
Precedent 4, July 22) as "'good enough' vs. real search infra," never
revisited since. REAL NEW EVIDENCE this session: Supabase's `vector`
extension (pgvector 0.8.0) and `pg_trgm` (trigram fuzzy text match) are
BOTH available in this exact project (confirmed via list_extensions) but
NOT installed - meaning a real embeddings-based or fuzzy-match upgrade to
Oracle's own grounding is NOT architecturally blocked, just never built.
This repo's RAG tutorials (Corrective RAG - retrieval that grades itself
and retries; Hybrid Search RAG - keyword+vector combined) are real,
checkable REFERENCE PATTERNS for what a better retrieval mechanism would
look like, even though none of the actual Python code would ship.
REAL COUNTER-EVIDENCE: this is real added scope (a new table, a real
recurring embeddings-API cost, a backfill job) - not free, and the
current keyword heuristic hasn't caused a reported real failure, only a
self-flagged "not ideal" note. This axis's claim SURVIVES Step 3 as a
real Tier-3 candidate, explicitly NOT decided here.

STEP 3 — Envision implementation (via /Engineer's shape, NOT built)
=====================================================================
Candidate 1 - TOON-style context compaction for ground-worker calls.
  Goal contract: a shared `_compactContext(obj)` helper (rpgace_core.js,
  near phylumPath) converting verbose JSON/prose into a token-dense
  notation before _callGroundWorkerJSON/_callGroundWorkerText requests.
  Files touched: rpgace_core.js only (one shared helper, rule 8 - not a
  copy per call site). Tier: 2 (multi-call-site, no new infra, no
  spending decision - just less text sent for the same real information).
  Real evidence needed before building: an actual before/after token
  count on a real chapter/proposal, not an assumed percentage.

Candidate 2 - Vector/hybrid retrieval for Oracle tree grounding.
  Goal contract: enable the `vector` extension; new `taxonomy_embeddings`
  table (node_id, embedding vector); a one-time backfill Vercel function
  calling an embeddings API; oracleTreeGrounding's retrieval swapped from
  keyword-score to cosine-similarity (+ optionally a corrective-RAG
  self-grading pass). Files touched: a new migration, a new api/*.js
  endpoint, rpgace_core.js's grounding module. Tier: 3 (new extension,
  new table, new recurring embedding-API cost, a real architecture
  change to a hub both Oracle and Taxonomy Tree depend on per
  interconnection_map.md). Real evidence needed: an actual cost estimate
  per embedding call, and at least one real example of the CURRENT
  keyword heuristic actually picking a worse result than a vector search
  would have - not just "it's less rigorous in principle."

Candidate 3 - Commit Archaeologist (already ADOPT-verdicted in Step 1).
  Tier: 1. `npx skills add` once the real slug is confirmed against the
  repo's actual agent_skills/ layout.
