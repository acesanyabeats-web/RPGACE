REAL DATASET-UPLOAD BUGS FOUND AND FIXED, in order (none glossed over):
1. A Git-Bash-style path (/c/Users/...) passed to the Windows-native
   Kaggle CLI broke its temp-staging path sanitizer (only escapes \
   and : - forward slashes leaked through as literal nonexistent
   subdirectories). Fixed: convert to a real Windows path first.
2. Subdirectories are silently skipped by `kaggle datasets create`
   without an explicit -r/--dir-mode flag - the first "successful"
   upload contained one 411-byte file, none of the real weights.
3. `-r tar` mode does not dereference symlinks. The HF cache stores
   weights as symlinks to content-addressed blobs; Python's
   `tarfile.add()` stores symlink stub entries (a few bytes, just the
   link target) instead of real file content by default. Produced 5
   identical ~10KB "archives" that LOOKED like a successful upload but
   contained zero real weight data - caught by direct verification (a
   local tarfile test) before trusting it, not assumed correct.
   REAL LESSON: the same class of "green checkmark, silently wrong
   data" risk this whole project's rule 4 exists to catch, just in a
   different codebase.
4. The "obvious" fix (dereference into a real copy) hit a real
   constraint: only 8.6GB free disk, and the CLI's tar mode stages the
   full archive locally first - text_encoder/ alone is ~9.4GB, so that
   would have failed or filled the disk. Real fix: NTFS hardlinks
   (verified zero extra disk usage before/after) flattened into unique
   top-level filenames (e.g. text_encoder__model-00001-of-00002...),
   bypassing the CLI's broken directory/tar handling entirely in favor
   of its working per-file streaming upload path.
