1. TECHNICAL RISK. Real risk if credit-exhaustion detection is done
   carelessly: false negatives (never catches it — no worse than today)
   or false positives (misclassifies an unrelated real error as credit
   exhaustion, silently queuing garbage instead of surfacing a real bug
   to Alex via a toast). Mitigation: match only on Anthropic's own
   documented insufficient-credit phrasing (case-insensitive "credit
   balance" / "insufficient credit"), and on ANY non-match, rethrow the
   original error completely unchanged — behavior for every other error
   type stays identical to today. Cannot be tested against a real credit
   exhaustion event without actually draining credits — flagged honestly,
   fails open (worse case is "doesn't catch it," never "queues wrongly").

2. SCOPE/COST. Touches 3 shared functions used across Bookworm, Content
   Intelligence, and Taxonomy placement — the edit must be surgical
   (append detection + enqueue, not restructure the functions). New table
   costs nothing until actually used. New Routine costs nothing while
   dormant (hourly poll of an empty table is free-tier trivial).

3. MAINTAINABILITY. Two Routines will now exist (Morning Brief + this
   new Fallback Drain) — naming and structure kept deliberately parallel
   so a future session recognizes the pattern instantly. Table schema
   reuses oracle_dev_suggestions' shape rather than inventing a new one
   (rule 8).

4. UX / HONESTY. This MVP does NOT auto-resume the original caller — no
   code exists yet to poll the queue and re-inject an answer back into
   whatever Bookworm/Content-Intelligence/Taxonomy job originally asked.
   The real value on day one is: Alex (or a future Claude Code session)
   can see what got queued and what was answered, not that the app keeps
   working invisibly the moment credits run out. This must be stated
   plainly, not oversold — matches the original /debate verdict exactly
   ("adopt with modification... never a live-chat replacement").

5. WHY NOT BUILD THIS NOW (honest counter-case). Alex isn't currently out
   of credits — there is no live trigger condition today. Building this
   preemptively risks becoming another built-but-unverified piece sitting
   dormant, the same pattern already true of F16-18. Counter-argument:
   cost while dormant is genuinely near-zero, the design is fresh in this
   session right now (cheaper to build today than re-derive during a
   future real outage), and Alex already said "sounds good" to the idea
   specifically — this plan is executing an already-made decision, not
   re-opening whether to build it.

ADDENDUM — /debate: "auto-resume" explained clearly, MVP-only vs. wired-back
(Alex asked for this after the Tier-3 table confirmation, since he wasn't
sure what "auto-resume" meant in practice. Table was created in the

════════════════════════════════════════════════════════════════════

REAL EVIDENCE CHECKED FIRST (per CLAUDE.md's own building-guide rule 6):
grepped the existing "long AI jobs stream, continue in background, poll
from UI" pattern (_analyzeChapter/_continueAnalyzingInBackground/
analysis_complete/analysis_heartbeat, rpgace_core.js ~9643-10180). Real
finding: this existing pattern is a SAME-SESSION JS retry loop — the
browser tab stays open (or gets reopened) and a setTimeout-driven chain
keeps calling the ground worker again until analysis_complete flips true.
It is NOT an example of a completely separate process answering a
question hours or days later and something else noticing. That distinct
timing is exactly what the fallback lane introduces, and it's the real
source of the friction below.

WHAT EACH OPTION ACTUALLY MEANS, CONCRETELY:

MVP-only: a Bookworm chapter analysis (or Content Intelligence proposal,
or taxonomy score) fails today because credits are out. The toast fires
exactly like it does today. A row lands in oracle_fallback_queue. An
hour later (or whenever the drain Routine next fires), that row gets a
real Claude-generated answer written into its `answer` column. Nothing
else happens automatically. Alex, or a future Claude Code session, opens
the table, reads the answer, and manually decides what to do with it —
paste it back in, re-trigger the original action by hand, etc.

Auto-resume: the same failure and queueing happens, but additionally,
whichever module made the original call (Bookworm/Content-Intelligence/
Taxonomy) would need NEW code that, the next time its own status-polling
runs (the existing analysis_heartbeat-style check, or an equivalent for
Content Intelligence/Taxonomy), notices "oh, there's now an answered
fallback row for this," and feeds that answer back into its own pipeline
automatically — e.g. Bookworm parses it into insights[] and continues
_continueAnalyzingInBackground's chain, Content Intelligence inserts the
resulting proposal row itself, Taxonomy placement runs the answer through
decidePlacementScored as if it were a live response. This requires the
app to actually be opened again after the fallback has been answered —
it is not something that happens with no app involvement at all, since
RPGACE's own client JS is what would have to notice and act on it.

DEBATE — ATTACK PHASE:

Round 1A (FOR auto-resume, attacking MVP-only): MVP-only makes the
queued answer functionally inert without a human noticing it and
manually redoing the original task by hand. CLAUDE.md's rule 6 exists
specifically so Alex never has to babysit a long AI job — leaving this
one failure path as a dead end that requires manual intervention is a
real, avoidable regression against that same standing principle.

Round 1B (FOR MVP-only, attacking auto-resume): the existing polling
pattern this would need to extend is a same-session retry loop, not a
"resume from a completely different execution context, possibly days
later" mechanism — those are genuinely different problems. Building
real resume logic means teaching THREE separate modules (Bookworm's
chapter continuation, Content Intelligence's proposal pipeline, Taxonomy's
placement scoring) each how to recognize an answered fallback row and
feed it back into their own, different, pipeline shapes. That's three
real integration points to build and hand-test, for a scenario (Alex
completely out of credits) that hasn't happened even once yet.

Round 2A (auto-resume counter-attacks): the "three separate integration
points" objection is overstated, because all three callers already share
the exact same 3 ground-worker functions (rule 3: "reuse phylumPath.
_callExtractor / _callGroundWorkerJSON / _callGroundWorkerText — never
hand-roll another fetch"). If credit-exhaustion detection already lives
at that one shared choke point (which this plan already does), a "was
this queued, is it now answered" check can live at the exact same choke
point too — the low-level plumbing is genuinely once, not three times.

Round 2B (MVP-only counter-attacks back): true for the low-level check,
but using the answer once it comes back is NOT shared — Bookworm needs to
re-parse it into insights[] and resume a specific recursive chain,
Content Intelligence needs its own proposal-insert shape, and Taxonomy
placement's result still has to land in the human-checkpointed review
queue either way (rule 4: "every taxonomy write gets a human checkpoint
... no exceptions"). So even a fully-wired auto-resume for Taxonomy
doesn't remove the human step there — it only automates getting the
proposal INTO the queue faster, which narrows how much "auto" actually
buys for that specific caller.

DEFENSE PHASE:

Auto-resume defends: the taxonomy human-checkpoint point is fair but
doesn't kill the case — it just clarifies that "auto-resume" for
Taxonomy means "auto-generates the review-queue proposal," never
"auto-writes the tree." That's not a new risk; it's the same rule that
already applies to every placement regardless of fallback.

MVP-only defends: the real case for MVP-only isn't that auto-resume is
impossible — it's that this exact session already found three separate
real gaps hiding inside earlier "fully migrated" claims (Approach B
phases 1-3) specifically from moving across multiple tables/call sites
at once instead of proving one path first. Building and shipping three
new integration points in one pass, for a scenario that hasn't happened
yet, repeats the same shape of risk this session already paid for once.

COUNCIL OF 5 — CLEAN SUMMARY (both cases, no declared winner, per this
skill's own design — Alex chooses):

- Real cost of MVP-only: a queued answer that needs a human (or a future
  Claude Code session) to notice and act on manually. Real benefit: ships
  today, zero new integration risk, matches this session's own hard-won
  lesson about proving one path before expanding.
- Real cost of full auto-resume: three separate new integration points
  (Bookworm resume logic, Content Intelligence resume logic, Taxonomy
  resume-into-review-queue logic), each needing its own real hand-test,
  none of which can be tested against a genuine credit-exhaustion event
  without actually running out of credits again. Real benefit: the
  fallback becomes genuinely "invisible" to Alex for whichever callers
  get it, closer to the original pitch ("would be an awesome update").
- A real middle path Council of 5 surfaced, not originally offered as an
  option: wire auto-resume for ONE caller only — Bookworm, since it's the
  most mature pipeline and already has the closest-matching existing
  polling shape (analysis_heartbeat) to extend — and leave Content
  Intelligence/Taxonomy on MVP-only (queued+answered, manual pickup) for
  now. This gets a real, working end-to-end proof on the lowest-risk
  caller without committing to three simultaneous new integrations.

REAL BUG FOUND AND FIXED WHILE BUILDING (not in the original plan):
_placeInsightCascade's tryPhylum() had its own .catch() that turned
EVERY error, including what would become a real credit-exhaustion
failure, into `return null` ("insight doesn't fit this phylum") - which
meant the cascade would silently burn through every remaining phylum/
reword attempt and could score a real insight as garbage
(confidenceScore:0, wrongly recorded as "doesn't fit") instead of ever
surfacing the real failure. Fixed: a tagged fallbackQueued error is now
rethrown instead of swallowed, so _continueAnalyzingInBackground can
stop cleanly and mark the chapter "waiting on fallback" instead of
silently corrupting it with false negatives.
