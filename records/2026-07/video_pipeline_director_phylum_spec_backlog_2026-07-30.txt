PART 2 — COUNCIL OF 5 SCRUTINY (real risks, not padded)
=====================================================================

1. TECHNICAL RISK — "sync to the beat" oversells current capability.
   Building more automation on top of duration-ESTIMATED EDLs, without
   naming this gap, would ship a feature that looks precise and isn't.
   Any UI/copy in this workflow should say "suggested timing" not
   "synced timing" until Finding 4 is actually addressed (Fork 2).

2. SCOPE/COST — Phylum 14's full tree-build-out (if that's what Alex
   wants from "populate the taxonomy phylum path") is the SAME real
   cost class as the 10 already-built phyla (a full 7-step framework
   pass: keywords, tree, data repair, enable, fusion, hand-test). This
   is a separate, standalone body of work from video-pipeline
   automation — conflating the two would blow the scope of "plan the
   video pipeline" into "build an 11th taxonomy phylum," a materially
   bigger ask that deserves its own explicit yes/no (Fork 1).

3. MAINTAINABILITY — building more automation ON TOP of an unverified
   foundation (style_profiles has never once saved successfully) risks
   compounding a silent failure instead of fixing it. Per this
   project's own rule 4 ("one failed fix = stop, get real evidence, do
   not patch blind a second time"), the Director Match save path needs
   a real, direct smoke test BEFORE anything else gets layered onto it
   — not a rebuild, a verification.

4. UX — the "stuck at stage 1" pattern across both real rows suggests
   the current manual 5-stage-button model has real friction: a busy
   producer (working one-handed some days, per Alex's own recent
   accessibility note) is unlikely to reliably click through 5 discrete
   stage-advance buttons over the days/weeks a real video takes to
   finish. Auto-advance triggers (e.g. an edited_path being filled in
   auto-advances status to 'edited') are a real, cheap improvement
   worth planning in, not just the return-nav button Alex explicitly
   asked for.

5. WHY NOT TO BUILD ALL OF THIS NOW — three separate foundational gaps
   (reference_tracks scale/genre backfill, beat_audio_jobs never
   exercised, style_profiles never verified) already sit on the
   existing backlog, independent of this new workflow ask. Stacking
   fresh automation on top of three already-known-empty foundations is
   a real risk of building a flashy front-end over data that doesn't
   exist yet. A real "build order" decision is needed, not just a
   feature list (Fork 3).

PART 3 — 5thDIMENSION RECONCILIATION: the real phased workflow
=====================================================================
Reconciling Finding 1-5 against Alex's actual stated goal (a beat →
music-video workflow using Director Phylum grounding, that produces
eye-gripping short-form content and motivates cinematic beat-making) —
built vs. reported drift is now resolved (Finding 1), so here is the
real, current, already-existing pipeline shape, with what's genuinely
new marked [NEW]:

  Stage 0 — Beat Log (EXISTS, works). Title/key/scale/BPM/mood/energy/
  reference-track/auto colour-palette. Optional F18 Visual Treatment
  checkbox.

  Stage 1 — Content Pipeline entry (EXISTS, works). content_productions
  + video_jobs rows created and linked (status='beat_logged').

  Stage 2 — Director Match (EXISTS, UNVERIFIED). Oracle grounds in the
  real 50-director f14_filmmaker_library, picks one matching the beat's
  mood/key/palette. DIRECTOR_CHOSEN trailer → should write a
  style_profiles row. REAL NEXT STEP: a direct smoke test of this exact
  path (log a beat, run Director Match, confirm a style_profiles row
  actually appears) before building anything downstream of it.

  Stage 3 — Visual Treatment Doc (EXISTS, chained automatically via
  F18 checkbox). Full treatment + 4-scene breakdown, saved into
  content_productions.creative_docs.

  Stage 4 — Storyboard / EDL (EXISTS, DURATION-ESTIMATED not
  audio-derived — Finding 4). [NEW, Fork 2-dependent]: optionally
  upgrade to real beat-grid-anchored timing.

  Stage 5 — Asset creation (OUTSIDE RPGACE, by design — Finding 5).
  Neural Frames prompt (already generated) / OpenMontage (already-
  judged separate tool) / manual filming — Alex's own external step.

  Stage 6 — Editing (OUTSIDE RPGACE) → raw_path/edited_path/
  rendered_path logged back into video_jobs.

  Stage 7 — Export (youtube/instagram/tiktok/beatstars) — export_paths
  logged; F16's Beatstars listing generator reused for that leg.

  [NEW] Cross-navigation both ways: a "↩ [beat title]" button on
  videoPipeline._renderRow's action row (same shape as contentPipeline's
  existing "💬 Oracle session" button) jumping to the linked
  content_production/beat detail — this is Alex's explicit "return
  button to beat logged in" ask. Symmetric addition worth including:
  contentPipeline's own row has no equivalent "→ Video Pipeline" jump
  for a production that HAS a linked video_jobs row — closing the gap
  in both directions, not just one, since the goal is easy back-and-
  forth, not one-way navigation. Tier 1, small, zero architecture risk
  — reuses an established pattern verbatim.

  [NEW, real UX fix per Council-of-5 finding 4] Auto-advance triggers:
  saving a raw_path auto-advances status to 'raw_footage', saving an
  edited_path to 'edited', etc. — removes reliance on manually clicking
  5 stage buttons across a multi-day/week production.
