  - main.js:4057's LOCAL_SERVER constant is DEAD CODE - grepped, exactly
    one match, the definition itself. The real, live pattern Content
    Intelligence actually uses is NOT a direct browser->localhost fetch -
    it's a Supabase async job queue (intel_jobs: id/created_at/url/
    status/progress/error, RLS policy "anon_all" - confirmed via a real
    pg_policies query, not assumed) that Alex's local_server.py polls on
    its own clock and writes results back to. This is the exact reason
    the new feature was built the same way rather than inventing a second
    divergent pattern for talking to the same local server (rule 8).
  - No Supabase Storage bucket existed anywhere in this project before
    today (confirmed: storage.buckets was empty) - audio files are real
    binary content, not JSON-appropriate, so a bucket is the correct new
    piece of infrastructure, not an existing one being missed.

BUILT (Tier-3 migration confirmed by Alex before applying):
  - New table beat_audio_jobs (id uuid pk, created_at, filename,
    storage_path, status, bpm numeric, musical_key text, error) - same
    shape/purpose as intel_jobs. RLS: anon_all, same policy and same
