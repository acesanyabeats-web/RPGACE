1) HEADROOM (chopratejas/headroom) - context compression layer/proxy
   for AI agents; wraps Claude Code, Codex, etc.; MCP server;
   cross-agent memory; "headroom learn" mines failed sessions into
   CLAUDE.md corrections
=====================================================================
FULL DEBATE - real case on both sides.

Side A (Aintergration): a local proxy/wrap tool assumes the user
controls their own CLI invocation of Claude Code on their own machine.
This session runs inside a managed Claude Code Remote container - I
don't control how I'm launched, so `headroom wrap claude` isn't
something I can self-install and have take effect on my OWN current
invocation. Real architectural mismatch for target B specifically
because of THIS environment, not because the tool is bad.

Side B's real case: "headroom learn... writes corrections to
CLAUDE.local.md / CLAUDE.md / AGENTS.md" is, functionally, exactly what
`/Bedtime` and `/Routine` already do by hand every session (mine
CLAUDE.md's own Current State section from real session outcomes) -
this is a genuine, real precedent match, not a stretch. Headroom's
`codeburn optimize`-style analogue (flagging bloated CLAUDE.md,
ghost skills never invoked) would be real, useful, FREE signal on
THIS repo specifically, since CLAUDE.md has grown large and this
project's own doc-discipline rule (added July 28) exists precisely
because of that growth.

Envisioned implementation (not built): Alex would need to run Headroom
on HIS OWN machine, wrapping whatever local Claude Code CLI session he
runs there (separate from this remote session) - `headroom deploy` then
`headroom wrap claude`. This session itself can't self-wrap.

Verdict: REFERENCE ONLY for target B, with a real, actionable half -
Alex could genuinely run `headroom optimize`/`headroom learn` against
his own local `~/.claude/` directory (if he uses Claude Code locally at
all, separate from this remote environment) and get real waste
findings for free. NOT APPLICABLE for target A - RPGACE's own Oracle
calls are bounded single-turn prompts, not a growing agentic context;
Headroom's core compression value (tool outputs, logs, RAG chunks
piling up over a long agent session) doesn't match RPGACE's shape.

2) GRAPHIFY (Graphify-Labs/graphify) - tree-sitter AST knowledge graph
   of a codebase, Claude Code skill, local + free for code (LLM only
   for docs/PDFs/images)
=====================================================================
FULL DEBATE - the strongest real candidate in this batch.

Side A: requires `uv tool install graphifyy` + a real build pass
(`/graphify .`) over the whole repo - genuine setup cost, and a new
Python dependency (mitigated: Python already runs in this session,
confirmed by this session's own `archaeologist.py` smoke test).

Side B's real case: RPGACE is exactly the kind of codebase this tool
targets - one ~16,400+ line file (`rpgace_core.js`) with dozens of
modules, plus six real oversight docs (`patch_notes.html`,
`interconnection_map.md`, etc.) that already try to describe cross-
module connections by hand. Graphify's "god nodes," "communities,"
and cross-file link resolution would answer "what actually connects to
what" faster than grepping - a GENUINELY DIFFERENT question from what
Commit Archaeologist answers (archaeology = why/history; graphify =
what/structure), so this is not a rule-8 duplication of item #1's
installed skill. It can also graph the docs alongside the code (its
own docs/PDF/markdown-link support), which could surface real doc-vs-
code drift candidates for a future `/5thDimension` pass to check.

Envisioned implementation (not built): `uv tool install graphifyy`,
`graphify install --project` (writes `.claude/skills/graphify/`),
`/graphify .` run once against the RPGACE repo root, committing the
resulting `graphify-out/` per its own recommended team workflow.
Tier: 2 (new tool + new committed output directory, no RPGACE runtime
change, no spending).

Verdict: ADOPT CANDIDATE for target B - the strongest one in this
batch. Not decided here; flagged for Alex's own go-ahead the same way
Commit Archaeologist was, since it's a real new dependency + a real
new committed directory, not a zero-footprint change.

3) PONYTAIL (DietrichGebert/ponytail) - Claude Code plugin enforcing a
   YAGNI/minimal-code ladder before writing anything; real benchmark:
   -54% LOC, -22% tokens, 100% safety maintained
=====================================================================
FULL DEBATE - genuinely contested, not a clean adopt or reject.

Side A: this session's own system prompt ALREADY carries an explicit,
similar instruction ("Don't add features, refactor, or introduce
abstractions beyond what the task requires... Three similar lines is
better than a premature abstraction"), and CLAUDE.md's rule 11 (token
cost) plus rule 8 (dedup) cover much of the same ground in prose.
Installing a second mechanism for the same discipline risks being a
real rule-8 duplication - the exact question this skill needed to ask
before recommending it.

Side B's real case: prose instructions are a standing rule I read once
per session; Ponytail's own real, measured benchmark (54% LOC cut, 100%
safety preserved) suggests an operationalized decision ladder ("does
this need to exist? already in the codebase? stdlib? native? installed
dep? one line? THEN the minimum") catches real over-builds that a
general "don't overengineer" instruction alone does not - its own
example (a date picker reaching for a whole library instead of native
`<input type="date">`) is a concrete failure mode worth guarding
against explicitly, not just in spirit.

Envisioned implementation (not built): `/plugin marketplace add
DietrichGebert/ponytail` + `/plugin install ponytail@ponytail` (two
prompts, per its own install note) in this Claude Code environment.
Tier: 1 (a plugin install, no RPGACE code/schema change, fully
reversible via `/plugin remove ponytail`).

Verdict: genuinely undecided by design - real cases on both sides
survived scrutiny, which is `/restructure` doing its job, not failing
to reach a conclusion. Alex's call: install as a real second check
alongside the existing prose discipline, or treat the existing CLAUDE.md
instruction as sufficient and skip it.

5) LLMLINGUA (microsoft/LLMLingua) - academic prompt-compression
   research library (trained small LM does the compressing)
=====================================================================
Quick verdict, real reasoning, not a full debate - REJECT for the
library itself, one real REFERENCE finding underneath it.

Same value proposition as Headroom (#1) - compress what gets sent to
an LLM - but heavier (needs a local ML model: GPT2-small/LLaMA-7B or a
BERT-based classifier for LLMLingua-2) and with zero Claude-Code
integration (no wrap/plugin/MCP mechanism, unlike Headroom). Adopting
it would mean building a second, worse-integrated version of what item
#1 already covers - a real rule-8 duplication, not a fresh idea.
REJECT as the library.

One real thing underneath it worth naming separately: its SecurityLingua
sub-project (compression that reveals jailbreak intent behind an
attack) is a genuinely different idea from prompt COMPRESSION for cost
- it's a compression-based SAFETY technique. RPGACE already has a real,
built defense in this exact space (`oracleFetchGuard`, hardening Oracle
against prompt injection from fetched web/YouTube/Instagram content),
and a real, still-open, self-flagged gap (whether fetched content could
also inject raw HTML/script, a separate risk class named in a July 22
Aintergration pass and never resolved). SecurityLingua's technique is
REFERENCE ONLY for that specific, still-open gap - not built, just
named as a real pattern worth knowing about if that gap is ever
revisited.

6) GPTCACHE (zilliztech/GPTCache) - semantic (embedding-based) cache
   for LLM query/response pairs
=====================================================================
Quick verdict - REJECT for target A on product-fit grounds, not just
architecture.

This isn't just a stack mismatch (though it is one - needs a vector
store like Milvus/FAISS, a real new piece of infra beyond even the
pg_trgm work shipped earlier today). It's a real PRODUCT-fit rejection:
Oracle is a personal, conversational assistant - semantically caching
"similar" questions and serving a stale cached answer directly
undermines the thing that makes a personal assistant feel present and
current, unlike a support-FAQ bot where two similar questions truly
want the identical answer. Not applicable for target B either - a
Claude Code session's full context matters on every turn; nothing about
this session is "the same question asked slightly differently."

   open-weight/local models (Transformers, vLLM, llama.cpp)

target B either - I already produce structured output natively when
asked.

10) TIKTOKEN (openai/tiktoken) - OpenAI's own BPE tokenizer library
=====================================================================
Quick verdict - NOT APPLICABLE, and using it would actively mislead.

tiktoken tokenizes for OpenAI's own vocabularies (cl100k_base,
o200k_base). Claude uses a different tokenizer entirely - using
tiktoken to estimate RPGACE's real Claude API token/cost numbers (rule
11's whole reason for existing) would produce confidently WRONG
figures, not just unhelpful ones. Reject, not a maybe.
