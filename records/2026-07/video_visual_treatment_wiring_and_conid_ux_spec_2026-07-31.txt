COUNCIL OF 5 - IMPLEMENTABILITY, ITEM BY ITEM
=====================================================================
1. "Beatstars Listing" -> "Generate Beatstars Listing"
   Tier 0/1. Trivial label change, zero risk. BUILD NOW.

2. Delete button per ConID
   Tier 1. Real risk named above (FK violation if a linked video_jobs
   row exists) - handled by checking the same linkedIds map _refreshWidget
   already builds (Engineer pass 03), warning explicitly in the confirm
   dialog when a link exists, and catching/toasting the FK error clearly
   rather than pretending success. Two-click confirm() matches this
   project's own established "confirm destructive actions" rule (rule 8
   of the process rules) and mirrors Idea Bank's real precedent closely
   enough to count as reuse, not a new pattern. BUILD NOW.

3. "Visual Treatment function" on Content/Video Pipeline
   Tier 2 (touches 2 modules, real UX wiring). The capability already
   exists (visualOracle CMDS[1] + _saveDocToProduction); the real gap is
   the missing direct link from a specific ConID. Since the button
   already knows the exact target row (row.con_id / row.id), the manual
   "which ConID does this belong to" save-picker step is unnecessary
   overhead here and can be skipped - auto-save straight to that row's
   creative_docs.visual_treatment, reusing _saveDocToProduction's real
   trailer-parsing logic rather than re-inventing it (rule 8, dedup).
   Beat data (title/bpm/key/scale/mood) is pulled from the linked
   video_jobs.script the same way _generateBeatstarsListing already
   does, so the command doesn't need Alex to hand-type it twice. BUILD
   NOW - this is the single most direct answer to Alex's stated gap.

4. Content Pipeline as "step 1/2/3/4" overarching ladder
   Tier 2, real design fork: change the underlying `status` enum
   (migration + ripple risk to every existing consumer of that column
   across 3 creation paths) vs. keep the existing 6 real status values
   and give music_video-type ConIDs their own 4-step DISPLAY label
   mapping only. Chosen: the display-mapping route - zero schema
   change, zero ripple to Content Repurpose/Idea Bank's own use of the
   same column, and the content_type branch point already exists (July
   30 pass) to hang this off cleanly. Mapping: Idea/Scripted ->
   "1. Beat Logged"/"2. Visual Treatment", Filmed/Edited ->
   "3. Video Generation", Posted/Analysed -> "4. Captions Ready" - this
   keeps every other module reading `.status` unchanged while giving
   Alex's exact mental model as the visible label on music_video cards
   only. BUILD NOW (labels only, no data migration).

5. Video Pipeline "taking the script/keywords/context... to build
   characters, scenes and the whole music video in sync to the beat
   with timestamps"
   REAL, HONEST LIMIT - not buildable this pass. This is full generative
   video synthesis synced to a real audio beat-grid. Two separate,
   already-identified capability gaps stand between here and there,
   neither closed by this pass:
     (a) No real beat-grid/onset audio analysis exists yet (Slice C,
         already planned July 30, needs the existing librosa hook
         extended to onset/beat detection - unbuilt).
     (b) No video-rendering/generation engine exists inside RPGACE at
         all - OpenMontage was Aintergration-verdicted (July 24) as a
         separate OPERATED tool, explicitly never embedded in RPGACE's
         own runtime (toolchain mismatch: Python/Node/FFmpeg vs.
         RPGACE's deliberate zero-build-step vanilla JS).
   Pretending to build (5) without (a) and (b) would be exactly the
   kind of overclaim this project's own rules explicitly forbid (Oracle
   self-awareness incident, July 28 - a live capability gap misstated
   as built). REAL, HONEST STEP THAT IS BUILDABLE NOW: give videoPipeline
   a "📄 Script + Treatment" section on the job detail view, surfacing
   the real script (video_jobs.script), the real EDL shot list
   (video_jobs.edl), and the real saved creative_docs (visual_treatment/
   director_match/storyboard, read off the linked content_productions
   row) together in one place - so whatever data DOES exist is visibly
   ready to hand to OpenMontage manually, or to Slice C once it ships,
   rather than scattered across 3 different Oracle conversations Alex
   has to remember and re-find. This is the correct, honest interpretation
   of "video pipeline should take the script/keywords/context" available
   today - a real handoff surface, not fake automation. BUILD NOW.
