=== PHASE 4: MINOTAUR SIDEKICK DESIGN (the brief Findings 6+7 argue for) ===

Governing constraint from Finding 7: do NOT become a sixth hand-maintained snapshot. Two
phases, deliberately separable so Council of 5 can clear one without the other.

PHASE A — "surface what already exists" (cheap, no new content, no Oracle calls):
A new rpgace_core.js module (RPGACE.register('minotaurGuide', {...}), same pattern as every
other module) adding one dashDeck card ("🐂 Minotaur Guide") that opens via the existing
dashDeck._popup() helper (dedup discipline — the 26 existing overlay sites already prove this
is the one correct pattern, no new popup scaffolding). Inside: the SAME river copy already
written and kept honest in minotaur_map.html, rendered from a shared data structure instead of
copy-pasted a second time — extract minotaur_map.html's river content into one JS object both
the standalone page and the new in-app popup read from, so there is exactly one copy, not two
(this is the actual rule-8 fix Finding 5 calls for, applied narrowly to just this one piece
rather than all three duplicate diagram systems at once). A simple picker jumps between the
Bird's-Eye View and any of the 11 rivers. Zero Oracle cost. Zero new data pipeline. Converts
"the manual" from a link Alex has to remember to open separately into something reachable
without leaving the app.

PHASE B — "answer open-ended questions in Minotaur voice" (real new scope, needs Oracle):
A chat-style box in the same popup for questions the static river cards don't cover. Would
reuse oracleAppGrounding's existing pattern exactly (rule 3: never hand-roll a second fetch
to /api/oracle) — grounds the system prompt with real system_flow_map.md/interconnection_map.md
excerpts plus the Minotaur vocabulary (river/tributary/estuary/fork/reservoir), and reuses
_liveFactsLine()'s already-built live-query plumbing for any live number it needs (module
count, pending-review count) rather than building a second live-fact fetcher. This is the part
that costs real tokens on every use and is real new maintenance surface — flagged as the part
most worth Council of 5 scrutiny on whether it's actually wanted versus Phase A alone being
sufficient (Finding 8's counter-case applies most directly here).

Explicitly NOT proposed: a full architectural fix unifying all three diagram systems (manual's
Level 1-4, system_flow_map.md's Mermaid, minotaur_map.html's rivers) into one live-queried
source — that is a real, much larger Tier-2/3 undertaking Finding 8's counter-case argues
against attempting in this same session, and is named here only as a possible future item if
Council of 5 or a later session decides the smaller Phase A/B win isn't enough.
