Real work items (W-numbered - a new series, kept separate from the
Massive Expansion plan's A-items and the Galaxy Map's G-items, since
Alex asked for a genuinely separate tracked plan):

W1 (rename + relocate) — Corpus physically becomes part of Bookworm's
   own card/page (not just a conceptual rename) - "music corpus inside
   of bookworm." Real, low-risk UI/entry-point move, same shape as the
   Aug 15 A5 Phase 1 pattern (dashDeck._openBookworm gains a Corpus
   section/jump button; refCorpus's own module/data untouched).

W2 (rename) — File Analyzer -> "Videoworm", the article-analysis path
   -> "Articleworm" (matches A8's original text exactly). UI labels/
   card titles only at this stage - zero pipeline change.

W3 (rename, honestly scoped) — Corpus -> "MusicWorm" identity in the
   UI. Real audio-listening capability stays explicitly OUT of scope
   for this plan's first pass (confirmed still "a bare idea," zero
   pipeline exists per Part B.6) - a real, separate future phase, not
   silently implied as done by the rename. Any MusicWorm-labeled UI
   this plan builds must say plainly "insight extraction not yet
   built" rather than imply parity with Bookworm/Videoworm.

W4 (picker) — A real "which worm?" picker landing on Bookworm's own
   card, toggling between worms on one page (per A8's exact vision,
   now that W1 puts Corpus/MusicWorm there too).

W5 (the real new architecture piece) — A shared, additive
   insight-to-Encyclopedia wrapper function. Whenever ANY worm places
   a real insight (Bookworm's _placeInsightCascade, ciAutoPropose's
   _scan, and MusicWorm's own pipeline once W3's later phase builds
   one), the SAME wrapper also writes one real `encyclopedia` row -
   the quote/excerpt plus context explaining that specific insight -
   cross-linked via the EXISTING `taxonomy_node_id` column (reuse, not
   a new column - confirm the reverse-direction write is safe at build
   time). Critically additive: never replaces or gates the existing
   taxonomy_tree/taxonomy_proposals write, which stays the real
   structural-knowledge decision mechanism - Encyclopedia becomes a
   parallel, browsable "evidence" layer, not a second placement
   engine. (This reading comes directly from Alex's own words - "entries
   ... that explain A CHOSEN insight" - an insight that's already been
   decided, not a new decision path - not re-asked as a separate
   interrogation question since his own phrasing already resolves it.)

W6 (real code reduction) — Once W5's wrapper exists, check whether
   Bookworm's and ciAutoPropose's own placement-call boilerplate can
   route through ONE shared function instead of two independently-
   maintained call sites (rule 8). This is the concrete, checkable
   version of Alex's own "reduce code" goal - not assumed, verified
   against the real diff once W5 is built.

W7 (connects to, does not replace, the existing A4 backlog item) —
   Revisit A4 ("Content Intelligence real-insight extraction volume")
   in light of W5: does giving Content Intelligence insights a second,
   cheaper output channel (an Encyclopedia entry, no taxonomy-tree
   structural decision required) change how urgent raising the 5-
   video/9-proposal cap is? A real, connected question - not assumed
   answered by W5 alone. A4 stays its own tracked item; W7 is the
   cross-reference check, not a merge (the two are related but
   distinct real problems - taxonomy volume vs. Encyclopedia coverage).

W8 (Bookworm UX) — Real, already-logged, never-built: replace the
   modal-chain chapter review with a card-list view (CLAUDE.md's own
   July 17 backlog item 1). Matches Alex's "Both" answer on complaint
   type.

W9 (Bookworm feature) — Real EPUB support (the already-named dry-
   riverbed item).

W10 (Encyclopedia's own revamp, now genuinely warranted) — Once W5
   ships, Encyclopedia's real row count and importance grow
   materially beyond today's 70 rows (sourced from Oracle-chat saves
   only). Real candidates: a "source worm" badge/filter per entry (so
   Alex can browse "show me only Videoworm-sourced entries"); revisit
   ENC_CATEGORY_MAP's keyword-matching quality at higher real volume.

Real, honest sequencing note: W5/W6/W7 are the real architectural core
(and the highest-risk, since they touch Bookworm's already-working,
carefully-tuned placement pipeline - built strictly additive to keep
regression risk low). W1/W2/W3/W4 are real but lower-risk UI/identity
moves. W8/W9/W10 are real, independent quality-of-life items that can
happen in any order relative to the others - flagged as such so a
future session doesn't assume they must wait for W5.
