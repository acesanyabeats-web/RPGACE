4. REAL TECHNICAL FINDING: THE OBVIOUS APPROACH DOESN'T WORK
=========================================================================
The natural way to attribute a real error to "which module" would be a
stack trace. Tested directly in headless Chromium against the live
minified app (not assumed): RPGACE.register() modules are plain object
literals, so V8 reports a real thrown error as "at Object._submit (...)"
— the enclosing module name ("beatLog") is NOT present in the trace at
all. This is a real, structural consequence of this codebase's own module
convention, discovered by testing, not assumed.

Real, viable fix found instead: mangle:false (this project's permanent
minify setting) DOES preserve every real method name. A new generator
script, scripts/generate_method_module_map.py, parses rpgace_core.js
directly (real brace-depth matching per RPGACE.register('name', {...})
block, not a naive regex) and builds a method-name -> owning-module
lookup, keeping ONLY unambiguous entries (exactly one module defines that
method name). Real, measured result: 58 modules scanned, 432 of 456
distinct method names resolve unambiguously (94.7%); 24 genuinely
ambiguous names (_inject/_render/init/_close/open/run/toggle/etc, shared
by 2-8 modules each) are correctly EXCLUDED, never guessed. Confirmed via
direct test: "_submit" -> "beatLog" (real, single owner); "_inject" ->
null (real, 8 owners, correctly rejected rather than guessed).

Re-run this script and paste its output into errorLog.METHOD_MODULE_MAP
whenever a module gains/loses/renames a method — same "regenerate then
re-embed" discipline as the Galaxy Map's own generator-script pipeline.

5. THE REAL BUILT MECHANISM (rpgace_core.js, errorLog module)
=========================================================================
errorLog._capture(type, source, message, opts) now accepts an optional
opts.stack. window.onerror/unhandledrejection pass e.error.stack/
e.reason.stack; toast()'s own new call passes (new Error()).stack.

_extractModule(stack) walks the stack's real frames, checks each method
name against METHOD_MODULE_MAP, returns the first confident match or null
— never a guess.

On a genuinely NEW error (not a dedup-increment of an existing active
row):
  1. If a module was identified, look up its real perspective_reports row
     (scope_level='module', scope_id=<moduleName>, status='active') and
     attach linked_perspective_id/expected_baseline to the error_log row —
     real Q1 answer, the existing baseline becomes real live context on
     the error itself.
  2. Insert the error_log row via raw fetch + Prefer:return=representation
     (RPGACE.sb.insert() never returns the new id — the standing CLAUDE.md
     landmine, avoided here the same way phylumPath._insertNewSteps/
     bookworm._createBookFromExtraction already do, rule 8).
  3. If a module was identified AND the insert's representation came back,
     look up smoke_test_items (category='RPGACE App — Modules',
     item_name=<moduleName>). If found, PATCH it to status='broken' with a
     real broken_note derived from the actual error message, and
     linked_error_id set to the new row — reusing the EXACT SAME columns
     smoke_test.html's manual "Mark Broken"/"Fixed, Re-confirm" buttons
     already read/write, just triggered from the opposite (automatic)
     direction.
  4. If that smoke_test row has a linked_plan_item_id, look up the real
     ceo_plan_items row. Only if its CURRENT status is genuinely 'green'
     does it flip to 'purple' (real /colourgradient discipline — a
     regression requires a real prior-green state; anything else is
     correctly left alone).
Every step fails open independently (try/catch + .catch on each real
network call) — a cascade step failing never blocks the base error_log
insert, and never throws a second, louder error in front of Alex.

future_integrations.html's own #purple-live section already live-queries
ceo_plan_items for status='purple' (confirmed via direct read — zero
changes needed there; it was built empty and waiting for exactly this).

7. SCOPE, HONESTLY STATED
=========================================================================
- This only auto-flips a module's smoke_test row when a genuine JS
  exception/promise rejection/error-toast is captured AND attributed to
  exactly one module. A real bug that doesn't throw and doesn't toast
  (silently wrong output) is invisible to this, same as it always was.
- Module attribution covers ~95% of distinct method names — the ~5%
  ambiguous ones (mostly generic lifecycle methods like init/_inject/
  _render) never get auto-attributed, by design (never a wrong guess).
- The purple cascade only reaches modules that (a) have a real smoke_test_
  items row AND (b) that row has a linked_plan_item_id pointing at a
  currently-green ceo_plan_items row — most of the 44 module rows have no
  linked_plan_item_id yet (they track modules, not plan items), so most
  real errors will stop at "smoke_test flips to broken," which is itself
  the real, valuable, new signal.
- error_log itself IS the real async queue Q3 asked for — no new table.
  A new CLAUDE.md session-start check (mirroring the existing oracle_
  dev_suggestions/graphify_jobs/system_map_flags pattern) plus a real
  /Routine tie-in are the "picked up by a future session" half of the loop.
