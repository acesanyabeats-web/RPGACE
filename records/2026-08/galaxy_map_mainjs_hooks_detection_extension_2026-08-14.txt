REAL ROOT CAUSE, CONFIRMED (GODMODE evidence pass, not guessed)
---------------------------------------------------------------------------
The entire Galaxy Map detection pipeline (compute_intra_river_flow's 4 signals,
compute_function_ui_signals' 2 signals) only ever reads rpgace_core.js. It has
zero visibility into:
  - main.js, where the real DOM/button-trigger side of many modules lives
    (RPGACE's own documented override convention: main.js defines an
    original/stub function, a rpgace_core.js module's init()/_intercept()
    reassigns window.X to the real implementation).
  - index.html's own 93 real inline onclick="fnName(...)" attributes — the
    most direct, confirmable evidence of a real user-facing control.
  - RPGACE.hooks.fire()/hooks.on() pairing — already named as an invisible
    gap in compute_intra_river_flow()'s own docstring, never actually built.

Confirmed concrete evidence chain for authGate (the sharper of the two
"mystery" cases — its real function wasn't even a Level-3 NODE, not just
missing UI evidence):
  index.html:61 <button onclick="checkPassword()">ENTER THE REALM</button>
  -> main.js:12 async function checkPassword(){ ... window.RPGACE_verifyPassword ... }
  -> rpgace_core.js:18309 window.RPGACE_verifyPassword = function(pw){ return
     RPGACE.modules.authGate.verify(pw); };  (zero indentation — true module-
     scope, OUTSIDE the register() object literal, the ONLY such case in the
     whole file, confirmed by a dedicated grep)

Because this assignment sits outside the `key: function` object-literal
shape every other module method uses, parse_module_functions()'s original
regex never saw it at all — authGate genuinely only had 2 Level-3 nodes
(verify, _installFetchWrap) before this pass, with its real password-verify
bridge invisible to the whole pipeline.

pathRouter's real evidence (rpgace_core.js:19069-19146):
  RPGACE.hooks.on('rpgace:login', ...) / RPGACE.hooks.on('page:show', ...)
  window.addEventListener('popstate', function(e){ ... showPage(name); ...})
Both hooks are fired from rpgace_core.js's own real "FUNCTION WRAPPERS"
section (lines ~395-544, its own comment: "Wraps existing main.js functions
to add hook fire points... Do NOT patch main.js — wrap here instead") —
checkPassword() is wrapped to fire 'rpgace:login' on a real successful
login; showPage() is wrapped to fire 'page:show' after every nav switch.
Neither hook-firing nor the popstate listener were detected by anything
before this pass.

   by both parse_module_functions() and _function_bodies() so they can
   never silently diverge). Matches the standard `name: function`/`name:
   async function` shape, OR a real zero-indent `window.<Name> = function`
   module-scope statement — deliberately anchored at column 0 so the ~20
   OTHER window.X assignments elsewhere in the file (all nested 4+ spaces

   evidence of rpgace_core.js's own addEventListener usage (never guessed):
   added 'input'(x5)/'keydown'(x3)/'popstate'(x1)/'change'/drag+touch/
   focusin event types to INPUT, and a bare `showPage(` call (35 real
   occurrences) to OUTPUT — a load-bearing signal needing zero cross-file
   scanning since it's already inside the file being read.

   does `window.<Y> = function` — direct OR via the one real main.js hop.
   Wired into compute_function_ui_signals() (drop-in, backward compatible —
   existing callers automatically inherit the improved evidence with zero
   further code changes needed on their part).

4. CORE_WRAPPER_HOOKS + compute_hook_signal_edges() — real
   RPGACE.hooks.fire()/hooks.on() module-to-module pairing detection,

   real 'core-wrapper[mainjs:<fn>]' firer. Wired into
   compute_intra_river_flow() as a new same-river Signal 5 (real, honest,
   MEASURED finding: zero same-river hook pairs exist anywhere in this
