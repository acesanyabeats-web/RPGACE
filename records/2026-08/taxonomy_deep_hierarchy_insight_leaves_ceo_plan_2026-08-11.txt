FORK B (Alex asked to see real tradeoffs -- UNRESOLVED, his call)
THE INSIGHT-ACCUMULATION MECHANISM
=====================================================================
Real problem restated: right now, ONE leaf holds ONE overwritten
piece of content (explainer + deep_content.generated). Alex wants a
leaf endpoint to hold a growing, readable LIST of every real insight
that's ever been placed there, opened as one readable text view.

--- OPTION 1: New dedicated table, built on the taxonomy_decision_log
    precedent (real evidence: this table already exists, already
    logs one row per placed insight with node_id/path/insight_text/
    source, fire-and-forget on every real _insertNewSteps call --
    rpgace_core.js:9115). ---
REAL FOR: a genuinely append-only, purpose-built shape -- one row per
  insight, trivially queryable ("all insights for leaf X, newest
  first"), no risk of corrupting existing explainer/deep_content
  data, and taxonomy_decision_log already proves the exact write
  pattern works in production (42 real rows exist today).
REAL AGAINST: taxonomy_decision_log currently has only 42 rows total
  against 174+ real existing leaves in phyla 1-10 alone -- meaning
  most of those leaves' real founding insights were NEVER logged
  there (they predate this logging, or were created through a
  different path). Building the new leaf-endpoint UI on top of this
  table means most EXISTING leaves would open to an empty or
  near-empty insight list on day one, even though they have real
  deep_content already -- a real, visible regression unless handled
  (see "retroactive backfill" below).
REAL COST: a new table (or a new dedicated one, since
  taxonomy_decision_log is a generic audit log for ALL placements,
  not scoped to "insight text meant for human reading" -- reusing it
  directly risks conflating two different real purposes, a rule-8
  question worth Alex's own call) + a new read view + a new leaf-
  endpoint UI (the "opens a readable text file" surface Alex
  described) + a real migration step: each of the 174+ existing
  leaves' current single explainer/deep_content becomes "insight #1"
  in the new list, so nothing existing goes blank.

--- OPTION 2: Reuse deep_content as a growing JSON array instead of
    one overwritten object. ---
REAL FOR: no new table, smaller real schema footprint -- deep_content
  is already a jsonb column, already holds structured data
  ({"generated":..., "generated_at":...}), extending it to
  {"insights":[{...},{...}]} is a real, contained change touching
  taxonomy_tree's own existing column rather than adding new
  infrastructure.
REAL AGAINST: every current READER of deep_content.generated (at
  least 3 real call sites found this session alone --
  _generateArticleText's synthesis, jargonEncyclopedia's glossary
  view, taxonomy_map.html's live query) expects ONE string, not an
  array -- every one of those needs updating in the same pass or it
  silently breaks/shows garbage. Real, wider blast radius than Option
  1 for a comparable amount of new capability.

REAL RECOMMENDATION (not a decision -- Alex asked to choose): Option
1 (new dedicated table) is the lower-risk path specifically because
it doesn't touch any of deep_content's existing readers, and
taxonomy_decision_log already proves the write pattern works. The
real backfill problem (existing leaves showing empty) is solvable
(migrate each leaf's current single deep_content.generated into
insight #1 of the new list, one real one-time script) and is smaller
work than auditing/fixing every existing deep_content reader under
Option 2.
