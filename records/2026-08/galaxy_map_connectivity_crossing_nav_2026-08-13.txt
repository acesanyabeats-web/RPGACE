CROSSING REDUCTION — real, measured, honest about limits
-------------------------------------------------------------
Standard technique adopted (Aintergration'd, not invented): Sugiyama/
Eades barycenter heuristic for rank-column reordering (Level 2/3), a
real greedy 2-opt local search for Level 1's ring ORDER (radial layouts
have no rank, so barycenter doesn't directly apply there).
REAL FAILED ATTEMPT, not hidden (rule 4): a DFS-over-adjacency ring
order was tried first for Level 1 and MEASURED WORSE (17 crossings vs.
15 for the old plain numeric order) — discarded rather than shipped as
a claimed fix. Replaced with the 2-opt search, which by construction can
only match-or-beat its starting point: verified 15 -> 6 crossings (60%
real reduction), re-confirmed via 3 fresh process runs.
Level 2/3's barycenter pass is real and correctly implemented but
empirically found to be mostly a NO-OP in the rivers tested (River III/
V/VII/XI: 0 crossings before and after in 3 of 4; River XI stayed at 1
crossing before and after) — NOT because it's broken, but because most
buckets are too small (1-3 items) for within-bucket reordering to have
anything to improve, and River XI's one remaining crossing is a
STRUCTURAL property of the rank-to-X-position mapping itself (the "-1"
helper bucket sits to the RIGHT of the terminal, so an edge from an
upstream rank-1 module can pass through the terminal's own column) —
genuinely not fixable by reordering, would need Alex's own decision on
whether to change the rank_x layout he originally directed. Flagged as
a real, specific, NOT-built follow-up rather than claimed solved.
Minimizing edge crossings on a general graph is NP-hard — this is a
real, honest limit of ANY heuristic, stated plainly, not a "zero
crossings, guaranteed" claim.

A REAL, UNRELATED BUG FOUND WHILE VERIFYING (rule 4's own discipline paid off)
-------------------------------------------------------------------------------
Testing idempotency (re-running the exact same script against the exact
same source twice) found galaxy_map_level3.html was NOT reproducible —
two fresh runs produced genuinely different node positions/canvas sizes.
Root cause: `compute_function_rank()`'s DFS iterates `callees.get(f,())`,
a `set()` — Python hash-randomizes string-set iteration order PER
PROCESS (PYTHONHASHSEED unset, confirmed), so a fresh process could walk
the same real edges in a different order and land at a different (still
individually valid, but non-reproducible) layout. This predates this
session's edits (present since the original G14 rollout) — the earlier
"confirmed idempotent" claim on that commit was real but incomplete: it
only checked within-process consistency, not a genuinely fresh process
run. Fixed with `sorted(callees.get(f, ()))`; re-verified idempotent
across 3 fresh process invocations. A SIMILAR set-iteration pattern
exists in `build_component_zone_map()` (graphify_river_group.py
~line 1283, `adj.get(x, set()) - comp`) — a different, older pipeline
not touched by this pass, flagged as a real, same-class latent risk for
a future session, not fixed here (scope discipline).
