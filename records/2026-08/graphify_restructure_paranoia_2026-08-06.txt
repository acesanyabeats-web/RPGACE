2) HOW TO USE + READ IT — the real rundown (for Alex)
------------------------------------------------------------------

**Three commands, once a graph exists** (`graphify-out/graph.json`):
- `graphify query "<question>"` — broad context, BFS by default (add
  `--dfs` to trace one specific chain instead of a broad neighborhood).
  `--budget N` caps the answer at N tokens (default 2000) — raise it if
  the output says "TRUNCATED."
- `graphify explain "<name>"` — a full profile of ONE node: its source
  file, type, how many connections it has ("degree"), then every real
  connection with its relation/confidence/source file.
- `graphify path "<A>" "<B>"` — the shortest real chain of connections
  between two named things, with the relation label on each hop.

**Reading the output:**
- `Traversal: BFS depth=N | Start: [...] | N nodes found` — the header:
  which mode ran, which node(s) it started from, how many nodes it
  found in the neighborhood.
- `NODE <label> [src=<file> loc=<line> community=<cluster name>]` — one
  real thing in the graph (a doc section, a function, a file). `src`/
  `loc` are a real citation — click through to verify, same discipline
  as everywhere else in this project (never trust a claim without a
  source).
- `EDGE <A> --<relation> [<confidence>]--> <B>` — a real connection
  between two nodes. `confidence` is one of EXTRACTED (directly seen in
  the source), INFERRED (graphify's own reasonable guess), or AMBIGUOUS
  (uncertain — treat these as a lead to verify, not a fact).
- `community=<name>` — which cluster graphify's own community-detection
  grouped that node into (a rough "these things are related" signal,
  not a hand-authored category).
- A `TRUNCATED` footer means the real answer got cut at the token
  budget — either raise `--budget` or ask a narrower question.

**The one thing to know before trusting a "no results" answer**: a raw,
natural-language question (multiple words, casual phrasing) often
returns nothing useful because the matcher is literal substring
matching against the graph's own vocabulary — not because the topic
genuinely isn't in the graph. Real fix demonstrated in Demo A/B above:
extract the real vocabulary first, pick a few matching words from THAT
list, then query with those. This is real, documented graphify
discipline (`references/query.md` Step 0) — this session's earlier
queries skipped it, which is why they looked more broken than they are.

3) /paranoia + /restructure — CAN GRAPHIFY PLUG INTO /update-logging-system
   (and Routine/scope/Summary/GODMODE/commit-archaeologist/Engineer,
   and RPGACE more broadly) FOR REAL TOKEN SAVINGS?
------------------------------------------------------------------

**Real evidence (from the live demo above, not assumed):**
- graphify genuinely works well for DOC-content cross-referencing (all
  of CLAUDE.md/interconnection_map.md/ai_tooling_and_rules_map.md/
  patch_notes.html/the dated .txt backlog files) — Demo B proved this,
  a single call surfaced real cross-doc connections a sequence of greps
  would have taken longer to assemble.
- graphify genuinely CANNOT answer "what does RPGACE module X do" for
  ANY module defined via `RPGACE.register('name', {...})` — which is
  every real module in `rpgace_core.js`, RPGACE's own standing
  convention. This is not a staleness problem a rebuild fixes (Demo F);
  it's a structural mismatch between graphify's AST extractor and
  RPGACE's own module-declaration pattern.
- The doc-content graph itself is ALSO going stale in real time: the
  `--code-only` rebuild this session deliberately left 132 changed doc
  files unindexed (semantic/LLM extraction needs a key or a real
  subagent-dispatch — a real cost, not run in this pass, logged as a
  deliberate scope decision per rule 11, not silently skipped).

**Aintergration/restructure lens A — RPGACE the application**: N/A.
graphify is a Claude-Code-side dev tool; it has no runtime relationship
to the deployed app at all.

**Aintergration/restructure lens B — this Claude Code session/workflow**,
against `/restructure`'s own 3 axes:
- *Shorter code*: N/A — graphify is external tooling, not code inside
  any RPGACE skill file. The real question is whether a skill's OWN
  instructions could get shorter by delegating evidence-gathering to
  `graphify query` instead of spelling out a grep/Read procedure. For
  the DOC-reading half of evidence-gathering, yes, plausibly. For the
  CODE-reading half, no — the extractor gap above blocks it.
- *Quicker load/response*: real, demonstrated win for doc-content
  questions (Demo B: one call, real cross-doc answer). Real, demonstrated
  LOSS for code-structure questions (Demo C/D: a wasted round-trip that
  still needs a grep afterward — worse than just grepping first).
- *More detailed/context-appropriate/meticulously-picked output*: real
  win for docs (community clustering surfaced connections a targeted
  grep might miss). Not applicable for code — there's nothing to surface
  when the query returns zero nodes.

**Debate — FOR plugging graphify into `/update-logging-system`
specifically**: its own actual job (per its SKILL.md) is a DOC-artifact
completeness checklist, not a code-structure question — that's exactly
the half of graphify's capability that's real and demonstrated working.
Before marking an artifact `[ ] — skipped, no structural change`, a
quick `graphify query` on the change's own topic words is a genuinely
cheap, genuinely useful first-pass check for "does an existing doc
section already cover this," catching a real dedup opportunity the
checklist doesn't currently have any mechanism for.

**Debate — AGAINST, real honest case**: graphify's OWN index needs to
stay current to keep delivering that value, which is the exact same
"needs enforced upkeep or it silently goes stale" problem
`/update-logging-system` exists to solve for the seven oversight docs —
adding it as a dependency inside that very framework, without also
tracking the graph's OWN currency, would just relocate the staleness
problem one level down, not solve it. A stale graph returning a
plausible-but-wrong "no existing coverage" read would be actively worse
than skipping the check and grepping directly — false confidence costs
more than admitted ignorance.

**Resolution**: Adopt, narrowly and conditionally — not as a blanket
"plug graphify into everything" move. Two concrete additions:

1. `/update-logging-system`'s own dependency map gains graphify's index
   as a tracked artifact: any change that touches `rpgace_core.js`/
   `main.js`/`api/*.js` structure should include `graphify . --update
   --code-only --no-viz` (free, no LLM key, ~seconds) in the same pass —
   this keeps the code-side index from drifting further, even though it
   can't fix the `RPGACE.register()` extraction gap. Doc-only sessions
   don't need this step (nothing code-side changed).
2. `/update-logging-system`'s own completeness-check procedure gains an
   OPTIONAL first-pass step: before marking a doc artifact untouched,
   a single properly-vocab-expanded `graphify query` on the change's own
   topic is a legitimate, cheap way to check for existing coverage —
   framed as a genuine time-saver, never as authoritative on its own
   (a "no results" answer is never proof something isn't covered,
   given the doc-side graph itself is only as current as its last real
   semantic rebuild).

**Explicitly NOT adopted**: plugging graphify into `Routine`/`scope`/
`Summary`/`GODMODE`/`commit-archaeologist`/`Engineer`'s own SKILL.md
files as a blanket replacement for their existing evidence-gathering.
Real reasons, per skill:
- `commit-archaeologist` — genuinely no overlap; it reads git history,
  graphify reads current-state structure, different data entirely.
- `Routine`/`scope`/`Summary`/`GODMODE` — their evidence pulls from BOTH
  live code state AND doc content AND Supabase state; graphify can only
  ever help the doc-content third, and only when its own index is
  current. Rewriting any of these to lead with graphify would overstate
  what it can actually do today and risk exactly the false-confidence
  failure mode named above.
- `Engineer` — its Truth Check step re-verifies real git/file/deployment
  state; graphify's own honesty rules ("never invent an edge... use
  AMBIGUOUS") make it a fine SECONDARY cross-reference but a bad
  PRIMARY source for a step whose entire job is catching false claims.

**Council of 5 + `/simplify` fact-check**: the adopted scope is real,
narrow, and doesn't oversell — it adds exactly 2 lines of real value to
ONE skill (`/update-logging-system`) rather than a sweeping "graphify
everywhere" rewrite across 6+ skill files, which would have repeated the
Aug 6 earlier lesson (a checklist doesn't enforce itself; a tool doesn't
either, if plugged in past what it can actually do). The `--code-only`
maintenance step is genuinely free (no LLM key, no token cost) so it's
a real efficiency gain with zero real downside. The doc-query step is
explicitly framed as optional/non-authoritative, so a stale doc-graph
can't silently produce a wrong "already covered" skip.

**Honest limitation, stated plainly**: this does NOT make graphify a
general token-reduction lever for RPGACE work as a whole, which is what
Alex's question was hoping to hear. The real, demonstrated value is
narrower: free code-index upkeep, plus an optional cheap doc-cross-
reference check inside exactly one skill. The bigger promise (cheaper
code-structure lookups across the whole project) is blocked on a real,
structural gap in graphify's own extractor recognizing
`RPGACE.register('name', {...})` as a module boundary — not something
fixable from inside RPGACE's own repo, and not something this pass
attempted to patch in graphify's own (external, bundled) skill code.
