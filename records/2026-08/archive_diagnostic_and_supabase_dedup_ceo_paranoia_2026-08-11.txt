=== STEP 1 — COMPILE: what this literally maps to ===

Re-read literally, Alex's own sentence already describes a real process
in 5 real clauses:
  (a) "old updates get stored as current capabilities" — a superseded
      update, once resolved, becomes a plain CURRENT-STATE fact, not a
      story about how it became true.
  (b) "all logs associated with change get turned to present foundation"
      — narrative/incident detail collapses into present-tense
      foundational description.
  (c) "new update showing new" — the live doc shows only the DELTA, not
      the whole history.
  (d) "archived updates get sent to an archive report" — superseded
      material physically moves to a dedicated archive, not deleted.
  (e) "keeping updates fresh decluttered and dehoarded" — the live view
      stays lean.

Real, load-bearing finding: this is not a new idea. It is CLAUDE.md's OWN
already-written doc-discipline rule, word for word in spirit:

  "when a Current state entry's underlying event is done, verified, and
  no longer being actively re-litigated, collapse it to a single
  durable-fact bullet... don't leave the full incident narrative sitting
  in CLAUDE.md indefinitely."

And it has ALREADY been executed once for real: the July 31 prune moved
every dated "Current state (July 24)" / "Prior state" section verbatim
into CLAUDE_archive.md, rewrote CLAUDE.md's own Current State section
into one-line present-tense facts, and went from ~154KB to ~92KB with
zero durable fact lost. **CLAUDE_archive.md already IS the archive
report Alex is describing.** The mechanism exists. What does NOT exist
is a STANDING, CHECKABLE version of it — the July 31 prune was one
manual pass, not a repeatable discipline, and this session's own
minotaur_map.html changelog-drift finding (same day, this session) is
live proof the underlying discipline had already lapsed again in a
DIFFERENT doc within weeks. Same root problem /update-logging-system was
built to solve for rule 6 ("a checklist doesn't enforce itself") — this
is that exact gap, in the archival direction instead of the
touch-every-doc direction.

**/restructure lens**: does fitting this INSTEAD of `/drift` +

**Council of 5 — real pros/cons, not manufactured balance:**

*For building (extend-not-invent version)*:
- Real, already-proven precedent (July 31 prune) shows the mechanism
  works when it runs.
- The style_profiles finding is real, live proof the underlying gap is
  costing something concrete right now (a wrong claim sitting in
  CLAUDE.md's own "Live numbers" section, the exact section built to
  prevent this).
- Cheap to build: this is mostly 2 new checklist items on 2 already-
  existing skill files, not new infrastructure.

*Against (honest, not padded)*:
- Rule 11 (token cost): a Supabase re-query pass on every session-start
  for every "Live numbers" claim is real, recurring cost for a class of
  drift that's usually harmless (a stale row count rarely breaks
  anything) — should be scoped to WHEN it fires, not blanket every
  session.
- Over-archiving risk: if "move to archive the moment it's superseded"
  is applied too eagerly, CLAUDE.md could lose useful nearby context a
  session actually needs mid-task — the July 31 prune worked because a
  human (Alex) was the actual judge of what was "fully resolved," not a
  mechanical rule. Any standing version of this needs to keep a real
  judgment step, not become auto-delete.
- Building a full literal Supabase dedup scanner (Fork 1 option B) with
  no current evidence of a real duplication gap would be solving an
  imagined problem, not a real one — against rule 4 (verify before
  acting) and rule 11.

**Verdict**: adopt the narrow, extend-not-invent version. Do NOT build a
new parallel "archive diagnostic system" file or Supabase dedup scanner
service. Do NOT blanket-rescan Supabase every session.
