3. ORCHESTRATOR CC'S REAL OPINION (asked for directly, given honestly)
=========================================================================

The FEEL Alex described (say a thing → get shown reasoning → say yes → it happens) is
fully buildable. The literal MECHANISM ("/CEO running inside Oracle," "/paranoia and
/interrogation" firing per-action) is not, for a concrete, evidence-based reason (1c):
Oracle cannot invoke a Claude Code skill file. Two real design choices resolve this
honestly rather than faking it:

(a) Recognize intent, don't reason it live. A small, CURATED vocabulary (a real
    lookup table, not open-ended NL parsing) maps a recognized phrase → one specific
    real action. Oracle's job is pattern-matching within a known set, exactly like
    DIRECTOR_CHOSEN/EDL_JSON already do — not open-ended agentic decision-making.

(b) Pre-written explanations, not live-reasoned ones — AND real, correction from
    Alex: stored in Supabase, never hardcoded in JS. Alex's own direct catch: "why
    pre-written, just use supabase where skills are stored, so whenever i update a
    skill it can give oracle an updated pre-written." Real, honest reconciliation:
    `.claude/skills/*.md` files themselves stay Claude-Code-only (the standing
    Total-systems constraint — Oracle's own deployed runtime has zero access to this
    repo's skill files, same as 1c already establishes) — but the REAL, correct fix
    his catch points at is that the "pre-written explanation" text should NOT be a
    hardcoded JS constant either. It belongs in a real Supabase table (new
    `oracle_actions`, same live-editable-content pattern `oracle_module_anatomy`
    already proves in production) — so a future Claude Code session (or Alex
    directly) can update an action's wording, add a new action, or retire one with a
    plain UPDATE/INSERT, and Oracle picks up the current version on its next fetch —
    zero code redeploy needed. The explanation text still gets written with real
    care once per action (matching the same rigor a /paranoia-level pass would give
    it) — it just now lives as data, not code, per this same discipline every other
    "curated but living" fact in this project already follows (rule 8: reuse the
    `oracle_module_anatomy` precedent, don't invent a second pattern for the same
    real need).

Verdict: build the CONFIRM-BEFORE-EXECUTE experience Alex described, exactly as he
described it, using a real, evidence-honest mechanism — a curated vocabulary + a real
client-side confirm popup (matching taxonomy's own `_showPlacementConfirm` pattern,
rule 8) — rather than a literal per-action live-paranoia call neither the architecture
nor the cost budget supports.

4. THE REAL PLAN — WHAT GETS BUILT, PHASE 1
=========================================================================

4a. New Oracle vocabulary table (source of truth, not yet built — this pass is
    planning only): a real Supabase table, `oracle_actions` (corrected per Alex's own
    direct ask above — a real table, never a hardcoded JS constant), one row per
    recognized command:
      { action_id, trigger_phrases: [...], target: 'module.method',
        data_touched: [...], explanation_significance, explanation_path_reasoning,
        explanation_benefit, confirm_required: true }
    Every row's `confirm_required` starts `true` — a deliberately conservative
    default (rule 4), never auto-execute-without-asking in Phase 1, matching Alex's
    own Q3 answer (a real confirm every time, not a low-stakes-auto-execute carve-out
    — that "some things auto-run" question from earlier in this same session was
    already answered differently here: EVERY action shows the confirm, then executes
    immediately on yes). Client-side, Oracle's grounding fetches the current live
    `oracle_actions` rows (same fetch-and-inject pattern `oracle_module_anatomy`
    already uses) so an edited/added/retired row reaches Oracle on its very next real
    call — no redeploy in the loop for a content-only change.

4b. Real first candidate action, matching Alex's own example: `log_beat`
      trigger_phrases: ["log the beat", "log this beat", "save this beat"]
      target: beatLog._submit (the EXISTING real function, unchanged)
      data_touched: content_productions row (insert), video_jobs row (insert)
      This is the smallest real, already-proven-safe action to start with — beatLog
      already has a real, working submit path; G41 only adds the NL-trigger +
      confirm-popup layer in front of it, zero change to the underlying write.

4c. Mechanism (extends 1a, never re-derived):
    - Oracle's prompt (scoped to a real keyword/context gate, same pattern as
      `oracleAppGrounding`'s existing gates) is built from the LIVE `oracle_actions`
      Supabase rows at grounding time (same fetch-then-inject shape
      `oracle_module_anatomy` already uses) and told: "if the user's message matches
      one of these recognized actions, end your reply with a trailer line:
      ORACLE_ACTION: <action_id>."
    - Client-side: a new hook consumer (same `'oracle:response-scanned'` hook
      DIRECTOR_CHOSEN/EDL_JSON already use) scans for `ORACLE_ACTION:`, looks up the
      matching `oracle_actions` row (already fetched, or a fresh read), and renders a
      real confirm popup with that
      entry's pre-written explanation fields filled in.
    - Alex clicks Accept/Deny (a real button — not typed "yes", matching rule 4's
      established UI pattern, e.g. `_showPlacementConfirm`).
    - On Accept: the client calls the real target function directly
      (`RPGACE.modules.beatLog._submit(...)`), using whatever real data the current
      conversation/page context already has (never fabricated).
    - On Deny: nothing happens, a toast confirms cancellation, same fail-loud
      discipline as everywhere else in this project.

4d. Explicitly NOT built in Phase 1 (real, honest scope limit, not silently dropped):
    - No auto-execute-without-confirm path at all yet, even for something Alex might
      later call "low-stakes" — starting maximally conservative, per rule 4's own
      established discipline; loosening this is a real, separate future decision, not
      assumed here.
    - No NL parsing beyond a fixed, curated phrase list — a genuinely open-ended
      "understand any instruction and improvise an action" system is a different,
      much bigger and riskier build (real agentic action-taking) that this plan does
      NOT propose.
    - Only ONE action (`log_beat`) ships in Phase 1 — proving the mechanism end-to-end
      on the single real example Alex himself gave, before expanding the vocabulary
      to more Content Pipeline stages (Visual Treatment trigger, Captions trigger,
      etc. — real, named Phase 2 candidates, not built this pass).
