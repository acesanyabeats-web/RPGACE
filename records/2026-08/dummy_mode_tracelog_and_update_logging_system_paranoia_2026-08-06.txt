IDEA A — DUMMY MODE TRACE LOG (planned, NOT built this pass)
======================================================================

REAL COMPLAINT: mockOracle's Dummy mode currently returns a labeled fake
reply, and the real button/DOM/hook/Supabase-write path downstream
genuinely runs on top of it (per the module's own design) — but nothing
SHOWS Alex which of those real things actually fired. He gets a fake
chat bubble and has to trust it worked, which defeats a chunk of the
mode's own stated purpose ("exercises real app wiring end-to-end").

GODMODE evidence (real code read):
- `RPGACE.hooks.fire(name, payload)` (rpgace_core.js) is the one real
  shared event bus — every cross-module signal in the project already
  goes through it (CLAUDE.md's own "Intercommunication convention" rule,
  optimization backlog item 6). A trace hook could listen here for free,
  with zero new firing sites needed anywhere else.
- `RPGACE.sb.insert/update/del/secureWrite` are the shared write paths
  (rule 8 — every real write in the app already funnels through one of
  these four functions). Wrapping just these four, once, would surface
  every attempted write during a dummy run without touching a single
  call site.
- `_fakeReply`'s own trailer-detection (director_chosen/edl_json scan)
  already proves the pattern of "inspect the outbound prompt, report
  what it implies" — a trace log is the same idea applied to the
  DOWNSTREAM side (what actually happened) instead of the upstream side
  (what was asked for).

DEBATE:
FOR — this is real, cheap, and reuses existing choke points (hooks.fire,
the 4 sb write functions) rather than needing new instrumentation at
every call site. It turns Dummy mode from "trust me, it did something"
into genuine evidence, matching the `/dummy` skill's own stated goal
("this exercises real app wiring end-to-end, not fake output quality")
— today it only half-delivers on that promise.
AGAINST — real scope risk: DOM mutations (which is often what Alex most
wants to see — "did the right element actually update") are NOT covered
by hooks.fire or the sb write functions; a MutationObserver would be the
only way to catch those and that's a genuinely heavier, noisier
mechanism (would fire on every unrelated DOM change too, needing a real
filter). Scoping the first version to hooks+writes only (leaving DOM
coverage as a stated future extension, not silently claimed) is the
honest move, not overpromising a "captures everything" trace.

INTERROGATION (real open forks — genuinely need Alex's input when this
gets picked up, not guessed defaults now):
1. Format: he said "error codes that summarise what's injected" — does
   he want short fixed codes (e.g. `HOOK:oracle:response-scanned`,
   `WRITE:encyclopedia:update`) or human-readable one-liners? Fixed
   codes are cheaper/more scannable; readable lines carry more context
   per entry. Recommend fixed codes with a short human clause appended,
   but this is his call.
2. Where does the log live/display? Options: (a) a new popup mirroring
   the "📥 Scouted" list pattern (`dashDeck._popup()`, consistent UX),
   (b) inline under the fake chat reply itself (immediate, but clutters
   the chat), (c) both. Recommend (a) for consistency with the just-shipped
   Scouted list, but confirm with him.
3. Persistence: per-session only (resets on reload, cheap, matches
   ENC_BULLET_CACHE's OLD mistake being fresh in mind — should NOT repeat
   that mistake if Alex wants to review a trace after closing the tab) or
   written somewhere durable? Recommend a lightweight Supabase table
   (`mock_trace_log` or similar) ONLY if he actually wants cross-session
   review — otherwise an in-memory array is enough and avoids a new table
   for a debugging-only feature. Needs his real answer, not a default.

COUNCIL OF 5 FACT-CHECK: real evidence-backed (hooks.fire and the 4 sb
functions are confirmed real, existing choke points, not invented);
scope is honestly bounded (DOM coverage explicitly named as NOT included
in v1, not silently dropped); real open forks are named as real forks,
not resolved by guessing.

VERDICT: Adopt — real, buildable, cheap relative to value. NOT built this
pass per Alex's own explicit instruction ("plan it and log as future
update to get back to"). Logged here as the durable spec; pick up with
`/interrogation` on the 3 open forks above before building.

guarantee it gets checked, unless it's actually WIRED into where

commit-archaeologist. Building this as a NEW ceremony that itself never

promise stacked on the first one.

RESOLUTION (this is where the AGAINST case wins scope, not the FOR case
losing): don't build a fourth ritual Alex has to remember to invoke.
Build the dependency map as ONE shared reference skill, then WIRE it
into the one real point where doc-writing already happens as a matter

duplication named above as a side effect), and by strengthening rule 6

commit-archaeologist/GODMODE don't need their own copy — they feed
evidence INTO decisions; Bedtime (or any direct mid-session "update
oversight" moment) is the actual write-out point, and that's the one
place this needs to be enforced.
