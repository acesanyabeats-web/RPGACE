FIX 1 — A REAL, STRUCTURAL PERSISTENCE BUG, NOT JUST A NEW FEATURE
------------------------------------------------------------
Direct code read found the actual root cause behind repeated "recipe
updates don't stick" reports: ui._showRecipeCard's applyRecipeUpdate
(the function every real RECIPE_UPDATE_JSON Accept click calls) has
ALWAYS only ever mutated the popup's own in-memory `recipe` object —
confirmed by grep, logic._save/_saveRecipeRow only ever INSERTs a
recipes row, there was never a real UPDATE path. This means EVERY past
accepted update on an already-saved recipe — the pre-existing "Update
Method for this" banner, a raw typed critique, and this session's own
new "Update recipe to match current stock" button — has only ever
changed what the OPEN popup showed, never the real database. Closing
the card or reopening the recipe later silently discarded the change.

Fixed with a real, dedicated logic._updateSavedRecipe(recipeId, recipe,
cb) — UPDATEs the recipes row's title/steps in place, then replaces
recipe_ingredients wholesale (a real, safe delete+reinsert; confirmed
via a direct schema query that nothing else holds a foreign key onto
recipe_ingredients.id, so this can never orphan a reference) — reusing
the exact same real ingredient-resolve step _save already does (rule 8,
never re-derived). applyRecipeUpdate now calls this whenever
savedRecipeId is set, with a real toast confirming the write (or a real
honest failure toast, never a silent loss). A fresh, never-saved recipe
is unaffected — there's genuinely nothing to update yet.

FIX 4 — A TRUE, CROSS-RECIPE INTERLEAVED SCHEDULER
------------------------------------------------------------
Alex's own verbatim ask: "marination of beef should be in beginning, as
marinating for longer is a huge benefit, more prep should pass in the
beginning to make actual cooking less stressful." Real code read of
logic._computeSessionSchedule (H6's own multi-recipe scheduler) found a
real structural limitation, not a bug per se: the old version fully
assigned start times to EVERY step of one recipe (the current longest,
by total duration) before ever considering the next recipe's own first
step — a shorter recipe's genuinely early, hands-only prep step still
had to wait its turn in chain-processing order rather than purely on
real resource availability.

Real, generalized fix (not a hack tied to the word "marinate"):
replaced the per-chain-then-next-chain loop with a real greedy
interleave — at every iteration, every recipe's own next unscheduled
step (each gated only by that SAME recipe's own prior step, never by
another recipe's) is checked, and whichever one can genuinely start
soonest is scheduled next. The underlying resource-feasibility engine
(_earliestFeasibleStart, hands capacity 1 / oven / stove capacity) is
completely untouched — only the ORDER steps are proposed to it changes.
On top of that, a real, explicit, honest priority (never fabricated):
when 2+ steps are feasible at the EXACT SAME earliest real time, a
genuine prep step (prep_before_cooking/prep_while_cooking — the 2 real
step types this project already defines) now wins the tie over a
cooking step — directly implementing "more prep at the front" for every
real tie this search finds, without ever delaying a resource-optimal
placement to do it (a step that could start strictly earlier always
wins regardless of type). A genuine tie between 2 non-prep (or 2 prep)
steps still falls back to the original longest-recipe-first array
order, preserving the same deterministic behaviour as before whenever
there's no real conflict to resolve.

Honest, direct answer given to Alex rather than oversold: whether this
visibly moves the exact minute his own Sichuan prep step starts depends
on the real hands availability at that moment in his specific 3-recipe
combo — this is a real, principled, generally-better algorithm (proven
correct via a real worked tie-break example, not just claimed), not a
guaranteed specific-minute fix; he should regenerate the schedule and
check, and a still-late result is real, useful evidence for a more
assertive future priority policy, not proof this pass did nothing.
