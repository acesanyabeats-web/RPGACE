3. REAL, HONEST TECHNICAL WRINKLE - FLAGGED, NOT GUESSED
================================================================================

USDA FoodData Central's nutrition figures are per 100g of a food. RPGACE's
own `recipe_ingredients.amount`/`unit` are whatever unit Oracle generated
the recipe with (could be "2 tbsp", "1 clove", "200g" - not guaranteed to
already be grams). Converting an arbitrary recipe unit into a gram figure
that can be multiplied against a per-100g USDA number is a real, separate
problem from just "look up the ingredient."

Two honest options, put to Alex directly rather than picked for him:
(a) When Oracle generates a recipe (the existing RECIPE_JSON call, zero
    extra API cost), also ask it to estimate a real gram-equivalent for
    each ingredient line alongside its existing amount/unit - reuses the
    exact mechanism already generating the recipe, no new call.
(b) Do the USDA lookup and math on a best-effort basis using only common
    unit-to-gram approximations (tbsp/tsp/cup/clove tables) with no
    per-recipe estimate - cheaper, but real inaccuracy on anything not in
    a standard conversion table (e.g. "1 chicken thigh").

Also needs a real answer: get a free USDA FoodData Central API key now
(instant, free sign-up at https://fdc.nal.usda.gov/api-key-signup, added
as a Vercel env var - unlike Fish Audio, there is no paid tier or ongoing
cost to weigh here), or hold the calorie half as a dormant scaffold like
the Fish Audio pattern until Alex says go.

4. REAL PROPOSED SCOPE (Loop 1 draft, nothing built yet)
================================================================================

New Supabase tables (all additive, anon_read_only/authenticated_all from
the start, matching every other HABITS table's posture):

- `pantry_stock` (ingredient_id FK, quantity, unit, updated_at) - one row
  per ingredient currently in stock. Decremented when a recipe is marked
  cooked (consumes its recipe_ingredients amounts), topped up when a
  purchase is logged.
- `shopping_lists` (id, planned_cook_id FK -> planned_cooks, created_at,
  status) - reuses H6's real planned_cooks session directly (rule 8,
  never a second parallel "recipe set" concept) - a single-recipe shop is
  just a session of one.
- `shopping_list_items` (list_id FK, ingredient_id FK, needed_amount,
  needed_unit, have_amount, to_buy_amount, bought boolean,
  ingredient_price_id FK nullable -> the real purchase row once logged).
- `ingredient_prices` gains one additive column: `brand text`.
- `ingredients` gains real nutrition columns: `kcal_per_100g`,
  `protein_g_per_100g`, `carbs_g_per_100g`, `fat_g_per_100g`,
  `nutrition_source` ('usda'|'manual'), `nutrition_cached_at` - direct
  columns on the existing 1:1 ingredient row, not a new join table
  (`ingredient_prices` is 1:many per ingredient by design - price varies
  by store/time; nutrition per ingredient does not, so it belongs on the
  ingredient itself).

New/extended UI in `cookingOracle` (ui/logic split, matching the existing
G53 convention):
- "🛒 Generate shopping list" on a planned_cooks session - aggregates
  every recipe's own recipe_ingredients, checks pantry_stock for
  have/not-have, computes to_buy_amount, writes shopping_lists +
  shopping_list_items.
- The shopping list view itself - have/not-have split, tick to mark
  bought -> the combined price-entry popup (brand/store/weight/price +
  Redo button per Q2) -> writes ingredient_prices + tops up pantry_stock.
- Recipe card gains a real Nutrition section (kcal/protein/carbs/fat,
  total + per serving), computed from recipe_ingredients x ingredients'
  cached nutrition columns.
- A new server-side USDA lookup (folds into an existing api/*.js action
  branch, per the standing Vercel-12-function-cap landmine - never a new
  physical file) - resolves an ingredient name to USDA nutrition data,
  caches it onto the ingredients row, never re-queried once cached.
