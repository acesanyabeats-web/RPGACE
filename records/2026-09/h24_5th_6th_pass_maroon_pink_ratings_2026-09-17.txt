MAROON — real build
------------------------------------------------------------
New real, curated `logic._DERIVATION_GROUPS` (same restrained, evidence-
seeded discipline as `_SUBSTITUTION_GROUPS`) — 2 real entries, both his
own verbatim examples, both genuine 1:1 real culinary facts (rule 7 —
never invented): egg -> egg white / egg yolk; desiccated coconut ->
toasted desiccated coconut (toasting doesn't meaningfully change real
countable quantity). `logic._findDerivation(name)` resolves a real
derived-ingredient name to its source. A real maroon status (⚗️, no
standard maroon-square emoji exists in Unicode) takes PRIORITY over
orange in `logic._classifyIngredientStatus` — deriving the actual real
ingredient is more accurate than substituting a different one, and only
fires when the real source genuinely has positive stock (never assumed).
`logic._deriveIngredient(sourceName, derivedAmount, yieldRatio, cb)` is
the real, committed write — deducts across whatever real pantry_stock
row(s) actually exist for the source, never letting a row go negative,
honestly reporting a real shortfall if stock is genuinely insufficient
rather than inventing extra stock to make the math come out even. Real
UI on `ui._renderSubstitutableStatusRow`'s new maroon branch: shows the
real source stock count + the real curated instructions + a "⚗️ Derive &
use N {source}" button computing the correct real source amount
(derivedAmount / yieldRatio). A successful derive does NOT change the
row's color (same "tick, not green" discipline as orange's confirm flow)
— shows a real "✓ Derived — used N" note instead.

PINK — real build
------------------------------------------------------------
`logic._computeIngredientUsage`'s group-building now tracks real
`perRecipe: [{recipeId, amount}]` per (ingredient_id, unit) group,
alongside the existing merged `amount` total (never replacing it — every
existing consumer unaffected). Real pink eligibility: 2+ DISTINCT real
recipes genuinely share the ingredient, real stock covers at least the
smallest single recipe's own need (otherwise it's an ordinary shortfall,
the existing ladder already handles it honestly) but not the combined
total. New `planned_cooks.pink_allocations` (additive jsonb column,
DEFAULT '{}') persists Alex's real per-session choice, keyed by
`ingredient_id|unit`. Deliberately NOT threaded through the broader
`_persistSessionDraft`/`_loadDraftSession`/`_acceptSchedule` machinery
(rule 4 — don't touch a working call site's contract more than needed);
`logic._loadPinkAllocations`/`logic._setPinkAllocation` are narrow,
dedicated read/write functions scoped to the one real consumer
(`ui._showSchedulePreview`). Real, dedicated UI, `ui._renderPinkRow` —
shows the real per-recipe breakdown (real recipe titles from
`sess.recipes`, real needed amounts) with a real button per contributing
recipe, "Give real stock to '{title}' (needs N {unit})" — Alex's own
explicit choice, never auto-picked. Once resolved: the group's own
status/toBuy is recomputed against ONLY the chosen recipe's real amount
(falls through to the normal 5-color ladder from there, e.g. a real
exact-match can correctly land on purple if the margin is thin — not
forced to green), and `pinkInfo.others` carries each OTHER real
recipe's own independently-computed fallback (its own real substitute or
derivation, `have:0` for its own share since the real stock went to the
chosen recipe) — reuses the exact same classify/substitute/derivation
machinery every other row already uses (rule 8), never a parallel 2nd
system. This is the real, concrete answer to "identify which
subsitution is least impactful" — the OTHER recipe's own real fallback
is shown right there, in context, once a real choice is made.

RATINGS — real build
------------------------------------------------------------
New, real, append-only `substitution_ratings` table (ingredient_id,
substitute_name, rating CHECK(rating in (-1,1)), created_at) — never
overwritten, same discipline as `ingredient_prices` (a changed mind
later adds a new real data point, never erases the old one).
`logic._rateSubstitution`/`logic._loadSubstitutionRatings` (client-side
net-score aggregation, same established precedent as
`_loadPantrySummed`'s own aggregation). `logic._findSubstitute` gained 2
real, optional trailing params (`ingredientId`, `ratings`) — every
existing caller that omits them is byte-identical to before (with no
ratings loaded, every candidate scores 0, original array order wins,
same as the old first-match-wins logic). When 2+ real candidates are
simultaneously available (a genuine case — e.g. both "dark soy sauce"
and "light soy sauce" in stock at once), the function now collects ALL
real matches (curated group AND heuristic, both previously
first-match-wins) and picks the highest real net-rated one via the new
`logic._pickBestRated`. Wired into the 3 real "surface a specific
substitute name" sites — `_computeIngredientUsage`'s own subName
resolution, its pink-others fallback resolution, and the Shopping
List's inline resolution — plus the recipe card's own ingredient
preview. `logic._loadSavedRecipe` gained a real `ingredient_id` field on
each returned ingredient (previously entirely absent) — the one real
thing needed to rate a substitution "from the recipe card," Alex's own
literal ask; a freshly-generated, not-yet-saved recipe still has none
(an honest, unavoidable gap, not fixed blind — nothing to rate against
until a real `recipe_ingredients` row exists). Real 👍/👎 rating buttons
now appear on an orange row in a REOPENED SAVED recipe's own ingredient
list, writing immediately, no forced prompt (his own explicit choice).
