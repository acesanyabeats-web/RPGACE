- `BTN_VARIANTS` — 13 real named variants, each derived directly from

  preserves each site's own distinct delete operation and success
  side-effect (toast+session-close-check vs. plain row.remove) while
  eliminating the real duplicated interaction-state-machine code.

REAL BUGS FOUND AND FIXED (found via this pass's own systematic sweep,
not from a user report)
------------------------------------------------------------
1. Two of the three original hand-rolled delete buttons (pantry-stock,
   equipment) never set `font-family:Rajdhani,sans-serif` at all —
   silently fell back to the browser default sans-serif, a visibly
   different typeface than every other button in the app. Now
   structurally impossible to reintroduce: `_mkDeleteArmBtn`'s one
   shared implementation always includes it via the `deleteArm` variant.
2. This SAME session's own H22 "Add to basket" button used a bare `'…'`
   loading-state text, inconsistent with the module's established
   `'⏳ <verb>...'` convention every other async button follows. Fixed
   to `'⏳ Adding...'` — a real self-caught bug from this session's own
   GODMODE pass, not a pre-existing one.
3. A real bug introduced DURING this pass's own build, caught only by
   re-running the pre-existing H18-H22 regression suites (not by
   `node --check`, which only validates syntax): `_mkBtn`'s internal
   variant lookup initially read `self.BTN_VARIANTS[variant]` instead
   of `self.ui.BTN_VARIANTS[variant]` — `BTN_VARIANTS` lives nested
   under `ui`, not on the module's top level. This would have broken
   effectively every popup in the Cooking module in production
   (`TypeError: Cannot read properties of undefined`) on the very first
   button render. Fixed before shipping; re-verified clean afterward.
