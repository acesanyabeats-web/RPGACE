REAL BUG FOUND FIRST, BEFORE BUILDING ANYTHING (rule 4)
------------------------------------------------------------
"lime" was STILL showing orange with "have a substitute in stock: lime
leaves" even though the earlier same-session pass had already merged the
real "lime"/"limes" duplicate ingredient row and verified real fridge
stock landed on the correct id. Traced by hand, not guessed: the recipe's
own ingredient wants unit "whole" (2 whole lime); the real Current Stock
row is logged in unit "Count" (his own dropdown selection when adding
stock). `logic._normalizeUnit`'s synonym table had no entry mapping
either of these — "whole" and "count" both normalized to themselves,
never to a shared bucket, so the exact-unit-match in
`logic._resolveHaveAmount` failed for the SAME real ingredient, `have`
came back 0, and the row fell through to the substitute-finder path
exactly as if no stock existed at all. Same real bug CLASS as H18's
"gram"/"g" fix — a genuine unit-string mismatch between what a recipe
asks for and what Alex's own stock entry used, never a data problem.

REAL FIX 1 — unit normalization
------------------------------------------------------------
Added `whole`/`wholes`/`count`/`counts` to `logic._normalizeUnit`'s
SYNONYMS table, all mapping to the same canonical bucket the existing
`unit`/`units` entries already use. This is the real, direct fix for
lime (and any other whole-item recipe ingredient matched against a
Current-Stock row logged as "Count") — verified via
`_resolveHaveAmount` directly: a real "2 Count" stock bucket now
correctly answers "2" for a recipe needing "whole".

REAL BUILD 2 — the confirm-to-green flow (his new, explicit ask)
------------------------------------------------------------
New real Supabase table, `ingredient_substitution_confirmations`
(ingredient_id, substitute_name, confirmed_at; UNIQUE on the pair),
`anon_read_only`/`authenticated_all` RLS from creation, added to
`api/data-write.js`'s ALLOWED_TABLES (satisfies "flip RLS first, then
allowlist" by construction, same precedent as every HABITS table this
project has shipped). Real write path, `logic._confirmSubstitution`
(rule 8 — one shared function, every real UI site below calls this
same one) — keyed on the (ingredient_id, substitute_name) PAIR, not a
global flag, so confirming "beef cuts with bone for beef shin" never
silently also confirms an unrelated pairing that happens to share the
same generic orange status. `logic._loadConfirmedSubs` is the matching
shared reader.

`logic._classifyIngredientStatus` gained 2 real, optional params
(`ingredientId`, `confirmedSubs`) — when a real substitute is found AND
that exact (ingredientId, substituteName) pair has already been
confirmed, it now returns green instead of orange. Every existing
caller that omits the new params is completely unaffected (verified:
orange still classifies exactly as before when they're not passed) —
same backward-compatible discipline every H18-H23 classifier extension
already used.
