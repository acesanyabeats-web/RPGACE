A real bug found and fixed before continuing, not shipped blind
===========================================================================
While anchoring a specific Oracle-domain bullet's matching card ("Full
oracle_dev_suggestions review... Full record: <code>...</code>"), the
card was found to have NO id attribute despite being a real Aug 6 card
inside the already-anchored Aug batch.

Root cause: scripts/patch_notes_add_anchors.py's CARD_RE used [^<]* to
capture a card's title text -- this silently fails/skips the ENTIRE card
whenever the title itself contains inline HTML markup (a nested <code>
or <b> tag), since the regex's title group stops at the first < it
meets, then expects an immediate </div> that never arrives.

Direct measurement: 69 of 424 real card-title divs contain nested markup
(mostly <code>...</code> around a filename or identifier). This means
ALL THREE prior anchor batches (Sep 79, Aug 173, Jul 93) had silently
undercounted -- real cards were skipped with no error, no warning.

Fixed: CARD_RE's title group changed to a DOTALL, non-greedy match up to
the FIRST </div> (safe, since a card-title never nests a real <div>,
only inline tags) -- (.*?)</div> with re.DOTALL. slugify() now strips any
inline tags via re.sub(r'<[^>]+>', ' ', title) before generating a slug,
so a stray word like "code" doesn't leak in from a stripped tag name.

Re-ran all 3 month batches -- idempotent by design, so this only filled
in the previously-missed cards, never touched an already-anchored one:
Sep +1 (the DD-1 batch-1 card itself, added after the original Sep run),
Aug +23, Jul +7. Verified via direct scan: 0 duplicate ids, div-balance
unchanged. 376 of 424 real cards now anchored (the remaining 48 are
undated roadmap/still-open items -- F-series steps, 6a-6f future ideas,
BUG items -- never in scope for this retrofit).

===========================================================================
A second, separate real bug found the same way -- the Jul batch itself
===========================================================================
The original Jul batch run (last turn) found 0 cards, which was wrongly
read at the time as "nothing to anchor yet" rather than investigated.
This turn, direct grep confirmed 100 real July-dated cards DO exist --
the actual cause: this project's own patch_notes.html writes "July 31"
in FULL for every July card, while every other month (Aug/Sep/etc.) uses
a 3-letter abbreviation ("Aug 6", "Sep 23"). The original MONTH_RE only
matched 3-letter forms, so "July" (4+ letters) never matched.

Fixed: MONTH_RE extended to accept an optional full-name suffix for every
month (Jan(?:uary)?, Jul(?:y)?, etc. -- future-proofed against any other
month someone might one day write in full, not just a Jul-specific
patch), plus a new norm_month() helper normalizing any captured month
text down to its 3-letter code before comparing against a --month filter
argument or building an id. Re-running Jul with the fix recovered 93
real cards this session (this turn's re-run on top of that recovered 7
more that had ALSO been missed by the inline-HTML bug above -- both bugs
were real and independent, confirmed by testing each fix in isolation).
