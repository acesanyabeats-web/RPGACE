Two real, separate asks folded into one build: (1) a generation-prompt
change — Oracle should lean on cups for liquids/spices and weight
(grams) for other ingredients, whichever a real recipe would actually
use; (2) a real engineering consequence I identified myself before
building anything (rule 1) — H18's whole 5-color system exact-matched
ingredient_id+unit, so the moment recipes start using cups while stock
stays in g/ml/count, EVERY liquid/spice ingredient would start reading as
"not in stock" (red) even when genuinely well-stocked — a real
regression to H18 the moment Alex's stated future stock-logging habit
actually shows up, not a hypothetical.

REAL DESIGN CONSTRAINT HONORED THROUGHOUT: NO INVENTED CONVERSIONS
------------------------------------------------------------
CLAUDE.md's own standing landmine ("never force-summed across mismatched
UNITS... no invented conversion") stays true here. Only 2 real,
NEVER-GUESSED bridges were added:

1. VOLUME_TO_ML — cup=240ml, tbsp=15ml, tsp=5ml, l=1000ml, ml=1. Real,
   exact, ingredient-INDEPENDENT physics: a cup is always the same real
   volume regardless of what's in it. No density guess anywhere in this
   path.
2. A weight bridge using the RECIPE'S OWN already-existing
   grams_estimate (built for nutrition, H2 — reused here, rule 8, never a
   new invented per-ingredient density table). When a recipe's unit
   isn't weight (e.g. "1 cup" flour) but a real stock bucket for that
   same ingredient_id IS weight (g/kg), the bridge derives a real
   grams-per-recipe-unit ratio from that SPECIFIC recipe's own estimate
   (gramsEstimate/neededAmount) and converts the real stock grams back
   into the recipe's own unit.

Genuinely NOT bridged, on purpose (rule 7 — honest gap, not guessed):
"count" against weight/volume (a real onion's weight varies — no honest
conversion exists without inventing one).

REAL SHARED BUILD (rule 8 — one implementation, every consumer reuses it)
------------------------------------------------------------
logic.VOLUME_TO_ML / logic.WEIGHT_TO_G — the 2 real, fixed unit tables.
logic._convertVolumeUnits(amount, fromUnit, toUnit) — pure, real
volume<->volume math, returns null if either side isn't a volume unit.
logic._resolveHaveAmount({neededUnit, neededAmount, gramsEstimate,
buckets}) — the ONE real "how much do I actually have of this, in the
recipe's own unit" resolver. Precedence, safest first: (1) an exact
normalized-unit match (unchanged H18 behavior); (2) the real volume
bridge; (3) the real grams_estimate weight bridge. Returns 0, honestly,
when none apply.

logic._loadPantrySummed — real, superseding shape change: `byKey` (a flat
ingredient_id|unit -> one bucket) replaced with `byIngredient`
(ingredient_id -> ARRAY of every real unit-bucket that ingredient has,
normalized-unit keyed). A flat exact-key map can only ever answer "do I
have EXACTLY this unit" — the bridge needs to see every real unit an
ingredient is actually stocked in.

3 real callers updated to match (confirmed via grep — no other real
caller existed):
- logic._computeIngredientUsage (schedule preview + shopping-list
  generation) — recipe_ingredients select gained grams_estimate,
  accumulated alongside amount per group (so 2+ rows in the same real
  normalized-unit group keep a valid grams-per-unit ratio); have is now
  resolved via _resolveHaveAmount against pantry.byIngredient.
- logic._findMakeableRecipes (the stock-match finder) — same real
  select+resolve change.
- ui._showRecipeCard's renderIngredients (the not-yet-saved-recipe,
  name-keyed path) — same real resolve, but the grams-per-unit ratio is
  deliberately computed from the ingredient's BASE (unscaled)
  amount/grams_estimate, never the currently-displayed SCALED amount —
  "have" doesn't change just because Alex asked for more servings.
