REAL MID-BUILD CORRECTIONS FROM ALEX (both addressed same pass, not
deferred)
------------------------------------------------------------
(1) "not pantry only, stock only, pantry is part of stock, like fridge
and freezer" — caught while the checkbox/prompt-constraint feature was
still being named "pantryOnly." Renamed throughout (stockOnly,
_generateWithStockConstraint, the checkbox/finder copy) — the underlying
DATA was always correct (pantry_stock's own `location` column already
covers pantry/fridge/freezer, H11), only the naming needed fixing to
match Alex's stated mental model.

(2) "in schedule cook - ingredients that are not equal to measurements in
recipes show as not in stock - i need this to be sensitive to colour to
make it make sense" — a real, separate bug found live: every have-vs-
needed match keyed strictly on (ingredient_id, exact unit STRING), so a
recipe asking for "gram" against pantry stock logged as "g" (or "clove"
vs "cloves", "tbsp" vs "tablespoon") silently failed to match, showing red
("don't have") for something genuinely in stock. Fixed with one shared
logic._normalizeUnit(u) — a curated synonym table (g/gram/grams/gramme,
kg, ml, l, tbsp, tsp, clove, piece, can/tin, cup, pinch, slice, unit) plus
a generic trailing-"s" plural strip (skipped for anything <=3 chars, so
"oz" never becomes "o") — NEVER a cross-system numeric conversion (g does
not become oz, no invented density/volume math). Applied everywhere a
(ingredient_id, unit) match happens: logic._loadPantrySummed's byKey/
byName, logic._computeIngredientUsage's groups key, logic.
_findMakeableRecipes's key, and ui._showRecipeCard's inline byName match.

REAL BUILD, PER RULE 8 (ONE SHARED IMPLEMENTATION EVERYWHERE)
------------------------------------------------------------
logic._classifyIngredientStatus({name, needed, have, aisleIndex}) — the
ONE real classifier:
  - have <= 0, same-aisle alternative present in pantry -> blue
  - have <= 0, no alternative -> red
  - 0 < have < needed -> yellow
  - have >= needed, margin (have-needed) < 20% of needed -> purple
  - have >= needed, margin >= 20% of needed -> green

logic._loadPantrySummed(cb) — real, superseding extension (not a second
loader): now returns a full snapshot {byKey, byName, aisleIndex} instead
of a bare byKey map, joining ingredients(name) in the one real query.
aisleIndex only ever includes an ingredient actually in stock (quantity >
0) — a zero-stock row must never count as a real "blue alternative."

logic._computeIngredientUsage — unchanged shape, now also returns a real
`status` per ingredient (computed once, shared by every caller).

INGREDIENT_STATUS_META (module top-level) + ui._renderIngredientStatusRow
— the one shared color/icon/label/render treatment, reused by the recipe
card, the schedule preview, and the shopping list.

REAL NEW FEATURE — "🥫 What Can I Cook Right Now?" (Q4's answer, built
in full)
------------------------------------------------------------
logic._findMakeableRecipes(cb) — real, evidence-checked classification of
every saved recipe against current stock. A recipe is "makeable" only
when EVERY real ingredient classifies green or purple (Alex's own stated
rule: those two are not needed before a shop; red/yellow/blue all are).
Reuses the exact same classifier + pantry snapshot as everywhere else —
never a second have/need computation.

ui._showStockMatchFinder — new hub button + popup. Makeable recipes sort
first; everything else stays visible underneath with an honest per-recipe
colour-count summary (never hidden, just correctly ranked lower). Clicking
a row reopens the real saved recipe via the new logic._loadSavedRecipe
(reconstructs the {title, servings_base, ingredients, steps} shape
ui._showRecipeCard already expects from recipes+recipe_ingredients) and
opens it through ui._showRecipeCard(recipe, null, recipeId) — the new,
OPTIONAL 3rd param `existingRecipeId` prevents a real duplicate-save bug
(without it, savedRecipeId would start null on a REOPENED recipe and a
later Save click would insert a genuine 2nd recipes row).

"✨ Or generate a new one using only what I have" — opens the SAME real
Generate form (ui._showGenerateForm) with its stock-only checkbox already
ticked (new 3rd param `forceStockOnly`), rather than a second, parallel
generate form.

GENERATION-TIME CONSTRAINT (the other half of Q4's combined answer)
------------------------------------------------------------
logic._generate gained a real, OPTIONAL 4th param, `stockOnly`. When true,
loads the real current stock (logic._loadPantryNamed, all 3 locations)
and extends the outbound Oracle prompt with a genuine CHOICE constraint —
"build this recipe using ONLY ingredients from this real current stock
list (pantry, fridge, and freezer combined)... do not introduce any
ingredient not on this list." Deliberately a CHOICE constraint, never a
fabricated QUANTITY guarantee — there is no "needed" amount to compare
against before a recipe exists, so the resulting recipe still gets
classified by the same real 5-color system once shown; if Oracle ends up
calling for more of something than is actually in stock, that shows up
honestly as yellow/red on the card rather than being hidden or silently
guaranteed away (rule 7). A real, empty stock array fails loud with an
honest error instead of silently sending the unconstrained prompt as if
the constraint had been honored. A checkbox on the Generate form ("📦 Use
only what I already have — no shopping trip needed") threads stockOnly
through both the direct-generate path and the narrow-down path (a short
description still routes through narrow-down first, per H9's existing
design; stockOnly now survives that hop too).
