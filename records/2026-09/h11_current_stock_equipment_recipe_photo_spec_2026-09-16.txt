  text-extraction only).

REAL /INTERROGATION (2 questions, both via AskUserQuestion, both answered

------------------------------------------------------------
Q1: What should "Equipment" actually track, given the real overlap risk
    with shoppingWishlist and habits_config's oven/stovetop numbers?
    Answer: **A real owned-equipment inventory** (containers, trays, wok,
    scales, etc., with counts) — genuinely useful for "do I have enough
    containers/trays to batch-store this" before committing to a cook.

Q2: For recipe photos "from the internet" — no image-search API exists
    today; real options were a free/keyless Wikipedia lookup (limited
    coverage) vs. a real keyed image-search API (needs Alex's own setup)
    vs. both.
    Answer: **Both — keyed API first, Wikipedia fallback.**

WHAT WAS BUILT
------------------------------------------------------------
Schema (Supabase, migration `cooking_current_stock_location_and_equipment`):
- `pantry_stock` gained a real `location` column (CHECK'd to
  pantry/fridge/freezer, default 'pantry'), and its PK changed from
  `(ingredient_id)` to `(ingredient_id, location)` so the same ingredient
  can be tracked separately per storage location. All 17 pre-existing
  rows correctly backfilled to `location='pantry'` (verified by direct
  query post-migration) — matches their real prior meaning exactly, no
  data lost or reinterpreted.
- New `kitchen_equipment` table (id/name/quantity/notes/created_at/
  updated_at), `anon_read_only`/`authenticated_all` RLS from creation
  (same "flip RLS first, then allowlist by construction" precedent as
  every other HABITS table), added to `api/data-write.js`'s
  `ALLOWED_TABLES`.

UI (rpgace_core.js, cookingOracle module):
- 4th hub button, "📦 Current Stock", opens `ui._showCurrentStock()` — a
  real 4-tab popup (Pantry/Fridge/Freezer/Equipment).
- The 3 food-storage tabs share ONE renderer, `ui._renderStockLocationTab
  (container, location)` (rule 8) — add/adjust-stock form + a live list,
  each row showing a real staleness badge (days since `updated_at`,
  flagged amber past 14 days) — the concrete "make batch cooking less
  wasteful" mechanism, built from a column that already existed, no new
  detector. Each row gets a real 2-click arm/confirm delete (same
  pattern already proven elsewhere in this project — Bookworm/Intel
  Delete's own dismiss buttons).
- `ui._renderEquipmentTab(container)` — a separate real add/list UI over
  `kitchen_equipment`, same 2-click delete convention.
- The old standalone `_showPantry` popup is retired — the pre-existing
  "📦 Pantry" button (inside the Generate form) now opens
  `_showCurrentStock('pantry')` instead, so there is one real stock UI,
  not two (rule 8).
- `logic._loadPantryNamed` (used by the existing Oracle ingredient-
  suggestion feature, H10) now sums quantity across all 3 locations per
  ingredient — its own return shape and its one real caller are
  unchanged; it genuinely doesn't matter to that feature WHERE stock
  physically sits.
- New `logic._loadStockByLocation`/`_deleteStockItem`/`_loadEquipment`/
  `_saveEquipment`/`_deleteEquipment`.

Recipe photo (`ui._showRecipeCard`, `api/search.js`):
- A real photo box renders at the top of the recipe card, populated via
  a new `logic._fetchRecipePhoto(title, cb)` call to `/api/search` with
  a new `type:'recipe-image'` field (every existing YouTube-search caller
  omits `type`, so the original behavior is byte-for-byte unchanged for
  them — confirmed by direct grep, exactly one existing caller).
- `api/search.js` gained a `handleRecipeImage()` branch: tries Unsplash
  first (`process.env.UNSPLASH_ACCESS_KEY`, server-side only, never
  shipped to the client — same secret discipline as
  `LASTFM_API_KEY`/`RPGACE_API_SECRET`), falls back to Wikipedia's free,
  keyless REST summary API when the key is unset or Unsplash finds
  nothing. Returns `{image:null}` — never a thrown error or a fake
  placeholder — when neither source finds a real match (rule 7). No 13th
  `api/*.js` file added (would have hit the 12-Serverless-Function Vercel
  Hobby cap, currently 11 of 12) — folded into the existing `search.js`
  endpoint instead, per the standing landmine's own instruction.
