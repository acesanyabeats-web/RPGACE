3. PARANOIA PASS (Aintergration + restructure, scoped to one design)
--------------------------------------------------------------------
Reference model (Aintergration, "Reference only — borrow the principle"):
Dota 2 battle pass = a season with a fixed end, flat XP per level (1,000/level),
weekly + seasonal challenges that pay big chunks, rewards unlocked at set levels,
a visible level number that keeps climbing past the reward track, and the past
season kept as history. Borrow: season, flat levels, challenges, reward track,
history. Do NOT borrow: paid tiers, loot boxes/random drops, FOMO timers that
punish missing a day (conflicts with the July 22 anti-loot-box decision).

Restructure verdict (what changes in RPGACE's skeleton):
- ONE ledger table (proposed name xp_events): one row per earned action:
  realm, source_table, source_id (unique pair = no double counting), xp,
  earned_at, season (year). Level, realm levels, titles, Chronicles "XP by
  section" and the yearly recap are all read from it. Kills systems A, B, C.
- How rows get written — two real options:
  (i) Postgres triggers on the source tables (one SQL function + an xp_rules
      table). Catches every writer (app, Routines, local_server.py), undo on
      delete is automatic, backfill = same function run once. One pipeline (rule 8).
  (ii) Client calls a shared RPGACE.xp.award() at each action. Easier to read,
      but every new feature must remember to call it (the exact drift that made
      addXP lie).
  Recommendation: (i) triggers, with (ii) only for things that have no row of
  their own (rare).
- Profile card: replace OUTPUT/GROWTH/XP bars with season level + realm bars.
- Legacy addXP(): becomes a no-op toast or is removed; questEngine stops
  painting the card.

Risks found:
- R1 Gaming/Goodhart: easy, repeatable actions (journal, ticks) can outpace
  shipping. Needs per-realm weights and/or daily caps.
- R2 Season start: today is Oct 13; a Jan-1 reset means Season 2026 is 11 weeks.
- R3 Undo/abuse: tick-untick loops; deleted rows. Triggers handle delete; ticks
  need a unique key per day.
- R4 Realm boundaries: some actions are two realms (cooking a recipe from a book,
  reading about production). One realm per action keeps it simple.
- R5 Triggers on tables with no backup: additive only (new table + triggers),
  no change to existing rows. Safe class under the CEO carve-out, but still shown.
- R6 Motivation decay mid-season: battle passes fix this with challenges; without
  them a flat ledger is just a counter.

-------------------------------------------------------------
Competitor "The Producer" (governing rule: beat made or video posted in 48h):
 - P1: Shipping must dominate. One shipped beat/video should be worth more than
   a week of chores, or the pass rewards being busy, not shipping.

 - P1: Small daily wins (routines, gym, cooking) keep the streak alive on days
   music doesn't happen; they must count, or the pass stalls on off days.
 - P2: Weekly challenges are the motivational engine; a ledger with no goals is
   just a number.
Competitor "The Skeptic" (why NOT):
 - P1: Real activity is low (0 cooks, 0 gym, 0 shipped). A big XP system risks
   being built before the habits it measures exist — infrastructure for its own
   sake (the Galaxy-Map trap, Sep 15 finding).
 - P2: Yearly reset wipes visible progress; for a solo user, losing level could
   demotivate. Needs a permanent "career" number alongside the season.
Competitor "The Engineer":
 - P1: Three systems today — any new one must DELETE the old two, not add a fourth.
 - P2: Triggers > client calls; otherwise this rots like addXP did.
Competitor "The Designer":
 - P1: The profile card is cramped on a phone; realm bars must fit at 400px.
 - P2: Realm titles need to read as earned ranks, not jokes; one ladder per realm.

Cross-examination outcome: Producer vs Habit Coach resolved by weighting, not
exclusion (both count; shipping weighted far higher). Skeptic P1 answered by
keeping the build small (ledger + triggers + card) and letting challenges come
later. Skeptic P2 is a real interrogation question (career total kept or not).

7.3 Anti-grind + balance ("2 into 1")
- Same action, same day: 1st-2nd 100%, 3rd 50%, 4th 25%, 5th+ 0.
- Never reduced: posted/released, sold, trip done, book finished, milestones, challenges.
- Balance bonus (weekly): touch 5+ realms +100, 8+ realms +250.

7.4 Undo
- Undone in the same week (before Sunday's report is saved): RPGACE asks
  "Was this actually done?" Yes = XP stays. No = XP comes off.
- After that week: XP stays; the detailed record may be gone; the saved
  weekly / monthly / season reports keep it.

7.5 Challenges (all four)
- Weekly: Monday, pick 3 from suggestions (at least 1 Oracle-suggested from real
  gaps); +150 each.
- Season goals: 3-5 set in January (e.g. ship 24 beats, read 6 books); 1,000-3,000 each.
- Realm quests: a short chain to each realm's next gated title.

7.6 Rewards
- Realm ranks, gated titles, badges (auto or claimed with a link/note).
- Treats: pin a Shopping Wishlist item OR a free-text treat to a season level or
  realm rank; hitting it marks it earned (buying still uses the normal cool-off).
- Themes: accent colours / profile frames unlock at season levels 10/25/50/75.
- Season rank (Sky ladder), Year Wrapped on Dec 31, Trophy cabinet page,
  Oracle flair (quiet: title in greetings, one toast + Morning Brief line).
- Every level-up, rank-up, badge and title is also a Chronicles item.

7.7 Profile card
- Sky rank medal + season level + progress to next level, a 13-spoke balance
  wheel (this week's XP per realm), tap -> Season page (realms, pass track,
  challenges, trophy cabinet). The OUTPUT / GROWTH / XP bars are removed.

7.8 How it's built (one pipeline, rule 8)
- New private tables (no anon policy, read via /api/data-write like plans):
  xp_rules (action -> realm, base XP, cap rule), xp_events (the ledger, one row
  per earned action; unique source_table+source_id+action; status
  active/pending_confirm/removed), xp_unlocks (titles, badges, ranks, themes,
  claimed proofs), xp_treats, xp_challenges, xp_reports (weekly/monthly/season
  snapshots, Year Wrapped).
- Postgres triggers on the source tables write xp_events using xp_rules, apply the
  cap, and on delete either mark pending_confirm (same week) or leave the row.
  The trigger function catches its own errors so an XP bug can never block
  saving a cook, tick or sale.
- Retired: careerStatCard's WEIGHTS/CUM_BANDS score, questEngine's card
  painting, legacy addXP pop-ups (removed or turned into ledger-backed toasts).
- Additive only: new tables + triggers; no existing rows changed.

8. COUNCIL OF 5
---------------
Technical risk: triggers on ~12 source tables are the riskiest part; a wrong rule
silently mis-awards. Mitigation: rules in a table (fixable without a deploy), the
trigger swallows its own errors, and XP-1 ships with a test script that inserts
and rolls back one row per source.
Scope/cost: 8 items over several sessions; near-zero AI cost (only Oracle
challenge suggestions and greetings). The heavy part is UI (season page, wheel,
cabinet).
Maintainability: one ledger + one rules table replaces 3 systems; a new feature
adds one rule row and one trigger line.
User experience: 13 realms is a lot; the wheel keeps the card light; realm
names are drafts for Alex to edit.
Why NOT (honest):
 1. Real usage is low today (0 cooks finished, 0 gym, 0 shipped, 0 routines).
    The pass can't motivate habits that never get logged; it risks becoming
    another system built ahead of use (the Sep 15 Galaxy Map finding).
 2. Points can replace the work (Goodhart). Shipping weight + caps reduce it,
    they don't remove it.
 3. Time spent here is time not spent on product debt (reference_tracks
    scale/genre backfill, hand-testing).
Verdict: build, but staged — XP-1 + XP-2 first (they also fix today's real bug of
three systems fighting the bar); use pre-season to see if it actually changes
behaviour before building XP-5..XP-8.
