3. FREE-FOR-ALL DEBATE (4 real shapes, each argued by its own competitor)
 A "Mission + context slot": a mission is generic (verb + skill, e.g. "Roast with a technique"); it has a context slot
   filled when planned/started; video specifics become CONTEXT CARDS under a mission ("poke-and-score crackling" is a
   technique card under Roast). For: exactly Alex's words, reusable, repeatable, helps block planning. Against: new
   shape on realm_tasks (or a new table), migration of 113 inbox rows.
 B "Generalise on intake": keep the pipeline; the cheap model maps each video quest to the nearest generic mission and
   stores the specific as an example. For: automatic, no new UI to learn. Against: alone it gives no place to choose
   context; mapping errors need review.
 C "Group, don't change": keep specific tasks, show them grouped under generic headings in Live now. For: cheapest.
   Against: doesn't give "pick context" or help planning; the inbox keeps filling with one-offs. Loses on Alex's goal.
 D "Context = the realm's own generator": choosing context runs the realm's existing engine (Chef → Generate recipe with
   the technique pre-filled; Athlete → exercise combo; Producer → reference track / beat idea; Creator → post idea).
   For: reuses engines (rule 8), "making those special to each cook". Against: costs a model call where the generator
   uses one; not every realm has a generator.
 Outcome: A + B + D together beat each alone. A is the shape, B fills it from videos, D fills the context slot.
 C is rejected (doesn't meet the goal). Why-not (Council of 5): one more step before doing (friction) — mitigated by
 picking context at plan time, not at the moment of doing; token cost per generated context — use the cheap model or
 the existing generator's own cost, never a premium triage call (Building guide 11).

6. DRAFT PLAN "Generic Missions" (GM-1..GM-9) — Council of 5 reviewed, awaiting Alex's approval (CEO Loop 1 Step 6)
 GM-1 Shape: missions stay realm_tasks rows (repeatable, generic, fixed XP); new private table mission_contexts
      (mission_id, realm, title, detail, source video|generated|typed|starter, source_ref, recipe_id, times_done,
      last_done_at, status kept|dropped). Additive (carve-out). chore_blocks.items[] item gains context_id/context.
 GM-2 Missions for Chef, Athlete, Producer, Creator: catalogue reworded into generic missions with a context kind
      (recipe / combo / reference / post idea / card), shown in Catalogue for keep/drop (missions only).
 GM-3 Filing pipeline: one client job (cheap model, batches of ~10) reads inbox video tasks for the 4 realms, maps each
      to a kept/proposed mission and writes a context card; the task leaves the inbox (status filed, never deleted).
      Nothing fits -> one proposed generic mission for review. Same job for every new video.
 GM-4 Backfill: run GM-3 on today's 113 inbox rows (count before/after; the 9 other realms' rows stay in the inbox).
 GM-5 Plan block: picking a mission asks for context: its cards (untried first, "done N times"), Generate (realm
      engine), or type your own. Stored on the block item.
 GM-6 Chef: Generate recipe pre-filled with mission + card -> saved to My Recipes, set as the block's planned cook,
      missing items added to shopping.
 GM-7 Athlete (exercise combo, DR-12), Producer (reference track / beat idea), Creator (post idea) as context sources.
 GM-8 Live now shows mission + context with its Open (recipe, combo, reference, post); Done pays the mission's fixed
      XP, card times_done +1.
 GM-9 Wrap: tests, docs, SELF_KNOWLEDGE, notes for rolling out to the other 9 realms.
 Council of 5: risk = model mis-filing (card shows "filed under X · move"); cost = one cheap call per ~10 tasks, Chef
 Generate uses the recipe engine's own model; maintainability = one filing job, no second pipeline (rule 8); UX = one
 extra pick in Plan block, chosen by Alex; why-not = adds a step before doing and a new table — accepted because
 context at plan time is exactly what Alex asked for. Status 'filed' needs the realm_tasks status check widened
 (query pg_constraint first; additive value, not a delete).
