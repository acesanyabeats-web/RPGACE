EVIDENCE (live code + Supabase, this pass)
- cookingOracle = rpgace_core.js ~42056-49339, 33 ui + 80 logic functions, 16 popup screens + full-screen Cook Mode.
- Screen graph: hub -> {Planned Cook, Grocery List, Generator, Current Stock, What Can I Cook}.
  Dead ends (link nowhere else in Cooking): Current Stock, Settings (only reachable from inside the
  generator), Cook Mode, Recipe-update confirm, Price entry.
  Each screen does pop.close() then opens the next: one-way chain, no back.
- Saved recipes (8 rows) have no library screen; reachable only via a session's recipe list or the
  stock-match finder.
- BUG: logic._recordPurchase tops up pantry_stock with on_conflict=ingredient_id, but the table's
  primary key is (ingredient_id, location) (pg_constraint checked). Postgres rejects that conflict
  target, so the top-up fails every time -> cb(error) -> "purchase log failed" toast even though the
  price + bought flip already wrote. It also reads quantity from any one location (limit=1) and
  never records a location. Never exercised: 0 bought items.
- GAP: logic._finishCook marks planned_cooks cooked + journal cooked; never deducts stock.
  0 cooks marked cooked so far.
- DUP (rule 8): logic._loadPantryNamed and logic._loadPantrySummed run the same pantry_stock read.
- shopping_lists has planned_cook_id (uuid) + status; a standing "top-up" list can be a row with
  no planned cook. Status CHECK must be read from pg_constraint before writing a new value.
- planned_cooks has no column to record what a finish deducted (no undo trail today).
