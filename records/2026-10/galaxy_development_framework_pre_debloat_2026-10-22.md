### Rules and workflows — real, extracted from every obstacle this build actually hit (Aug 14, Alex's own direct ask: "every obstacle and bug and solution/workaround and mapping/finding files and functions we found to map out galaxy map should now be included as rules and workflows of galaxy development framework")

These are not narrative — they're the reusable, prescriptive lessons a future Galaxy Map / Total-systems mapping pass should follow, extracted from real bugs found and fixed across the Aug 13-14 build (full incident detail lives in `records/2026-08/galaxy_map_*.txt` and `patch_notes.html`'s own dated cards; rule 8 — not retold here).

**R1 — A codebase's real relationships hide in more idioms than direct calls, and a mapping tool built against ONE file systematically under-detects anything crossing a file boundary.** RPGACE's own real, confirmed idioms beyond a literal `RPGACE.modules.X.Y()` call: a `window.callOracle`/`sendChat` re-wrap chain; a shared `RPGACE.utils.*` convergence point; direct DOM-id triggering (`#chat-input`/`#send-btn`); a documented `window.X = function` override (one file defines an original/stub, another reassigns the real implementation — confirmed for `authGate`/`toggleInstaPanel`/`toggleProdOraclePanel` and more); a dedicated wrapper section that bridges UI functions in one file to named events in another (rpgace_core.js's own "FUNCTION WRAPPERS," explicitly commented "Do NOT patch main.js — wrap here instead"); and real local variable aliasing (`var rt = RPGACE.modules.researchTabs`) that a literal-string regex alone will miss. **Workflow**: before declaring a mapping pass "done," explicitly enumerate which of these idioms the detector actually checks, and treat a module/function with zero detected relationships as a real, open question — is it truly isolated, or is the detector just blind to the idiom it uses — never assumed to be the former by default.

**R2 — Rivers (and any other spatial/mental grouping label) are a real, useful navigation construct for humans and Claude Code, not something that exists in the code itself.** Alex's own direct confirmation (Aug 14): "the code doesn't actually have any rivers, it was a concept i came up with for minotaur map." A real, structural consequence: cross-river relationships (a hook fired in one river's module, heard in another's) should be the EXPECTED common case, not a surprising anomaly to explain away — RPGACE's own real measurement found zero same-river hook pairs anywhere in 44 modules, meaning `RPGACE.hooks` is a purely cross-river mechanism in this codebase. **Workflow**: never force a real cross-cutting relationship into a same-grouping-only rendering just because that's the existing diagram's shape; add a genuinely separate visual/textual layer for it instead (this build's own precedent: Level 3's Alex-bubble and the dedicated hook-signal detector, not a same-river-only edge).

**R3 — When a signal's own real anchor point isn't rendered as a node (e.g. `init`, deliberately excluded from Level 3), attribute that signal onto ONE real, evidence-backed stand-in — never fan it out across every plausible candidate.** Fanning out inflates a bubble/count into implying several independent real touches where there's genuinely one (found and reverted for `pathRouter`'s own real popstate-listener evidence before shipping the single-anchor version). **Workflow**: prefer the most specific real evidence already available (an existing `incoming_attr`-style pairing) as the anchor; fall back to the first candidate in real, deterministic source order — never a guessed or unordered pick.

**R4 — A detection/gating rule should be asked for directly once two real hypotheses have been tried and disproven against a confirmed example — never iterated a third time blindly.** Same discipline as CLAUDE.md's own standing rule 9, re-confirmed twice this build (the Alex-bubble's OUTPUT-edge precision rule; the rank-band-vs-Level-4 sub-page choice). **Workflow**: state each disproven hypothesis and exactly which real confirmed case broke it, then ask — don't keep guessing.

**R5 — Idempotency is a real, checkable property, not an assumption — verify it, don't declare it.** Twice found broken by a hash-randomized Python `set()` iteration order (`compute_function_rank()`'s DFS, `build_component_zone_map()`'s tie-break) producing a different real layout on a fresh process re-run of identical source. **Workflow**: after any change to a generation script, run it twice in a row from a fresh process and diff the output (md5 or direct comparison) before calling it done — this is now a standing verification step for every Galaxy Map regeneration, not optional.

**R6 — A "before/after improvement" claim needs a real measured diff against the actual committed state, not a re-read of the new code alone.** Every real "resolved" claim in this build (authGate/pathRouter's Alex-bubble, the isolated-module count, the crossing-reduction numbers) was checked against `git show HEAD:<file>` or an equivalent real prior snapshot, not asserted from confidence in the fix. **Workflow**: when reporting a measured improvement, always cite the real before AND after number from an actual comparison, not just the after number from the new code's own logic.

**R7 — A real methodology/rules doc (like `system_map_spec.md`) can silently drift behind what the CODE/RENDERING layer has already implemented — check it specifically, don't assume it's current just because the code works.** Found Aug 14: the Alex-actor-as-connector-edge concept existed in real, shipped code (the "Alex bubble," built Aug 13) before `system_map_spec.md` ever named it as a real rule. **Workflow**: whenever a genuinely new detection/rendering CONCEPT ships (not just new data within an existing concept), check the governing methodology doc for whether it names that concept — if not, that's a real, fixable documentation gap, not a "the doc is just high-level" excuse.

**R8 — A `system_map_flags`-style tracking row does not auto-resolve when the real work behind it lands elsewhere — it needs an explicit close-the-loop check.** Found Aug 14: a real flag asking "does the Galaxy Map count as a new minotaur_map.html wing" sat `status='flagged'` for a full day after the real wing had already been added, because nothing ever went back to check. **Workflow**: any retroactive/trickle-down scan should explicitly re-check EXISTING open flags against current real state first, before hunting for new ones — a stale-open flag is exactly as real a finding as a newly-discovered gap.

**R9 — "Hand-test" doesn't always mean a literal browser click — for a framework with genuinely zero user-facing surface by design (like `/CEO` itself, per the Aug 12 fix removing all RPGACE-facing CEO UI), the real test is whether the automation PIPELINE fires correctly end-to-end on real work, demonstrated by repeated real exercise.** **Workflow**: before demanding a literal UI hand-test for something, check whether a real UI surface actually exists for it — if not, the honest verification is "did this actually run, for real, and produce the right result, more than once," not a fabricated click-test.

**R10 — Generating real, evidence-grounded content at scale (e.g. 42+ `/perspective` module reports) should pull from the SAME already-computed real detection data the Galaxy Map itself uses, via a real script — never hand-written one at a time past the first couple of proof-of-concept cases, and never fabricated/paraphrased.** This satisfies "gather real evidence before writing a word" by construction, since the evidence IS the generator's real input. **Workflow**: when a `/perspective`-style report (or any similarly-shaped evidence-grounded write-up) needs to scale past a handful of hand-written examples, write a generator script against the real, already-built detection functions rather than continuing by hand — reviewed and spot-checked before bulk-inserting, same discipline as any other generated artifact in this pipeline.

**R11 — Real code/data findings surfaced while building a mapping tool are worth fixing on the spot when cheap (a dead function reference, a stale count, a wrong card total) — even when they're unrelated to the mapping work itself.** Found and fixed opportunistically this build: manual.html's dashboard-card row citing a dead function (`_openVideoPipeline`, deleted Aug 6) and a stale card count. **Workflow**: a mapping/audit pass is also a real, free opportunity to catch nearby staleness — fix it inline (with a clear note of what was wrong and why), don't file it as a separate future item if it's a one-line correction.

**R12 — An actor/external bubble (Alex, Oracle, or any future external) is real ONLY where real evidence supports it — never rendered as a forced-permanent fixture at every level regardless of actual use.** Alex's own direct correction (Aug 14), after his own initial ask used the word "permanent": *"other externals don't have to be permanent, oracle too tbh, its just going to be very prevalent since claude api runs a lot of the architecture... what we are doing will also help map those out."* A bubble that's genuinely everywhere (because the evidence genuinely shows it everywhere, e.g. Oracle today) and a bubble that's forced everywhere (because the design says it must appear) LOOK the same on screen but are opposite in honesty — this project has always chosen the former. **Workflow**: any new actor/external bubble must be evidence-gated exactly like the Alex bubble already is (a real per-function/per-module call-count > 0, never a bare "this exists somewhere in the system" assumption), and the real edge count (not just presence) is itself load-bearing evidence — a module Oracle touches once and a module it touches nine times are not the same real relationship, and the map should say so.

**R13 — Real navigation between adjacent levels should exist at BOTH the coarse (zoom-out) end and the fine (drill-in) end of a level, not just one direction.** Alex's own direct ask (Aug 14): the leftmost/entry objects at level N need a real "backdoor" link up to the specific real level-(N-1) object that actually leads there — a genuine zoom-out for understanding broader Total-systems context — while the rightmost/terminal objects at level N need a real forward link continuing INTO the next level of logic (toward Levels 5/6, not back out). Real, concrete design, not yet implemented in rendering (flagged honestly — `ceo_plan_items` G19): reuse the exact real attribution mechanics already proven for river-boundary "next function" stubs (`attribute_river_connection_function()`) and Level-3 cross-module backdoors (`compute_cross_module_function_calls()`) — never a generic "back" button with no real evidenced destination, same standing discipline as every other link this pipeline draws. **Workflow**: when building this, entry-side links point OUTWARD/UP (real zoom-out, matches the existing "⬅ from River N" stub language), terminal-side links point FORWARD/IN (real drill-deeper, a genuinely new direction this pipeline hasn't drawn before) — never conflate the two just because both are "navigation."

**R14 — A brand-new "should X integrate with Y" architecture question has no real baseline to `/drift`-check against, and forcing one produces a fake verdict.** Found Aug 14, real Alex ask ("use /paranoia and /drift to tell me if it is a good idea" on whether `/cartographer` should be used by GODMODE/`/scope`/`/commit-archaeologist`): `/drift`'s own real job is checking work against a *ratified plan* — there was no prior plan stating these should integrate, so a literal `/drift` run would have nothing real to check against. **Workflow**: when asked to `/drift` a genuinely novel proposal with no prior baseline, say so plainly rather than manufacture a fake VERDICT/BASIS pair, and substitute the actually-matching tool — here, `/restructure`-shaped two-sided reasoning (does fitting Y into X's existing skeleton genuinely help, real case both ways) answered the real question `/drift` couldn't. A named protocol producing an honest "that's not what this tool checks, here's the one that does" is a correct outcome, not a failure to follow instructions.

**R15 — Once a mapping tool exists with real, queryable relational data (module→river ownership, dashboard-card→module resolution, external-connector attachment), it is the FIRST evidence source for "where does X live" questions, not a cold grep of the raw source.** Alex's own direct ask (Aug 15): *"use galaxy map for this as a baseline rule instead of grepping, or use both in tandem to help with quality of findings, output of changes and functions themselves, and token usage."* Real worked example, same day: investigating A5 (Research Lab dismantling) via 2 cheap Python queries against `graphify_river_group.py`'s already-computed `RIVER_MODULES`/`DASHBOARD_CARDS` immediately surfaced that `conidPot`/`beatLog`/`contentProductionLive`/`videoSummary` were ALREADY River XI modules and `refCorpus` was ALREADY grouped with taxonomy-linking code — reframing a feared backend rewrite into a much smaller, evidence-backed UI-routing problem, for a fraction of the token cost a cold `rpgace_core.js` grep sweep would have taken. **Workflow**: for any "what module owns X" / "what already exists near X" / "where does X sit relative to Y" question, query the Galaxy Map's own computed tables first (`RIVER_MODULES`, `DASHBOARD_CARDS`, `CARDS_BY_RIVER`, `EXTERNAL_RIVER_LINKS`, or the rendered `graphify-out/galaxy_map*.html` pages) — fall back to a targeted grep only for the specific implementation detail the map doesn't capture (e.g. one tab's internal DOM-id wiring), and use both together rather than either alone when a finding needs both the relational picture and an exact source citation. Mirrors CLAUDE.md's own standing rule 15, named there the same session.

**R16 — A structural design that gives ONE peer among structurally-equal units special/exclusive treatment (e.g. "this one unit is the gateway to deeper structure") is probably an oversight, not a decision, unless there's a real, stated reason — check every peer for the same treatment before finalizing.** Found Aug 18, real Alex correction on the L0/Dimension/River/Current redefinition plan: a draft wrongly framed "RPGACE Architecture" as the one privileged L0 unit whose bubbles gate into the deeper Level 0-4 structure, when Alex's own original spec already said every unit's own bubbles gate into ITS OWN real dimensions — the L0-4 hierarchy is one real dataset that each of the other 6 units provides a genuinely different, equally real lens over (Alex's decisions, Supabase's tables, Skills' procedures, External AI's calls, Orchestrator CC's commits, Oversight Docs' coverage), not a single door reached through one favored unit. His own words, generalizing this past the one fix: *"you should always, and i mean ALWAYS, make considerations like this (its QoL updates, who doesnt love them?)."* **Workflow**: when drafting any structural design over a set of peer objects (units, modules, rivers, actors), explicitly ask "does every peer get the same kind of treatment, and if one doesn't, do I have a REAL, stated reason, or did I just default to whichever one felt most central while writing the summary?" — before presenting the design, not after a correction.

**R17 — Once the Galaxy Map is a real truth source (layer (f)), oversight-doc updates are not a separate trailing pass — each G-step's own real /Engineer execution scopes and executes its own relevant oversight-doc updates as part of building that step.** Alex's own direct ask (Aug 18): "i would also like all the oversight documents to update based on all the capabilities we've added through galaxy map, and make them stem from it too to help update, and scope their changes into the g-steps too." Real distinction from the standing rule-6 obligation (CLAUDE.md): rule 6 says an update happens same-session; R17 additionally says WHICH doc(s) need updating for a given G-step is itself part of that G-step's own Stage 1 evidence-gathering, not decided ad hoc afterward. **Workflow**: when executing a Galaxy Map G-step via `/Engineer`, Stage 1 explicitly names which real oversight doc(s) that step's own new capability affects (same discipline `.claude/skills/update-logging-system/SKILL.md`'s dependency map already uses for other change types) before Stage 2 building starts, and Stage 3's Council-of-5 report includes those doc updates as part of the real diff being reported on — never a separately-scheduled catch-up pass.

**R18 — A summary/count constant derived from a growing collection (a river count, a module count, a phylum count) is a real, silent-staleness risk distinct from a code bug — the collection can grow while the constant describing its size never gets touched, since nothing forces the two to move together.** Real, confirmed instance (Aug 20 2026): `TOTAL_ZONES = 16` was correct from its own creation until River XVII was added (Aug 18, G49) — `RIVER_NAME` grew to 17 real entries, but `TOTAL_ZONES` was never updated, silently dropping River XVII from the Obsidian vault export AND creating a real angle-collision risk in `zone_center()`'s own ring-position formula (river 17's stale angle `2π·16/16` collided with river 1's `2π·0/16`). Found by a plain file-count sanity check during unrelated work, not a deliberate audit. **Workflow**: whenever a new item is added to a collection that a separate constant/count summarizes, grep for that constant's own name project-wide in the SAME commit — the same "two separate greps" discipline CLAUDE.md's own rule 13 already established for display-text-vs-raw-literal, extended here to summary-constant-vs-source-list.

**R19 — A hardcoded cross-file path read (`Path('filename')`, `open('filename')`) embedded inside detection/mapping tooling must be grepped project-wide before that file is merged, renamed, or deleted — and prefer fail-loud over fail-open when the read feeds a staleness-detection pipeline.** Real, confirmed instance (Aug 20 2026): merging `main.js` into `rpgace_core.js` left `graphify_river_group.py`'s `MAIN_JS = Path('main.js')` and a second script's own separate hardcoded read both pointing at a file that no longer existed — both failed OPEN (empty dict/string, no crash), meaning the exact Aug 14 UI/backend detection fix these enabled would have silently regressed with zero visible error if not independently re-tested afterward. **Workflow**: `grep -rn "Path('<oldname>')\|open('<oldname>')"` across `scripts/` before considering a file merge/move/delete complete (same discipline as CLAUDE.md's own `vercel.json` api-file-deletion landmine, generalized past just `api/*.js`); when a read like this exists specifically to catch drift/staleness elsewhere, its OWN failure mode should raise loud, not quietly return empty — a silent empty result defeats the entire reason the check exists.

**R20 — A generator script that derives its OUTPUT FILENAMES from a mutable field (a river's display name, not a stable id) is not actually idempotent against a rename unless it also deletes stale files, not just writes fresh ones.** Real, confirmed instance (Aug 20 2026): `graphify_to_obsidian.py`'s river-hub notes are named from `RIVER_NAME[n]` (e.g. `"05 — River V — Two Independent Streams.md"`) — when Aug 18's G49 split renamed River V, the script kept writing the new filename correctly but never deleted the old one, leaving a real stale file sitting undetected in the vault for 2 days until a plain file-count check surfaced it. **Workflow**: any generator whose output filename is derived from mutable data must track its own run's full expected-filename set and delete any pre-existing file in its output directory NOT in that set, every run — "fully regenerated each time" has to mean this literally, not just "the files I expect to exist get written correctly."

**R21 — Before writing new code that consumes an existing function's return value, check its REAL return shape directly (read the function or run it) — a plausible name is not evidence of a scalar/list/dict/tuple shape.** Real, confirmed instance (Aug 20 2026, caught mid-build of G57): `compute_module_supabase_touch_count()` sounds like it returns a count (an int) but actually returns `(n_functions, n_total, {table_names})` — a first draft rendered the raw tuple literally into a real Obsidian note (`"7 real table touch(es)"` became `"(7, 19, {'taxonomy_proposals', ...}) real table touch(es)"`) before a direct spot-check of the generated output caught it. **Workflow**: this is rule 1's own discipline ("pull real source before editing, never guess at function internals") applied specifically to RETURN VALUES — a docstring skim can still leave the exact shape ambiguous; read the `return` statement itself or print a real sample output before writing consumption code around it.

**R25 — A `/CEO` Loop 2 item that skips `/Engineer`'s real 5-stage loop for a custom Omnitrix dispatch does not get the Truth Check for free, no matter how careful the substitute review is.** Real, confirmed instance (Aug 23 2026, found while shipping DD8, the session immediately after R24 was written): DD8 was dispatched via a custom Agent-tool prompt, not `/Engineer` itself. The orchestrating session's own manual review WAS genuinely thorough — it independently re-verified a module count, row counts, and div-balance against live evidence before shipping — but it still missed a real, self-contradicting hard number the build introduced into its own `patch_notes.html` card ("Seven `achiever_archive` rows logged" in one sentence, "21 of 21... with one honest blank" in the next — internally contradictory on its own terms, and both wrong; the real, Supabase-verified number was 9). This is not a review-effort problem — it's a coverage gap: free-form structural review checks whether a diff does what a report claims, it does not systematically re-derive every hard number a build's own NEW prose asserts and cross-check it against every other place in the same commit that states the same fact. That is precisely `/Engineer` Stage 5's named discipline, extended by the new Stage 5c (Self-Consistency Sweep, `.claude/skills/Engineer/SKILL.md`) built the same pass specifically for this failure class. **Workflow, now standing**: Loop 2 Step 1 (`CEO/SKILL.md`) states plainly that a custom dispatch is a real, nameable deviation, not a silent equivalent — and any Loop 2 item whose report contains a specific count is not "done" until Stage 5c has actually run against it. The irony is the point, not an excuse to skip the fix: a plan built entirely to catch doc-to-doc drift produced doc-INTERNAL drift in its own very first extension pass, caught only by the orchestrating session happening to grep for it rather than by any structural safeguard — which is exactly why this needed to become a structural safeguard instead of staying a one-off catch.

**R24 — A doc can go stale by a change made somewhere else entirely; the fix is a targeted doc-to-doc check, never a full sweep.** Real, confirmed instance (Aug 23 2026, the worked example behind the whole DD1-DD6 plan): `future_integrations.html`'s hand-typed A5 card read "Research Lab page confirmed fully intact, untouched" while CLAUDE.md's own Current State correctly described that page as retired, and the real `ceo_plan_items` row sat at a third value again — three sources of truth silently diverged for over a week, caught only by Alex's own hand-test. Two further instances found in the same pass: five `smoke_test_items` rows whose HOW-TO-TEST instructions pointed at Galaxy Map pages deleted during the Aug 21 fold passes (real, but outside those passes' file-grep blast radius, since the rows live in Supabase); and a `smoke_test_items` row invalidated purely by a file it CITED being deleted, without the feature it tested changing at all. **Workflow, now standing**: `update-logging-system`'s artifact 20, the **Cross-Doc Drift Check** — name the subject that changed, look at only the 2-4 docs that plausibly claim something about it, grade any gap with `/drift`'s vocabulary, route to brown/achiever (stale claim) or purple/`error_log` (broken code). Explicitly NOT a pairwise sweep of all 12 docs on every push — that costs more than the drift it catches (rule 11). `/scope`, GODMODE and `/commit-archaeologist` now each carry this obligation too, which they did not before; all of them point at the one definition rather than carrying a copy (rule 8). **A structural lesson worth keeping beyond the checklist**: the A5 card only COULD go stale because it was hand-typed HTML next to a live-fetched section — DD2 removed the whole class of bug by making every card on that page live-fetched from the same table `/colourgradient` reads. Where a doc can be rendered from real data instead of asserted by hand, prefer that; a checklist is the fallback for what genuinely cannot be.

**R23 — Oversight-doc logging and Supabase plan-tracking status are two separate updates that don't share muscle memory; a session can do the first perfectly and still leave the second stale.** Real, confirmed instance (Aug 22 2026): "A2 — Dummy Oracle banner slide-down UI fix" shipped (2 real commits) and was Alex-hand-tested working, and every file-based oversight doc (CLAUDE.md/patch_notes.html/Chronicles) correctly logged it the same session it shipped — but its own `ceo_plan_items` row sat `status='red'` for 11 days after, since flipping that row was never part of the same reflexive action as writing a patch_notes.html card. Found only because Alex explicitly asked for a `/paranoia`+`/CEO` drift check against the day's own `/Routine`-ratified Top 10, not caught by any of the routine logging that had already happened correctly. **Workflow, now standing and automatic, not just an on-request check**: `Bedtime` and `Summary` both check `ceo_plan_items`/`future_integrations.html` for any row matching work shipped in the span being logged, in the SAME pass as the file-based docs — `update-logging-system`'s own dependency map artifact 19 is the checkable form of this rule; both skills point here rather than each carrying their own copy (rule 8).
