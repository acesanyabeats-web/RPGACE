A1. In-app Oracle: "✗ Oracle error: Unauthorized"
Real investigation done (rpgace_core.js's authGate module, api/auth.js,
main.js's checkPassword — all read in full): the auth chain itself is
structurally correct. `verify(pw)` awaits a real server check, sets
`authGate._apiSecret` synchronously inside its own resolved promise
BEFORE returning true, and `checkPassword()` awaits that whole chain
before ever calling `initApp()` — no race in the normal fresh-login
path. `api/auth.js` always returns a real secret on a correct password,
never a partial/empty success. No localStorage-based "skip the gate"
mechanism exists that could leave `_apiSecret` null while still
appearing logged in.
REAL, UNRESOLVED GAP: `_apiSecret` lives ONLY in JS memory, with zero
persistence (no localStorage/sessionStorage backup) — so ANY scenario
where the page's JS state resets without a fresh password re-entry
(a PWA/service-worker swap of a live session, multiple tabs, a long-
idle tab that got backgrounded and resumed differently than a normal
reload) would silently start sending every `/api/*` call — including
Oracle — with no `X-RPGACE-Auth` header, and `requireAuth()` would
correctly return a real 401, surfacing exactly as "Unauthorized."
Per rule 4/rule 9 (don't patch blind, no guessed second attempt without
real evidence): NOT fixed this session. Real evidence still needed from
Alex to close this for good — specifically: did this happen right after
a fresh password entry, or after the tab/PWA had been open a while
without re-entering it? A browser DevTools Network-tab screenshot of
the actual failing `/api/oracle` request (showing whether
`X-RPGACE-Auth` was present, empty, or simply missing) would confirm
the theory directly rather than guessing at a fix.

dashboard bulletin is Oracle-GENERATED (an LLM call, like today's
Morning Brief), it inherits Oracle's own real failure modes — exactly
