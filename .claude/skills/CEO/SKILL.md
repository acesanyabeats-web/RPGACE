# /CEO — running a real multi-day build without re-litigating it every session

Alex's own words, verbatim, from inside the massive-expansion critique-doc build (Aug 11 2026): *"this is a multi day build, so create a plan, use any of my inputs through /interrogation, then run /paranoia with /engineer, /aintergrations and /restructure as advisors for writing the full list. make sure to use /drift on everything written in this document throughout to make sure nothing is missed, then compile into huge summary report. this report will then be given to me to read and improve, so we change the plan with /drift in mind. the final approved plan will be the original drift file for /Engineer to then execute through multiple days and sessions, with each build going through /drift and /paranoia to make sure everything is being executed as needed. then when steps in plan are complete, they compile into a smoke test document that will be implemented into rpgace as an oversight doc... run this as a new CEO framework that needs an md file."*

This is not a new kind of reasoning — same design as `/5thDimension`, `/Routine`, and `/paranoia`: a fixed sequence of protocols RPGACE already has, run in a specific order for a specific shape of problem. What's genuinely new here is the shape it's built for: a build that will outlive a single session, where the real risk isn't "did this one pass go well" but "did session 4 still know what session 1 approved."

**Source of truth**: this file, plus the `drift`, `paranoia`, `interrogation`, `Engineer`, `aintergration`, and `restructure` sibling skills it sequences. If this file and CLAUDE.md's own `## Invokable frameworks` section ever disagree on GODMODE/Council of 5/Omnitrix behavior, CLAUDE.md wins.

## The two loops

### Loop 1 — PLANNING (produces an approved plan, builds nothing)

**Step 1 — Compile.** Gather every real idea in scope — a pasted doc, a backlog of open forks, whatever prompted the build — into one real, close-to-verbatim spec file (rule 5's existing convention: a committed `.txt`, never left in chat only). Cross-reference against the existing backlog for real overlaps (two asks that are secretly the same underlying problem) rather than filing everything as flat, disconnected items. **This step already has a real precedent**: `alex_critique_and_massive_expansion_spec_2026-08-10.txt`, Parts A-C, built exactly this way before this skill existed.

**Step 2 — `/interrogation`.** Resolve genuine ambiguity before drafting the full list — never guess at intent for anything consequential. Skip this step's questions for anything already unambiguous; forcing a question round on a clearly-specified item is `/interrogation`'s own named failure mode.

**Step 3 — `/paranoia`, with `/Engineer`, `/aintergration`, and `/restructure` as advisors.** `/paranoia` already sequences most of the heaviest protocols in the project on its own; naming these three as advisors means their specific lenses get pulled in at the right points inside that sequence — `/Engineer`'s shape sketches real implementations for anything that needs to look concrete rather than hand-wavy, `/aintergration` judges any third-party tool the plan wants to lean on, `/restructure` flags anything that would actually change RPGACE-Claude Code's own skeleton rather than just adding a feature to it. This produces the real, full drafted list.

**Step 4 — `/drift`-check the draft against the compiled ideas, continuously.** Not a one-time gate at the end — while Step 3 is drafting, periodically re-run `/drift` Steps 1-4 against Step 1's own compiled source: does the drafted list still cover everything Step 1 found, or has something been silently dropped or reworded into a different, smaller ask? A `MINOR` finding here is a missed item to add back; a `CAPTURED` finding means the draft has quietly redefined the goal and needs to stop and re-anchor to what was actually asked.

**Step 5 — Compile the huge summary report.** The real deliverable of Loop 1. Written from the drafted list, organized (reuse `/scope`'s grouped-category method), and explicit about what's proposed vs. what's already decided vs. what's still a real open fork only Alex can settle.

**Step 6 — Alex reads, pushes back, and approves (or asks for changes).** This is the real gate. Nothing from Loop 1 becomes buildable until Alex has actually seen the report — per his own words, "given to me to read and improve." If he pushes back on part of it, that's `/drift` in the literal, intended sense: the plan changes, a new version of the report is written, and this step repeats. **Real, already-proven precedent**: this happened for real, same session this skill was named — Alex pushed back on 4 of 5 first-pass tool verdicts in the compiled report, real evidence-gathering and real building followed directly from that pushback (see Part F of the same spec file).

**Step 7 — The approved plan becomes the real `/drift` baseline.** Once Alex signs off (in whole or in named parts), that approved version — not the original draft, not chat scrollback — is the pinned, `ratified` baseline every future session's `/drift` check measures against for this build. Loop 1 ends here; Loop 2 begins.

### Loop 2 — EXECUTION (spans many future sessions, builds real things)

**Step 1 — `/Engineer` executes against the ratified baseline.** Each session picks up the next unstarted or in-progress item from the approved plan and runs it through `/Engineer`'s own real build-verify-report cycle (Opus builds, Sonnet reviews, a real Truth Check before anything is called done) — `/CEO` does not replace `/Engineer`'s own discipline, it hands `/Engineer` a real, pre-approved goal instead of a freshly-negotiated one each time. **A custom Omnitrix dispatch plus an ad hoc orchestrator review does NOT satisfy this step, even when the review is thorough (CLAUDE.md rule 17, R25 below)** — only actually invoking `/Engineer`'s own Stage 5/5b/5c gets a Loop 2 item its real Truth Check and Self-Consistency Sweep. If a session takes the shortcut anyway (time pressure, a build that felt simple enough not to need it), that's a real, nameable deviation to state plainly in the report, not something to silently treat as equivalent.

**Step 2 — Every build gets checked with `/drift`.** After `/Engineer` reports a real result, run `/drift` Steps 1-4 against the ratified baseline for that specific item: does what actually got built match what the plan asked for? `MINOR` gets fixed as a doc correction; `MATERIAL` gets a real undo/shelve/adopt decision (adopt needs Alex's confirmation if the change is real enough to matter); `CAPTURED` stops that item and surfaces to Alex before continuing — the goal moved, and that always needs his say-so, same weight as everywhere else in this project.

**Step 3 — Completed items populate the smoke-test doc.** A real, new RPGACE oversight-doc artifact (see below) — not built empty in advance, created and grown as real plan items actually finish. Alex ticks items by hand as he confirms they work in the live app; this is deliberately a *human* checkpoint, not an auto-tick, matching every other taxonomy/destructive-action checkpoint already in this project.

**Step 4 — Errors amend the smoke-test doc, and feed back to Oracle self-awareness.** When a ticked item later breaks (an error surfaces, a hand-test fails), the smoke-test doc's own entry for it gets un-ticked with a real note of what broke — and per Alex's own ask, that state should be reachable by `oracleAppGrounding.SELF_KNOWLEDGE` (the existing live Oracle self-awareness mechanism, not a new parallel one — rule 8) so Oracle itself knows what's currently working vs. currently broken, not just what was built once. When fixed, re-ticked, and self-awareness reflects that too. **Real, honest scope note**: routing live error codes through Supabase into self-awareness automatically (Alex's own stated wish) is real future infrastructure, not built by this skill file alone — it's exactly the kind of concrete piece Loop 1's own Step 3 (`/Engineer` sketches) should size and schedule as its own plan item once a real approved plan calls for it, not invented ad hoc here.

**Step 5 — Ties into Chronicles.** Real plan-item completions and the smoke-test doc's own state changes are exactly the shape of thing `system_updates`/Chronicles already logs — route them there the same way any other real Claude Code change gets logged (rule 6), so the smoke-test doc and Chronicles tell the same story from two angles (a checklist vs. a timeline) rather than drifting apart from each other.

**Step 6 — Every real episode logged opens with the real prompt scope that produced it, not just the outcome.** Alex's own words, verbatim (Aug 15): *"ceo framework should also have a step where it records the previous scope of my prompt into the doc to help fill it out."* Real reasoning behind the ask, also his own: he wants a record of what was actually asked alongside what was found/built, specifically so he (and a future session) can see the before/after of a method working — his own worked example, same session: liking that a report said "this is just a UI change," which only makes sense read against what he'd actually asked for (A5's full dismantling ask) versus what the Galaxy Map's real evidence narrowed it down to. Without the original scope recorded, a later reader has no way to see that narrowing happened at all. This is now a real, standing requirement for `session_lessons.html` (the doc this step feeds — see its own artifact entry in `update-logging-system/SKILL.md`, artifact 17) and for any `ceo_reports` row logged under Loop 2: **the first block of every entry is the real, close-to-verbatim prompt/scope that was active** (quote Alex's own words where he gave them, or state the real task-in-progress plainly where he didn't), written BEFORE the obstacle/reasoning/solution blocks — never synthesized afterward from what the solution turned out to be, which would silently launder away exactly the "scope narrowed once real evidence came in" signal this step exists to preserve. **Workflow**: when writing a `session_lessons.html` card or a `ceo_reports` summary, the first thing decided is "what was actually being asked when this happened," sourced from the real prompt text, not inferred from the fix.

## Grounded Mode — CEO active on every prompt until the plan is smoke-tested (Aug 11 2026, Alex's own explicit ask)

Alex's own words, verbatim: *"from now on CEO framework is grounded to every prompt until the plan is done and smoke tested. this will help continue /drift verification throughout the build phase and iterations along the way to keep larger goals in tact. this will help chase long term goals."* This is a real, standing behavior change, not a one-time instruction — while any `ceo_plans` row has `status = 'active'`, this session (and every future session working on RPGACE) treats that plan as live context for every prompt, not just prompts that explicitly say "/CEO".

**What "grounded to every prompt" actually means in practice** — scoped to stay honest about rule 11 (tokens/time are a design constraint), never the full Loop 2 ceremony on every single message:

1. **Before starting real work on a prompt**, check the real, derived display state (`paused`/`dormant`/`active`/`none` — see the `/stopCEO`/`/ResumeCEO` section below for the real distinction between `paused` and `dormant`). If it's anything other than `active`, Grounded Mode is a no-op — proceed normally. `paused` and `dormant` are both "off" for this purpose; they only differ in how they turn back on.
2. **If an active plan exists**, a lightweight relevance check: does this prompt's work touch a `ceo_plan_items` row (by item code, title keyword, or file/module overlap)? If clearly no (a genuinely unrelated bug fix, a one-line UI tweak), say so plainly and proceed without further ceremony — Grounded Mode does not force every unrelated prompt through a plan lens.
3. **If it does touch a plan item**, run `/drift` Steps 1-4 against that item's own real baseline (same shape as Loop 2 Step 2, just triggered by the prompt itself rather than waiting for a `/CEO`-named invocation) — update that item's `status`/`last_verdict`/`evidence` row in `ceo_plan_items` when the work changes its real state. This is what keeps "larger goals in tact" the way Alex asked: a plan item's real status is never more than one real prompt behind what's actually true, rather than only refreshed when someone remembers to run `/colourgradient` or `/CEO` by name.
4. **A `CAPTURED`-grade finding during a Grounded Mode check stops and asks**, same weight as every other `CAPTURED` finding in this file — Grounded Mode sharpens how often the check runs, it does not loosen what a bad finding requires.
5. **If the touched plan item sits anywhere in the real mapping hierarchy** (a galaxy/river/module/connector-edge change — `system_map_spec.md` §1) — added Aug 13, real Alex ask ("update into ceo so it happens when ceo mode is on") — Step 3's `/drift` check runs alongside `.claude/skills/cartographer/SKILL.md`'s own trickle-down/up cross-reference (Steps 3-4 of that skill), not as a separate ritual. A real MINOR/MATERIAL/CAPTURED integration-friction finding from that cross-reference gets surfaced to Alex the same way any other Grounded Mode finding does. Most Grounded Mode checks won't touch the mapping hierarchy at all — this step only fires when one genuinely does.

**`/stopCEO` and `/ResumeCEO` — real, named controls, not implicit.** Alex's own ask: *"/stopCEO and /ResumeCEO will help access plans and stop or resume planned build."*

- **`/stopCEO`** — sets the active plan's `ceo_plans.status` to `'paused'` (with `paused_at` timestamped). Grounded Mode goes fully dormant for that plan — no per-prompt relevance checks, no drift re-verification — until resumed. Real, honest use case: Alex wants to work on something genuinely unrelated to the active plan for a stretch without every prompt getting checked against it, or a plan needs to sit while he thinks about Loop 1 Step 6 feedback. `/stopCEO` never deletes anything — every `ceo_plan_items`/`ceo_reports` row for that plan stays exactly as it was.
- **`/ResumeCEO`** — sets `status` back to `'active'` (with a fresh `resumed_at` entry, `paused_at` left as history, not overwritten). The next prompt after resuming runs a real `/drift` catch-up pass across all `ceo_plan_items` for that plan (per-item Step 3 of Loop 2) before Grounded Mode resumes its normal per-prompt cadence — a plan that was paused for real days shouldn't resume assuming nothing changed underneath it; check first.
- **If more than one plan is ever `active` simultaneously** (not the common case today — only one real `/CEO`-tracked plan exists as of Aug 11), `/stopCEO`/`/ResumeCEO` take an explicit plan name/id argument; with none active or exactly one, they act on that one plan without requiring the argument.

**Two genuinely different OFF states — a real Aug 11 (2nd pass, same day) addition, per Alex's own explicit re-iteration.** His own words: *"every prompt in orchestrator is grounded with CEO framework while ceomode is on, when plan is finished and future plans is completely empty, /ceo mode switches off automatically until a plan or report populates the future integrations doc, or /stopceo switches off the mode too until /resumeceo is prompted by me."* This names TWO real, distinct off-paths, never conflated:
- **`paused`** — the manual `/stopCEO` path above. Stays off no matter what else changes, until Alex himself runs `/ResumeCEO`. Nothing auto-resumes this one.
- **`dormant`** — a fully-derived (not stored) state: the active plan's own `ceo_plan_items` are all green (real, checkable — auto-flips the plan's `status` to `'complete'` the moment this becomes true) AND `future_integrations.html` (every non-green `ceo_plan_items` row, across every plan) is completely empty — nothing real left to ground against. Alex doesn't need to do anything for this to end; the very next real plan or Future Integrations item, from ANY source, makes the next check read `active` again automatically, with no explicit "reactivate" step.

**Real correction, Aug 12 — a live app UI element was built for this and REMOVED, real `/misunderstanding` finding.** A same-day earlier pass read "just pop up that say CEO off or on, like a mode toggle" (Alex's own real answer to a different open question) as an instruction to build a real, visible toggle pill inside `rpgace_core.js` — rendered on every page of the deployed RPGACE app. Alex's own direct correction: *"ceo should not be present in rpgace, only orchestrator CC since its a development framework only, doesnt make sense to put it anywhere in rpgace total systems but orchestrator CC."* **Fixed**: the `ceoMode` module (the pill, `_fetchState()`, `_deriveDisplay()`, `stop()`/`resume()`) was deleted from `rpgace_core.js` entirely — RPGACE the product now has zero code, zero UI, zero visible trace of `/CEO`. The real distinction that holds, stated plainly so it isn't re-broken later: `ceo_plans`/`ceo_plan_items`/`ceo_reports` stay as Supabase DATA (Orchestrator-CC-internal, same posture as `session_memory`/`graphify_jobs` — invisible to a real RPGACE user, queried only by this session); `smoke_test.html`/`future_integrations.html` stay as real, independent, previously-and-separately-requested oversight ARTIFACTS that Loop 2 happens to populate, not "the CEO framework" rendered into the product. **The one live, checkable way to know Grounded Mode's real state going forward: ask this session directly** — it reads `ceo_plans`/`ceo_plan_items` from Supabase and reports back in chat, exactly the way any other `/drift`/`/colourgradient` status check already works. No pill, no popup, no app-facing surface, ever again without Alex's own explicit re-ask.

## The Supabase datasheet — `ceo_plans` / `ceo_plan_items` / `ceo_reports` (Aug 11 2026, Alex's own explicit ask)

Alex's own words, verbatim: *"making a supabase for this would help a lot, and tie all the loose reports and plans together. tie reports to the plans to make datasheet on all of it."* Real problem this solves: before this table set existed, a `/CEO` plan's real state lived only as prose scattered across CLAUDE.md bullets and dated `records/*.txt` files — genuinely durable (rule 5's own convention), but not queryable, and nothing tied a specific report file back to the specific plan item it verified. Three tables, `anon_all`/`authenticated_all` RLS matching the established internal-dev-tooling posture (`session_memory`, `graphify_jobs` — this is RPGACE-Claude-Code's own working data, not a Tier-3-sensitive table):

```sql
CREATE TABLE ceo_plans (
  id uuid primary key default gen_random_uuid(),
  name text not null,                 -- e.g. 'Massive Expansion'
  source_file text,                   -- the compiled spec .txt this plan came from
  status text not null default 'active', -- active | paused | complete
  basis text,                         -- ratified | provisional | none (drift vocabulary)
  created_at timestamptz default now(),
  ratified_at timestamptz,
  paused_at timestamptz,
  resumed_at timestamptz,
  completed_at timestamptz,
  notes text
);

CREATE TABLE ceo_plan_items (
  id uuid primary key default gen_random_uuid(),
  plan_id uuid references ceo_plans(id),
  item_code text not null,            -- e.g. 'A1', 'A10' (matches the compiled spec's own numbering)
  title text not null,
  status text not null default 'red', -- red | yellow | green (the /colourgradient vocabulary)
  basis text,                         -- ratified | provisional | none
  last_verdict text,                  -- on_track | drifted | inconclusive | blocked
  evidence text,                      -- a real file:line / commit hash / query result citation, never a guess
  last_checked_at timestamptz default now(),
  created_at timestamptz default now()
);

CREATE TABLE ceo_reports (
  id uuid primary key default gen_random_uuid(),
  plan_id uuid references ceo_plans(id),
  plan_item_id uuid references ceo_plan_items(id), -- nullable: a whole-plan report has no single item
  report_type text not null,          -- drift | paranoia | colourgradient | engineer | ceo_loop1 | ceo_loop2
  file_path text,                     -- the real records/*.txt this corresponds to, rule 5's own convention
  summary text,
  created_at timestamptz default now()
);
```

**How this ties in, concretely**: `/drift`'s own Step 5 report shape (Baseline/Work map/Verdict/Findings/Grades) is exactly what populates a `ceo_reports` row's `summary` plus updates the matching `ceo_plan_items` row; `/colourgradient`'s green/yellow/red benchmark reads `ceo_plan_items.status` directly instead of re-deriving it from scratch every run (real speed + consistency win, not a new evidence method — `/colourgradient`'s own guardrail against inventing a second evidence source still holds, this is a cache of the SAME evidence, not a shortcut around gathering it); Grounded Mode's per-prompt check (above) is what keeps these rows fresh without waiting for an explicit `/CEO`/`/drift`/`/colourgradient` invocation. **Never treat a `ceo_plan_items.status` value as truth on its own** — it's a cache of the last real check, timestamped via `last_checked_at`; if that timestamp is old relative to how much has changed, re-verify before trusting it, same "a doc's own claim needs re-verification" discipline as everywhere else in this project.

**Migration note, honest**: this table set is genuinely new infrastructure, built the same session it was asked for (additive `CREATE TABLE` only, no risk to existing data — proceeds under this file's own reduced-friction model without a separate stop-and-ask, per CLAUDE.md's own "CEO-framework Supabase migrations — narrowed, not abolished" carve-out for purely additive schema). It does not retroactively replace `records/*.txt` files as the verbatim-record store (rule 5 still applies — a report's full prose still gets written to a committed file); it ties those files together and makes their real-time STATUS queryable, which prose files alone can't do.

## The reduced-friction confirmation model — read the boundary carefully

Alex's own words: *"I don't care if it is not made well first time, I want you to just not drift and report everything truly... just do accept once or accept all etc... just report and log everything truthfully with /drift."*

This is real, and it is honored — but scoped exactly the way CLAUDE.md's own GODMODE boundary is scoped, not as a general override:

- **What this DOES reduce**: re-confirming individual Tier 1/2-shaped build steps that are already inside a plan Alex has personally read and ratified in Loop 1 Step 6. Once he's approved "build the Kimi/Luna routing scaffold," a future session executing that exact item doesn't need to re-ask "should I build this" — that question was already answered. Mistakes are expected and fine ("I don't care if it is not made well first time") — `/drift` is what catches and reports them, not a permission gate re-asked every time.
- **What this does NOT reduce, ever**: Tier 3 — destructive git operations, force-pushes, Supabase migrations, taxonomy writes, spending, credential/API-key handling, anything CLAUDE.md's own non-negotiable rules already gate on explicit confirmation. `/CEO` never substitutes for that confirmation, exactly the same boundary GODMODE's own section states word-for-word ("rigor is not authorization"). A plan item that turns out to need a real migration or a real spend decision still stops and asks, even mid-execution of an otherwise-approved plan.
- **The honest reason this split matters**: Alex approved the *plan*, not a blank check on *every possible consequence* of executing it. A build step that stays inside what was actually approved doesn't need re-asking. A build step that would require something Tier 3 - shaped and wasn't explicitly named in the approved plan is a new decision, not a re-litigation of an old one, and gets treated like any other Tier 3 fork.

### Rules and workflows — real, extracted from every obstacle this build actually hit (Aug 14, Alex's own direct ask: "every obstacle and bug and solution/workaround and mapping/finding files and functions we found to map out galaxy map should now be included as rules and workflows of galaxy development framework")

These are not narrative — they're the reusable, prescriptive lessons a future Galaxy Map / Total-systems mapping pass should follow, extracted from real bugs found and fixed across the Aug 13-14 build (full incident detail lives in `records/2026-08/galaxy_map_*.txt` and `patch_notes.html`'s own dated cards; rule 8 — not retold here).

**R1 — A codebase's real relationships hide in more idioms than direct calls, and a mapping tool built against ONE file systematically under-detects anything crossing a file boundary.** RPGACE's own real, confirmed idioms beyond a literal `RPGACE.modules.X.Y()` call: a `window.callOracle`/`sendChat` re-wrap chain; a shared `RPGACE.utils.*` convergence point; direct DOM-id triggering (`#chat-input`/`#send-btn`); a documented `window.X = function` override (one file defines an original/stub, another reassigns the real implementation — confirmed for `authGate`/`toggleInstaPanel`/`toggleProdOraclePanel` and more); a dedicated wrapper section that bridges UI functions in one file to named events in another (rpgace_core.js's own "FUNCTION WRAPPERS," explicitly commented "Do NOT patch main.js — wrap here instead"); and real local variable aliasing (`var rt = RPGACE.modules.researchTabs`) that a literal-string regex alone will miss. **Workflow**: before declaring a mapping pass "done," explicitly enumerate which of these idioms the detector actually checks, and treat a module/function with zero detected relationships as a real, open question — is it truly isolated, or is the detector just blind to the idiom it uses — never assumed to be the former by default.

**R2 — Rivers (and any other spatial/mental grouping label) are a real, useful navigation construct for humans and Claude Code, not something that exists in the code itself.** Alex's own direct confirmation (Aug 14): "the code doesn't actually have any rivers, it was a concept i came up with for minotaur map." A real, structural consequence: cross-river relationships (a hook fired in one river's module, heard in another's) should be the EXPECTED common case, not a surprising anomaly to explain away — RPGACE's own real measurement found zero same-river hook pairs anywhere in 44 modules, meaning `RPGACE.hooks` is a purely cross-river mechanism in this codebase. **Workflow**: never force a real cross-cutting relationship into a same-grouping-only rendering just because that's the existing diagram's shape; add a genuinely separate visual/textual layer for it instead (this build's own precedent: Level 3's Alex-bubble and the dedicated hook-signal detector, not a same-river-only edge).

**R3 — When a signal's own real anchor point isn't rendered as a node (e.g. `init`, deliberately excluded from Level 3), attribute that signal onto ONE real, evidence-backed stand-in — never fan it out across every plausible candidate.** Fanning out inflates a bubble/count into implying several independent real touches where there's genuinely one (found and reverted for `pathRouter`'s own real popstate-listener evidence before shipping the single-anchor version). **Workflow**: prefer the most specific real evidence already available (an existing `incoming_attr`-style pairing) as the anchor; fall back to the first candidate in real, deterministic source order — never a guessed or unordered pick.

**R4 — A detection/gating rule should be asked for directly once two real hypotheses have been tried and disproven against a confirmed example — never iterated a third time blindly.** Same discipline as CLAUDE.md's own standing rule 9, re-confirmed twice this build (the Alex-bubble's OUTPUT-edge precision rule; the rank-band-vs-Level-4 sub-page choice). **Workflow**: state each disproven hypothesis and exactly which real confirmed case broke it, then ask — don't keep guessing.

**R5 — Idempotency is a real, checkable property, not an assumption — verify it, don't declare it.** Twice found broken by a hash-randomized Python `set()` iteration order (`compute_function_rank()`'s DFS, `build_component_zone_map()`'s tie-break) producing a different real layout on a fresh process re-run of identical source. **Workflow**: after any change to a generation script, run it twice in a row from a fresh process and diff the output (md5 or direct comparison) before calling it done — this is now a standing verification step for every Galaxy Map regeneration, not optional.

**R6 — A "before/after improvement" claim needs a real measured diff against the actual committed state, not a re-read of the new code alone.** Every real "resolved" claim in this build (authGate/pathRouter's Alex-bubble, the isolated-module count, the crossing-reduction numbers) was checked against `git show HEAD:<file>` or an equivalent real prior snapshot, not asserted from confidence in the fix. **Workflow**: when reporting a measured improvement, always cite the real before AND after number from an actual comparison, not just the after number from the new code's own logic.

**R7 — A real methodology/rules doc (like `system_map_spec.md`) can silently drift behind what the CODE/RENDERING layer has already implemented — check it specifically, don't assume it's current just because the code works.** Found Aug 14: the Alex-actor-as-connector-edge concept existed in real, shipped code (the "Alex bubble," built Aug 13) before `system_map_spec.md` ever named it as a real rule. **Workflow**: whenever a genuinely new detection/rendering CONCEPT ships (not just new data within an existing concept), check the governing methodology doc for whether it names that concept — if not, that's a real, fixable documentation gap, not a "the doc is just high-level" excuse.

**R8 — A `system_map_flags`-style tracking row does not auto-resolve when the real work behind it lands elsewhere — it needs an explicit close-the-loop check.** Found Aug 14: a real flag asking "does the Galaxy Map count as a new minotaur_map.html wing" sat `status='flagged'` for a full day after the real wing had already been added, because nothing ever went back to check. **Workflow**: any retroactive/trickle-down scan should explicitly re-check EXISTING open flags against current real state first, before hunting for new ones — a stale-open flag is exactly as real a finding as a newly-discovered gap.

**R9 — "Hand-test" doesn't always mean a literal browser click — for a framework with genuinely zero user-facing surface by design (like `/CEO` itself, per the Aug 12 fix removing all RPGACE-facing CEO UI), the real test is whether the automation PIPELINE fires correctly end-to-end on real work, demonstrated by repeated real exercise.** **Workflow**: before demanding a literal UI hand-test for something, check whether a real UI surface actually exists for it — if not, the honest verification is "did this actually run, for real, and produce the right result, more than once," not a fabricated click-test.

**R10 — Generating real, evidence-grounded content at scale (e.g. 42+ `/perspective` module reports) should pull from the SAME already-computed real detection data the Galaxy Map itself uses, via a real script — never hand-written one at a time past the first couple of proof-of-concept cases, and never fabricated/paraphrased.** This satisfies "gather real evidence before writing a word" by construction, since the evidence IS the generator's real input. **Workflow**: when a `/perspective`-style report (or any similarly-shaped evidence-grounded write-up) needs to scale past a handful of hand-written examples, write a generator script against the real, already-built detection functions rather than continuing by hand — reviewed and spot-checked before bulk-inserting, same discipline as any other generated artifact in this pipeline.

**R11 — Real code/data findings surfaced while building a mapping tool are worth fixing on the spot when cheap (a dead function reference, a stale count, a wrong card total) — even when they're unrelated to the mapping work itself.** Found and fixed opportunistically this build: manual.html's dashboard-card row citing a dead function (`_openVideoPipeline`, deleted Aug 6) and a stale card count. **Workflow**: a mapping/audit pass is also a real, free opportunity to catch nearby staleness — fix it inline (with a clear note of what was wrong and why), don't file it as a separate future item if it's a one-line correction.

**R12 — An actor/external bubble (Alex, Oracle, or any future external) is real ONLY where real evidence supports it — never rendered as a forced-permanent fixture at every level regardless of actual use.** Alex's own direct correction (Aug 14), after his own initial ask used the word "permanent": *"other externals don't have to be permanent, oracle too tbh, its just going to be very prevalent since claude api runs a lot of the architecture... what we are doing will also help map those out."* A bubble that's genuinely everywhere (because the evidence genuinely shows it everywhere, e.g. Oracle today) and a bubble that's forced everywhere (because the design says it must appear) LOOK the same on screen but are opposite in honesty — this project has always chosen the former. **Workflow**: any new actor/external bubble must be evidence-gated exactly like the Alex bubble already is (a real per-function/per-module call-count > 0, never a bare "this exists somewhere in the system" assumption), and the real edge count (not just presence) is itself load-bearing evidence — a module Oracle touches once and a module it touches nine times are not the same real relationship, and the map should say so.

**R13 — Real navigation between adjacent levels should exist at BOTH the coarse (zoom-out) end and the fine (drill-in) end of a level, not just one direction.** Alex's own direct ask (Aug 14): the leftmost/entry objects at level N need a real "backdoor" link up to the specific real level-(N-1) object that actually leads there — a genuine zoom-out for understanding broader Total-systems context — while the rightmost/terminal objects at level N need a real forward link continuing INTO the next level of logic (toward Levels 5/6, not back out). Real, concrete design, not yet implemented in rendering (flagged honestly — `ceo_plan_items` G19): reuse the exact real attribution mechanics already proven for river-boundary "next function" stubs (`attribute_river_connection_function()`) and Level-3 cross-module backdoors (`compute_cross_module_function_calls()`) — never a generic "back" button with no real evidenced destination, same standing discipline as every other link this pipeline draws. **Workflow**: when building this, entry-side links point OUTWARD/UP (real zoom-out, matches the existing "⬅ from River N" stub language), terminal-side links point FORWARD/IN (real drill-deeper, a genuinely new direction this pipeline hasn't drawn before) — never conflate the two just because both are "navigation."

**R14 — A brand-new "should X integrate with Y" architecture question has no real baseline to `/drift`-check against, and forcing one produces a fake verdict.** Found Aug 14, real Alex ask ("use /paranoia and /drift to tell me if it is a good idea" on whether `/cartographer` should be used by GODMODE/`/scope`/`/commit-archaeologist`): `/drift`'s own real job is checking work against a *ratified plan* — there was no prior plan stating these should integrate, so a literal `/drift` run would have nothing real to check against. **Workflow**: when asked to `/drift` a genuinely novel proposal with no prior baseline, say so plainly rather than manufacture a fake VERDICT/BASIS pair, and substitute the actually-matching tool — here, `/restructure`-shaped two-sided reasoning (does fitting Y into X's existing skeleton genuinely help, real case both ways) answered the real question `/drift` couldn't. A named protocol producing an honest "that's not what this tool checks, here's the one that does" is a correct outcome, not a failure to follow instructions.

**R15 — Once a mapping tool exists with real, queryable relational data (module→river ownership, dashboard-card→module resolution, external-connector attachment), it is the FIRST evidence source for "where does X live" questions, not a cold grep of the raw source.** Alex's own direct ask (Aug 15): *"use galaxy map for this as a baseline rule instead of grepping, or use both in tandem to help with quality of findings, output of changes and functions themselves, and token usage."* Real worked example, same day: investigating A5 (Research Lab dismantling) via 2 cheap Python queries against `graphify_river_group.py`'s already-computed `RIVER_MODULES`/`DASHBOARD_CARDS` immediately surfaced that `conidPot`/`beatLog`/`contentProductionLive`/`videoSummary` were ALREADY River XI modules and `refCorpus` was ALREADY grouped with taxonomy-linking code — reframing a feared backend rewrite into a much smaller, evidence-backed UI-routing problem, for a fraction of the token cost a cold `rpgace_core.js` grep sweep would have taken. **Workflow**: for any "what module owns X" / "what already exists near X" / "where does X sit relative to Y" question, query the Galaxy Map's own computed tables first (`RIVER_MODULES`, `DASHBOARD_CARDS`, `CARDS_BY_RIVER`, `EXTERNAL_RIVER_LINKS`, or the rendered `graphify-out/galaxy_map*.html` pages) — fall back to a targeted grep only for the specific implementation detail the map doesn't capture (e.g. one tab's internal DOM-id wiring), and use both together rather than either alone when a finding needs both the relational picture and an exact source citation. Mirrors CLAUDE.md's own standing rule 15, named there the same session.

**R16 — A structural design that gives ONE peer among structurally-equal units special/exclusive treatment (e.g. "this one unit is the gateway to deeper structure") is probably an oversight, not a decision, unless there's a real, stated reason — check every peer for the same treatment before finalizing.** Found Aug 18, real Alex correction on the L0/Dimension/River/Current redefinition plan: a draft wrongly framed "RPGACE Architecture" as the one privileged L0 unit whose bubbles gate into the deeper Level 0-4 structure, when Alex's own original spec already said every unit's own bubbles gate into ITS OWN real dimensions — the L0-4 hierarchy is one real dataset that each of the other 6 units provides a genuinely different, equally real lens over (Alex's decisions, Supabase's tables, Skills' procedures, External AI's calls, Orchestrator CC's commits, Oversight Docs' coverage), not a single door reached through one favored unit. His own words, generalizing this past the one fix: *"you should always, and i mean ALWAYS, make considerations like this (its QoL updates, who doesnt love them?)."* **Workflow**: when drafting any structural design over a set of peer objects (units, modules, rivers, actors), explicitly ask "does every peer get the same kind of treatment, and if one doesn't, do I have a REAL, stated reason, or did I just default to whichever one felt most central while writing the summary?" — before presenting the design, not after a correction.

**R17 — Once the Galaxy Map is a real truth source (layer (f)), oversight-doc updates are not a separate trailing pass — each G-step's own real /Engineer execution scopes and executes its own relevant oversight-doc updates as part of building that step.** Alex's own direct ask (Aug 18): "i would also like all the oversight documents to update based on all the capabilities we've added through galaxy map, and make them stem from it too to help update, and scope their changes into the g-steps too." Real distinction from the standing rule-6 obligation (CLAUDE.md): rule 6 says an update happens same-session; R17 additionally says WHICH doc(s) need updating for a given G-step is itself part of that G-step's own Stage 1 evidence-gathering, not decided ad hoc afterward. **Workflow**: when executing a Galaxy Map G-step via `/Engineer`, Stage 1 explicitly names which real oversight doc(s) that step's own new capability affects (same discipline `.claude/skills/update-logging-system/SKILL.md`'s dependency map already uses for other change types) before Stage 2 building starts, and Stage 3's Council-of-5 report includes those doc updates as part of the real diff being reported on — never a separately-scheduled catch-up pass.

**R18 — A summary/count constant derived from a growing collection (a river count, a module count, a phylum count) is a real, silent-staleness risk distinct from a code bug — the collection can grow while the constant describing its size never gets touched, since nothing forces the two to move together.** Real, confirmed instance (Aug 20 2026): `TOTAL_ZONES = 16` was correct from its own creation until River XVII was added (Aug 18, G49) — `RIVER_NAME` grew to 17 real entries, but `TOTAL_ZONES` was never updated, silently dropping River XVII from the Obsidian vault export AND creating a real angle-collision risk in `zone_center()`'s own ring-position formula (river 17's stale angle `2π·16/16` collided with river 1's `2π·0/16`). Found by a plain file-count sanity check during unrelated work, not a deliberate audit. **Workflow**: whenever a new item is added to a collection that a separate constant/count summarizes, grep for that constant's own name project-wide in the SAME commit — the same "two separate greps" discipline CLAUDE.md's own rule 13 already established for display-text-vs-raw-literal, extended here to summary-constant-vs-source-list.

**R19 — A hardcoded cross-file path read (`Path('filename')`, `open('filename')`) embedded inside detection/mapping tooling must be grepped project-wide before that file is merged, renamed, or deleted — and prefer fail-loud over fail-open when the read feeds a staleness-detection pipeline.** Real, confirmed instance (Aug 20 2026): merging `main.js` into `rpgace_core.js` left `graphify_river_group.py`'s `MAIN_JS = Path('main.js')` and a second script's own separate hardcoded read both pointing at a file that no longer existed — both failed OPEN (empty dict/string, no crash), meaning the exact Aug 14 UI/backend detection fix these enabled would have silently regressed with zero visible error if not independently re-tested afterward. **Workflow**: `grep -rn "Path('<oldname>')\|open('<oldname>')"` across `scripts/` before considering a file merge/move/delete complete (same discipline as CLAUDE.md's own `vercel.json` api-file-deletion landmine, generalized past just `api/*.js`); when a read like this exists specifically to catch drift/staleness elsewhere, its OWN failure mode should raise loud, not quietly return empty — a silent empty result defeats the entire reason the check exists.

**R20 — A generator script that derives its OUTPUT FILENAMES from a mutable field (a river's display name, not a stable id) is not actually idempotent against a rename unless it also deletes stale files, not just writes fresh ones.** Real, confirmed instance (Aug 20 2026): `graphify_to_obsidian.py`'s river-hub notes are named from `RIVER_NAME[n]` (e.g. `"05 — River V — Two Independent Streams.md"`) — when Aug 18's G49 split renamed River V, the script kept writing the new filename correctly but never deleted the old one, leaving a real stale file sitting undetected in the vault for 2 days until a plain file-count check surfaced it. **Workflow**: any generator whose output filename is derived from mutable data must track its own run's full expected-filename set and delete any pre-existing file in its output directory NOT in that set, every run — "fully regenerated each time" has to mean this literally, not just "the files I expect to exist get written correctly."

**R21 — Before writing new code that consumes an existing function's return value, check its REAL return shape directly (read the function or run it) — a plausible name is not evidence of a scalar/list/dict/tuple shape.** Real, confirmed instance (Aug 20 2026, caught mid-build of G57): `compute_module_supabase_touch_count()` sounds like it returns a count (an int) but actually returns `(n_functions, n_total, {table_names})` — a first draft rendered the raw tuple literally into a real Obsidian note (`"7 real table touch(es)"` became `"(7, 19, {'taxonomy_proposals', ...}) real table touch(es)"`) before a direct spot-check of the generated output caught it. **Workflow**: this is rule 1's own discipline ("pull real source before editing, never guess at function internals") applied specifically to RETURN VALUES — a docstring skim can still leave the exact shape ambiguous; read the `return` statement itself or print a real sample output before writing consumption code around it.

**R25 — A `/CEO` Loop 2 item that skips `/Engineer`'s real 5-stage loop for a custom Omnitrix dispatch does not get the Truth Check for free, no matter how careful the substitute review is.** Real, confirmed instance (Aug 23 2026, found while shipping DD8, the session immediately after R24 was written): DD8 was dispatched via a custom Agent-tool prompt, not `/Engineer` itself. The orchestrating session's own manual review WAS genuinely thorough — it independently re-verified a module count, row counts, and div-balance against live evidence before shipping — but it still missed a real, self-contradicting hard number the build introduced into its own `patch_notes.html` card ("Seven `achiever_archive` rows logged" in one sentence, "21 of 21... with one honest blank" in the next — internally contradictory on its own terms, and both wrong; the real, Supabase-verified number was 9). This is not a review-effort problem — it's a coverage gap: free-form structural review checks whether a diff does what a report claims, it does not systematically re-derive every hard number a build's own NEW prose asserts and cross-check it against every other place in the same commit that states the same fact. That is precisely `/Engineer` Stage 5's named discipline, extended by the new Stage 5c (Self-Consistency Sweep, `.claude/skills/Engineer/SKILL.md`) built the same pass specifically for this failure class. **Workflow, now standing**: Loop 2 Step 1 (above) states plainly that a custom dispatch is a real, nameable deviation, not a silent equivalent — and any Loop 2 item whose report contains a specific count is not "done" until Stage 5c has actually run against it. The irony is the point, not an excuse to skip the fix: a plan built entirely to catch doc-to-doc drift produced doc-INTERNAL drift in its own very first extension pass, caught only by the orchestrating session happening to grep for it rather than by any structural safeguard — which is exactly why this needed to become a structural safeguard instead of staying a one-off catch.

**R24 — A doc can go stale by a change made somewhere else entirely; the fix is a targeted doc-to-doc check, never a full sweep.** Real, confirmed instance (Aug 23 2026, the worked example behind the whole DD1-DD6 plan): `future_integrations.html`'s hand-typed A5 card read "Research Lab page confirmed fully intact, untouched" while CLAUDE.md's own Current State correctly described that page as retired, and the real `ceo_plan_items` row sat at a third value again — three sources of truth silently diverged for over a week, caught only by Alex's own hand-test. Two further instances found in the same pass: five `smoke_test_items` rows whose HOW-TO-TEST instructions pointed at Galaxy Map pages deleted during the Aug 21 fold passes (real, but outside those passes' file-grep blast radius, since the rows live in Supabase); and a `smoke_test_items` row invalidated purely by a file it CITED being deleted, without the feature it tested changing at all. **Workflow, now standing**: `update-logging-system`'s artifact 20, the **Cross-Doc Drift Check** — name the subject that changed, look at only the 2-4 docs that plausibly claim something about it, grade any gap with `/drift`'s vocabulary, route to brown/achiever (stale claim) or purple/`error_log` (broken code). Explicitly NOT a pairwise sweep of all 12 docs on every push — that costs more than the drift it catches (rule 11). `/scope`, GODMODE and `/commit-archaeologist` now each carry this obligation too, which they did not before; all of them point at the one definition rather than carrying a copy (rule 8). **A structural lesson worth keeping beyond the checklist**: the A5 card only COULD go stale because it was hand-typed HTML next to a live-fetched section — DD2 removed the whole class of bug by making every card on that page live-fetched from the same table `/colourgradient` reads. Where a doc can be rendered from real data instead of asserted by hand, prefer that; a checklist is the fallback for what genuinely cannot be.

**R23 — Oversight-doc logging and Supabase plan-tracking status are two separate updates that don't share muscle memory; a session can do the first perfectly and still leave the second stale.** Real, confirmed instance (Aug 22 2026): "A2 — Dummy Oracle banner slide-down UI fix" shipped (2 real commits) and was Alex-hand-tested working, and every file-based oversight doc (CLAUDE.md/patch_notes.html/Chronicles) correctly logged it the same session it shipped — but its own `ceo_plan_items` row sat `status='red'` for 11 days after, since flipping that row was never part of the same reflexive action as writing a patch_notes.html card. Every oversight doc's status should be readable through `/colourgradient`'s own blue/red/yellow/green/purple/brown vocabulary at all times — a doc that hasn't been checked against that vocabulary recently is itself a staleness risk, not just the individual facts inside it.

**R22 — Table-first, bubble-follows: a real, permanent standing rule (Aug 21 2026, Alex's own verbatim words, given while building the Decision Matrix): "whenever we update galaxy, it must update the matrix first or create a new one for table reference to bubble system, bubble systems always follow and showcase what on table to keep everything coherent."** Any real Galaxy Map artifact with both a table/matrix representation and a bubble/map representation must build (or update) the table FIRST — the table is the real source-of-truth data structure; the bubble/map view is a rendering layer computed FROM that same data, never a second, independently-imagined dataset. Concretely: never add a bubble/node that doesn't correspond to a real row already in that page's own table data; when a real change lands anywhere in the Galaxy Map that would add/remove/reshape a table row, update that table first (or create a new table if none exists yet for the new content), then regenerate the bubble view from it. `galaxy_map_decision_matrix.py` is the reference implementation this rule was extracted from: `build_matrix_table()` and `build_bubble_map()` both consume the exact same `build_unified()` output — the bubble map function has no data of its own. This generalizes the pattern already used by `galaxy_map.py`'s Infra/Inter facets, `galaxy_map_l0.py`'s original map/table toggle, and `galaxy_map_skill_network.html`'s map/table merge — R22 makes it an explicit, permanent, checkable rule rather than an implicit convention several pages happened to already follow.
