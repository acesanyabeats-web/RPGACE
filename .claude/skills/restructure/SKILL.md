# /restructure — would this repo change RPGACE-Claude Code's skeleton, and should it

Alex's own framing (verbatim, July 29): *"use this as one side of debate. the other side debates why using this instead of whole pieces of infrastructure in rpgace and claude code joint system could make 1) code shorter 2) loads quicker 3) output more detailed, context appropriate and meticulously picked. use /Engineer as a way to envision implementation for arguments, /scope and /godmode for research, /5thDimension and /omnitrix without fable with opus 5 and /aintergration. this is then council of 5 on output of debate with /scope and handed full report on rebirth of rpgace... the purpose is to see how fitting a repo would change the skeleton of rpgace-claude code system to make it evolve."*

This is a genuinely different question from Aintergration's. Aintergration asks "is this worth adopting, alongside what already exists" and its usual, correct answer for a whole third-party repo is Reject/Reference-only, because most such repos are a different tech stack bolted onto RPGACE's deliberate zero-build-step architecture (the Framer Motion and OmniRoute precedents). `/restructure` asks a sharper, rarer question: does this repo's *content* point at a real weak spot in RPGACE-Claude Code's own current skeleton that's worth evolving, even if none of the repo's literal code ever ships. The debate is built so that question gets a real fight rather than either side winning by default.

**Source of truth**: CLAUDE.md's `## Invokable frameworks` section defines GODMODE/Council of 5/Omnitrix/Aintergration; `scope`, `debate`, `5thDimension`, and `Engineer` are sibling skills in this directory. If this file and CLAUDE.md ever disagree, CLAUDE.md wins and this file is stale.

## The procedure, in order

**Step 1 — Side A: Aintergration's own verdict.** Run (or reuse, if already run this session) Aintergration's real GODMODE-evidence-checked adopt/reject/reference-only pass on the repo, item by item where a real adoption decision exists, triaged rather than exhaustive where most items share one verdict (same discipline as the system-design-book Worked Precedents). This is Side A's starting case: keep RPGACE-Claude Code's existing infrastructure, adopt only what survives Aintergration's own scrutiny standalone.

**Step 2 — Side B: the replacement case, on three named axes only.** Side B does not get to argue "the repo is generally cool" - it must build a real case that fitting a *specific* piece of the repo *instead of* a *specific* piece of RPGACE-Claude Code's current infrastructure would: (1) make code shorter, (2) make something load or respond quicker, (3) make Oracle/taxonomy/grounding output more detailed, context-appropriate, and meticulously picked. GODMODE + `/scope` do the research for both sides - real current line counts, real current latency/cost numbers (rule 11's own token-cost audits), real current retrieval mechanism (e.g. `oracleTreeGrounding`'s keyword-score heuristic), never an assumed baseline.

**Step 3 — Envision implementation, don't build it.** For any Side B claim that survives Step 2's evidence check, use `/Engineer`'s own shape (Stage 1 goal contract, Stage 2 evidence) to sketch what a real implementation would concretely look like - files touched, new tables/extensions, a rough Tier per the Judgment Funnel - without actually writing the code. This is what makes Side B's case checkable rather than hand-wavy: a claim that can't survive being sketched as a real, Tier-rated implementation doesn't survive to Step 4.

**Step 4 — Reconcile via /5thDimension, without Fable.** Feed both sides through `5thDimension`'s Phase 3-4 shape: does either side's claim actually match real built-vs-reported state, and does the resulting rewiring case stay anchored to Alex's real goals rather than technical tidiness. Omnitrix runs without Fable by default, Opus 5 as builder for any sketching work Step 3 needs, Sonnet reviewing - same rebalance as every other skill in this project. Aintergration is re-invoked here only if a genuinely new third-party candidate surfaces mid-debate that Step 1 didn't already cover.

**Step 5 — Council of 5, written from the debate transcript via /scope.** Same discipline as `/Engineer`'s own Stage 4: the report is written from what the debate actually produced, organized via `/scope`'s grouped-category method (real forks needing Alex's decision / real rejects with reasons / real confirms of what's already right), not reconstructed from memory.

**Step 6 — The report: "rebirth of RPGACE."** The final deliverable names, for each real surviving Side B claim: what it would change about RPGACE-Claude Code's actual skeleton, what Tier that change sits at, and what real evidence would need to exist before building it for real. This is a report, not a build - nothing in `/restructure` ships code on its own authority. A Tier-3 fork always still needs Alex's own explicit go-ahead, exactly like everywhere else in this project.

## Guardrails

- **Side B must be real, not manufactured.** If a full Step 2 pass genuinely finds no real case on any of the three axes, say so plainly - same honesty rule `/debate` and `/5thDimension` already hold themselves to. A `/restructure` run that always finds *something* to replace, regardless of the actual repo, isn't doing its job.
- **This never substitutes for Aintergration on a normal "is this one skill/tool worth adding" question.** If Alex just wants to know whether to bolt one thing on, that's Aintergration alone - `/restructure` is for when the real question is whether an existing piece of the skeleton itself should change shape.
- **Nothing gets built from this skill directly.** Every real, surviving finding is a proposal for a future dedicated build pass (its own `/Engineer` run, its own rule-5 spec-and-confirm), never executed inline just because it survived the debate.
- **Rare by design**, same standing as `/5thDimension` - a whole-architecture question, not a per-feature one. Most "here's a repo, is it useful" questions should go to Aintergration alone.
