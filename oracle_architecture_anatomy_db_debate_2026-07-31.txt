FREE-FOR-ALL DEBATE — 4 competitors, real disagreement, then convergence
===============================================================================

C1 (Token Accountant, picked: vessel shape + trigger/budget cost): a second
always-injected constant covering all 52 modules densely enough to answer "how
does X work" would run 4,000-7,000 tokens per trigger vs. ~300 for a scored
retrieval of 2-3 relevant rows. A full-blob second constant is a direct rule-11
violation — dead on arithmetic alone.

C2 (Rule-8 Auditor, picked: dedup + vessel shape): attacked a table as a second
source of truth for facts interconnection_map.md already states — the same class
of drift that let api/composio.js silently call wrong Gmail/Instagram account IDs
for weeks. Forced the surviving design to require a source_ref (file:line) on
every row, and to point at an existing doc's fact rather than restate it wherever
one already exists — the table becomes an index for a reader that cannot access
the repo, not a rival doc.

C3 (Access-Path Realist, picked: Claude Code benefit + dedup): killed the "both
Oracle and Claude Code can use it" framing outright. Claude Code has Read/Grep
over the whole repo, graphify query/explain/path, and 6 docs — a Supabase prose
copy is strictly lossier, staler, and slower to consult than the real thing.
Manufacturing a Claude-Code benefit to satisfy the "both" framing would itself be
the rule-8 violation the framing was trying to avoid.

C4 (Staleness Skeptic, picked: trigger/budget cost + Claude Code benefit):
converged with C1 rather than fought it (per the skill's own "combine, don't
crown a winner" rule) — 52 hand-written module rows is a 52x bigger staleness
surface than one string, and the CLAUDE.md meta-finding above is live proof that
hand-curated text drifts even when someone is actively trying to keep it current.

Merged surviving position: a table, but retrieval-scored (not full-inject), a
small first batch (not all 52 modules), source_ref on every row, curated by Claude
Code only, Oracle-facing only.

===============================================================================
COUNCIL OF 5 — FINAL VERDICT
===============================================================================

A. Vessel: a real new Supabase table — but smaller and narrower than the original
   framing, and NOT a 4th window.callOracle wrapper. Three wrappers already exist
   (oracleTreeGrounding/oracleAppGrounding/oracleFetchGuard) and CLAUDE.md logs a
   real landmine about all three needing to forward all 4 arguments or streaming
   silently downgrades to blocking. Extend oracleAppGrounding itself with a second
   keyword array + a new _buildAnatomyBlock(), reusing oracleTreeGrounding's proven
   scan->SELECT->score->top-N shape. Zero new wrap, zero new landmine surface.

B. Schema (9 cols): id, module_name (unique), layer (core-module|api|table|pattern),
   purpose (1 line), anatomy (2-4 sentences: real mechanism, not marketing copy),
   connects_to, gotchas (the per-module landmine — the single highest-value
   column), keywords (text[], compound phrases only — the hyphen/word-boundary
   landmine applies here same as everywhere else), source_ref (file:line),
   updated_at.
   Population: manually curated by Claude Code per architectural change, same
   discipline as the 6 docs — NOT auto-parsed from graphify (its raw AST output is
   mechanical, not conversational prose Oracle can answer from).
   RLS: anon_read_only (SELECT) + authenticated_all — matches the verified 17-table
   posture. Do NOT add to api/data-write.js's ALLOWED_TABLES — nothing in the app
   writes to it client-side; Claude Code curates via MCP/service-role directly,
   bypassing the proxy by design. Adding it to the write-proxy would create dead
   attack surface for zero benefit.
   Triggers: anatomy-shaped ("how does", "under the hood", "which module handles",
   "why is it built", "internals", "how is it implemented") — checked against the
   existing TRIGGER_KEYWORDS list for overlap; none found.

C. Claude Code benefit: REJECTED, honestly, per C3's own finding. Zero real
   knowledge benefit — Claude Code already has better direct access. The only real
   secondary use is inverse: reading the table tells a session what Oracle has
   already been told (an audit surface), not a knowledge source. The "database
   both Oracle and Claude Code can use" framing from the original ask does not
   survive real evidence intact — corrected here rather than quietly built as
   originally framed, per Council of 5's own rule that a killed/reshaped premise
   gets said plainly, not smoothed over.

D. Unresolved fork, left visible rather than resolved by guessing (per
   free-for-all-debate's own honesty rule): C2's dedup objection is mitigated by
   source_ref, not eliminated. Given nothing shipped since July 28 has been
   hand-tested yet, "don't build this now, revisit once hand-testing catches up"
   is a legitimate answer alongside "build the small first-batch version."
