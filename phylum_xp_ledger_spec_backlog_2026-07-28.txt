COUNCIL OF 5 — real scrutiny before any build decision
════════════════════════════════════════════════════════════════
Technical risk: LOW for the narrow version (a new table + a UI card).
MODERATE-HIGH if scope grows to retrofitting phylum tags onto the 6
existing career-score tables (a real schema migration across many
tables, several already RLS-locked to a write-proxy).

Real scope/cost: genuinely 4 real pieces — (1) persist quest completion
somewhere real, (2) tag quests with a phylum at generation time, (3) a
per-Phylum aggregation query/view, (4) a radar-chart UI. Squarely rule-5
multi-subsystem territory — this file exists because of that, not
despite it.

Maintainability: clean if scoped to a new, dedicated `quest_completions`-
shaped table (additive, doesn't touch the existing career-score formula
or its 6 tables at all).

UX: a real, motivating visualization once the underlying data is
trustworthy — genuinely good idea, not just AI enthusiasm.

Why NOT build it today: the real prerequisite (quest completion has zero
persistence) is unresolved, and — this is the sharper point Oracle's own
second flag raised unprompted — HOW to resolve it is itself a real fork
with different architectural consequences, not a given.

════════════════════════════════════════════════════════════════
THE REAL FORK — needs Alex's actual answer, not a guessed default
════════════════════════════════════════════════════════════════
When a quest completes, should that write:

  (A) to a NEW, dedicated table (e.g. `quest_completions`: quest_name,
      phylum_number, xp, completed_at) — kept fully separate from the
      6 tables the career score already reads. Narrower, safer, matches
      Oracle's own literal proposal. Real upside: quest completion stays
      an honest "did the app's suggested todo get done" signal, distinct
      from the career score's stricter "real shipped work / real learning
      depth" definition — which is exactly the separation the July 22
      Output/Growth-lane split was designed to protect (a Goodhart's-law
      concern already reasoned through once for this exact system; a
      Phylum radar fed by quest-checkbox activity would repeat the same
      class of gaming risk if it were folded into the real score instead
      of kept as its own honest, separate signal).

  (B) into the EXISTING career-score tables somehow, so quest completion
      actually moves the real Output/Growth number. Bigger, blurrier -
      quests are closer to a todo-list checkmark than "shipped content,"
      and conflating the two would weaken the score's own real meaning.

Recommendation (not yet acted on — Alex's call): (A). It's the
lower-risk, more honest option, and it's what Oracle itself originally
proposed before its own second, sharper flag started leaning toward
"just wire completeQuest() into the dashboard's tables," which is
actually option (B) in disguise — worth Alex knowing the two flags
pointed in slightly different directions once you look at the literal
mechanics, not just the prose.
