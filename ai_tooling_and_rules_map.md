# RPGACE — AI Tooling & Rules Map
**The 7th oversight doc.** Created July 31, 2026, per Alex's direct request, to answer two questions no other oversight doc answers: (1) which Claude Code capabilities — global/native to Claude Code itself, not written for RPGACE — are actually available in an RPGACE session, and what do they actually do to this specific system when used; (2) every rule/`.md`/`.txt` file that governs how a Claude Code session behaves here, and which of those are live authority vs. historical record. Real evidence only (file reads, `.claude/settings.json`, actual `SKILL.md` frontmatter) — no claim in this doc is guessed from a skill's name alone.

**Update discipline**: same as every other oversight doc — update in the same session a new global skill gets used against RPGACE for the first time, a new RPGACE-authored skill ships, or a new rule-bearing file is added anywhere in the repo. `/loggingregen` audits this doc the same way it audits the other six.

## Part 1 — Claude Code skills present in this environment

Two real populations exist side by side: skills **global/native to Claude Code** (ship with the harness or live in a personal `~/.claude/skills/` scope, available in ANY project, not authored for RPGACE) and skills **RPGACE built for itself** (`RPGACE/.claude/skills/`, appear only in this repo). Where a skill exists at both scopes (Claude Code resolves the more specific one automatically when working inside this repo), that's called out explicitly.

## Part 2 — Every rule/`.md`/`.txt` file that influences the system, by real authority level

### Tier A — Live, authoritative, read at the start of every session
- **`CLAUDE.md`** — the master operating rules. Everything else in this document is subordinate to it; where any file below disagrees with CLAUDE.md, CLAUDE.md wins (a rule CLAUDE.md itself states explicitly for `RPGACE_ORACLE_NOTES.md` and for `/Routine`'s own SKILL.md).
- **`.claude/CLAUDE.md`** — a second, SEPARATE root-level rules file specific to the `.claude/` scope Claude Code itself reads: currently just the `graphify` trigger instruction (`/graphify` invokes the skill; the mandatory-hook wording lives in `.claude/settings.json`, not here). Real, easy-to-miss distinction: this is a DIFFERENT file from the main `CLAUDE.md` at repo root, loaded from a different path, with a much narrower scope. Two files with the same filename, two different jobs — worth stating plainly so a future session doesn't assume they're the same file.
- **`.claude/settings.json`** — the actual harness-level enforcement mechanism: pins the model (`claude-sonnet-4-6`), auto-loads `CLAUDE.md` as a context file, sets `auto_approve:false`, wires the `node --check main.js` check command, and — the real load-bearing part — registers the `graphify hook-guard` on `Bash|Grep` and `Read|Glob` that fires the "MANDATORY: run graphify first" reminder seen throughout this session. This file is WHY graphify's staleness (Part 1b above) is a real friction point and not just a suggestion ignored at will.
- **`taxonomy_placement_rules.txt`** — the concrete rules `phylumPath.decidePlacementScored` actually encodes (referenced directly by `interconnection_map.md`'s "Unified placement engine" section) — a real, still-active rule file, not a historical record.
- **`DESIGN.md`** — the L1 interaction-tier constraint (no GSAP/Lenis/scroll-jacking, CSS-only animation) that CLAUDE.md's own Aintergration Worked Precedent 1 cites directly when rejecting third-party animation frameworks. Still live authority for any new UI work.
- **The six pre-existing oversight docs themselves** (`patch_notes.html`, `interconnection_map.md`, `manual.html`, `taxonomy_map.html`, `system_flow_map.md`, `minotaur_map.html`) — each one is simultaneously a RECORD and a RULE (interconnection_map.md's own "Standing rule: Oversight" section, system_flow_map.md's "update BOTH when architecture changes" line, minotaur_map.html's "update only when a wing changes" rule are all real operating instructions, not just content).
- **Every `SKILL.md` file** (both scopes) — each one is a rule file for exactly one procedure; `/Routine`'s own text states this plainly ("Source of truth: CLAUDE.md's Invokable frameworks section... If this file and CLAUDE.md ever disagree, CLAUDE.md wins and this file is stale" — the explicit subordination pattern every RPGACE skill follows).

A genuinely large population: `bookworm_spec_backlog.txt`, `chronicles_spec_backlog.txt`, `phylum_xp_ledger_spec_backlog_2026-07-28.txt`, `beat_log_matching_spec_backlog_2026-07-28.txt`, `content_pipeline_overseer_spec_backlog_2026-07-28.txt`, `beat_video_workflow_separation_and_6step_chain_spec_backlog_2026-07-30.txt`, `phylum_11_14_buildout_and_openmontage_spec_backlog_2026-07-30.txt`, `video_pipeline_director_phylum_spec_backlog_2026-07-30.txt`, `video_visual_treatment_wiring_and_conid_ux_spec_2026-07-31.txt`, `six_table_external_writer_migration_spec_2026-07-24.txt`, `openmontage_and_claude_fallback_spec_backlog_2026-07-24.txt`, `claude_fallback_build_plan_2026-07-24.txt`, `journal_chronicles_oversight_crossfeed_spec_backlog.txt`, `research_lab_lazyload_spec_backlog.txt`, `token_cost_audit_2026-07-19.txt`, `item7_process_debate_2026-07-24.txt`, `taxonomy_review_session_debate_2026-07-25.txt`, `oversight_doc_dedup_audit_2026-07-28.txt`, `oversight_doc_audit_and_reshape_2026-07-31.txt`, `manual_html_minotaur_sidekick_debate_2026-07-31.txt`, `oracle_architecture_anatomy_db_debate_2026-07-31.txt`, every `daily_priorities_debate_YYYY-MM-DD*.txt` (six on record), every `engineer_pass_YYYY-MM-DD_NN.txt` (five on record), `openmontage_kickoff_prompt_2026-07-31.txt`, `oracle_grounding_spec.txt`, `restructure_report_*` (three), `weekly_recap_2026-07-25.txt`, `STEP1_README.txt`. ### Notably absent — a real gap, not an oversight

Confirmed via direct file check (July 31): Oracle has never used this path — every real Oracle→Claude-Code suggestion so far has gone through the `oracle_dev_suggestions` Supabase table + the "🧪 Flag for Claude Code" button instead (a DIFFERENT, already-built mechanism). This doesn't mean the file-based path is broken; it means it has genuinely never been exercised, and a future session should not assume it holds any content without checking first.

## Part 3 — What this doc changes about the oversight system itself

CLAUDE.md's "Oversight — now SIX docs" section (and every doc's own cross-references to "the six oversight docs") is updated in the same commit as this file's creation to read "now SEVEN docs" with this file added to the list. Chronicles (`system_updates`) remains the separate, eighth, live in-app place — never conflated with this or any other file-based doc, same standing distinction CLAUDE.md already draws.

**Real drift found and fixed in the same pass, not just a naming choice.** The live app's own `dashDeck._openOversight()` (`rpgace_core.js:5788`) had already, at some prior point, unilaterally labeled `taxonomy_placement_rules.txt` as "The 7th doc" in its popup — with no matching entry ever added to CLAUDE.md's "SIX docs" section, no dated card anywhere recording when or why. A real, previously-uncaught instance of exactly the class of bug this whole doc exists to prevent (code and docs silently disagreeing about the system's own structure). Resolved by moving `taxonomy_placement_rules.txt` into the popup's "Working specs" tier (where it honestly belongs — a narrow, un-dated ruleset, not a full living doc with its own update discipline like the other seven) and adding this file as the real 7th "Primary" entry. `node --check` clean.
