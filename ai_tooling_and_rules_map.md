## Part 2 — Every rule/`.md`/`.txt` file that influences the system, by real authority level

### Tier A — Live, authoritative, read at the start of every session
- **`CLAUDE.md`** — the master operating rules. Everything else in this document is subordinate to it; where any file below disagrees with CLAUDE.md, CLAUDE.md wins (a rule CLAUDE.md itself states explicitly for `RPGACE_ORACLE_NOTES.md` and for `/Routine`'s own SKILL.md).
- **`.claude/CLAUDE.md`** — a second, SEPARATE root-level rules file specific to the `.claude/` scope Claude Code itself reads: currently just the `graphify` trigger instruction (`/graphify` invokes the skill; the mandatory-hook wording lives in `.claude/settings.json`, not here). Real, easy-to-miss distinction: this is a DIFFERENT file from the main `CLAUDE.md` at repo root, loaded from a different path, with a much narrower scope. Two files with the same filename, two different jobs — worth stating plainly so a future session doesn't assume they're the same file.
- **`.claude/settings.json`** — the actual harness-level enforcement mechanism: pins the model (`claude-sonnet-4-6`), auto-loads `CLAUDE.md` as a context file, sets `auto_approve:false`, wires the `node --check main.js` check command, and — the real load-bearing part — registers the `graphify hook-guard` on `Bash|Grep` and `Read|Glob` that fires the "MANDATORY: run graphify first" reminder seen throughout this session. This file is WHY graphify's staleness (Part 1b above) is a real friction point and not just a suggestion ignored at will.
- **`taxonomy_placement_rules.txt`** — the concrete rules `phylumPath.decidePlacementScored` actually encodes (referenced directly by `interconnection_map.md`'s "Unified placement engine" section) — a real, still-active rule file, not a historical record.
- **`DESIGN.md`** — the L1 interaction-tier constraint (no GSAP/Lenis/scroll-jacking, CSS-only animation) that CLAUDE.md's own Aintergration Worked Precedent 1 cites directly when rejecting third-party animation frameworks. Still live authority for any new UI work.
- **The six pre-existing oversight docs themselves** (`patch_notes.html`, `interconnection_map.md`, `manual.html`, `taxonomy_map.html`, `system_flow_map.md`, `minotaur_map.html`) — each one is simultaneously a RECORD and a RULE (interconnection_map.md's own "Standing rule: Oversight" section, system_flow_map.md's "update BOTH when architecture changes" line, minotaur_map.html's "update only when a wing changes" rule are all real operating instructions, not just content).
