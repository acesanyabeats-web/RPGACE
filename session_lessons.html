UI14 Phase 1: a shared reused DOM node (not a fresh popup box every time) meant one render-state's own inline style could silently leak into the next state — solved by fixing the container, not the one instance
Sep 5 2026
Found during headless-Chromium testing, before shipping
Prompt scopeUI14 Phase 1 — converting Bookworm's 7 chapter-reading render-states from each spawning its own fresh dashDeck._popup() to real in-page navigation, sharing one persistent #bookworm-reader container built inside #page-bookworm.
Obstacle_renderWaitingForNextInsight (the background-analysis wait state) sets box.style.textAlign = 'center' directly on the reader's content box — harmless under the OLD popup-per-state design, since each state got a brand-new box element with no inherited style. Under the NEW design, #bookworm-reader-box is one persistent DOM node reused across every state, so that inline style would silently survive into whichever state rendered next (e.g. the chapter list), left-aligned content suddenly rendering centered with no visible cause in that state's own code.
ReasoningCaught by a dedicated headless-Chromium test built specifically to exercise all 7 states in sequence, checking the reader box's own inline style after each transition rather than only checking each state's OWN rendered content in isolation — a test that only ever built and tore down one state at a time would never have exposed a cross-state leak. Once found, the real question was whether to fix it locally (have _renderWaitingForNextInsight's own exit paths reset the style) or structurally (have the shared container itself reset on every transition) — the structural fix is the one that closes the whole bug CLASS rather than the one instance found by testing, and any future state that sets a box-level style would otherwise reproduce the identical leak.
Solutionbookworm.ui._showReader() — the one shared function every render-state calls to get its content box — now calls box.removeAttribute('style') before returning it, clearing whatever the PREVIOUS state left behind. Re-verified via the same headless test: the waiting-state's centered text renders correctly, and the very next state to render is confirmed NOT to inherit it.
Resulting ruleConverting several independent popup-based render functions into states sharing ONE persistent container is not just a navigation change — every one of those functions may have been setting box-level properties (inline styles, classes, attributes) assuming a fresh element each time, and any of those assumptions silently breaks once the element is reused. The fix belongs in the shared entry point that hands out the box, not in each individual state that might set something on it — the same "fix the choke point, not each caller" discipline this project already applies to write paths (rule 8).

A real, recurring bug class — a function's own leading comment landing on the WRONG function after reordering — was found once in batch 17, then correctly anticipated and caught systematically in batches 18 and 19 before it could ship wrong
Sep 2-3 2026
Methodology built from a first real instance, reused twice
Prompt scopeG53 batches 17-19 (visualOracle, taxonomyTree, dashDeck) — the three modules whose real functions were interleaved in original source order (ui/logic/ui/logic/...), making a minimal Edit-tool surgery impossible; each required extracting every function as a raw text block via precise line-range slicing, then reassembling them grouped into ui/logic instead of left in their original order.
ObstacleSlicing a function's text as [header_line, next_header_line) means a function's own LEADING doc-comment is always captured as the TAIL of the PREVIOUS block in original source order — invisible as a problem as long as functions stay in their original relative order, but the whole point of this split is to reorder them into ui/logic groups. Reordering breaks the original adjacency: a comment can end up sitting before an unrelated function it was never written to describe, or orphaned at the tail of a block it has nothing to do with, while the function it actually documents ships with no comment at all. Caught for the first time mid-extraction in batch 17 (3 doc comments scooped onto the wrong function's tail) — genuinely not anticipated going in, since the first 16 batches' modules either had functions already in ui/logic-friendly order or few enough comments that this never surfaced.
ReasoningRather than treat batch 17's discovery as a one-off fix, generalized it into a real, repeatable detection method before batches 18/19 began: build a table comparing each function's ORIGINAL predecessor (in source order) against its NEW predecessor (in the reorganized ui/logic order) — any mismatch is a real candidate for a misplaced comment. Not every mismatch is real: some candidates' original predecessor has an empty tail (genuinely no comment sitting there), correctly left alone rather than force-relocating something that doesn't exist. Each real candidate gets its actual predecessor's tail content checked directly before anything moves.
SolutionA small `relocate(src_key, dst_key, marker)` helper: finds the marker text in `src`'s tail, splits it off, prepends it to `dst`'s head, asserts `src`'s trimmed remainder still ends in a real closing `},` (proving the split boundary was found correctly, not swallowing part of the code itself). Batch 18 found 6 real instances this way, batch 19 found 9 — both BEFORE any content was written to the live file, using the same predecessor-comparison table built specifically because batch 17 had already shown this bug class was real and would recur.
Resulting ruleWhen a mechanical text-reordering operation is applied more than once across a series (same shape of edit, different files), the first real bug it produces should be generalized into a systematic check for the NEXT application, not treated as a one-off fix specific to that file. The predecessor-comparison table is now a standing step in this project's own boundary-asserted extraction methodology, not something re-derived from scratch each batch.
A file-corruption incident, caught immediately by an existing safety habit and reverted with zero cost — and the exact discipline that prevented it became standing procedure for every batch after
Sep 2 2026
node --check caught it before any commit; procedure generalized
Prompt scopeG53 batch 14 (contentRepurpose + oracleAppGrounding) — oracleAppGrounding's SELF_KNOWLEDGE field is a giant ~22,000-character string that must never be retyped by hand (retyping risks silent corruption or truncation of Oracle's own grounding text), so the plan was to relocate it programmatically without ever passing its content through a manual edit.
ObstacleAn early file-move script, written to safely relocate SELF_KNOWLEDGE without retyping it, used an UNSCOPED text search for its target line (logic: {) instead of a search scoped to the module's own real line range. logic: { is a common literal that appears in many other modules throughout the same 20,000+ line file — the script matched the WRONG occurrence elsewhere in the file entirely, and wrote its output there, corrupting the live source file.
ReasoningThe corruption was caught immediately, not eventually, because the project's own standing rule — run node --check rpgace_core.js after every edit — was followed without exception, even for what looked like a purely mechanical, low-risk relocation. node --check failed instantly on the corrupted file. Batch 13 was already safely committed, so the fix was a clean git checkout revert with zero real loss — nothing corrupted was ever committed or pushed, and the only cost was the wasted first attempt.
SolutionRedone with every edit precisely scoped to the module's own real, directly-confirmed line range — never a bare unscoped string search across the whole file for a common literal. This incident is the direct origin of the "boundary-asserted extraction" methodology used for every subsequent hard batch (17, 18, 19): grep/read the exact current line numbers first, assert the EXACT expected text content at every boundary before touching anything (failing loud immediately on any drift), extract via precise line-range slicing, and run a reconstruction self-check (concatenating every extracted block and asserting it exactly equals the original module body) before any write ever happens.
Resulting ruleA script that locates its own edit target by searching for a string literal must scope that search to the exact real boundary of what it's editing (a line range already confirmed via grep/read) — never trust a literal to be unique across a 20,000+ line file just because it looks distinctive within the one module being edited. node --check after every edit is not a formality even for "safe, mechanical" relocations — it is what turned a real corruption into a zero-cost non-event instead of a shipped bug.
