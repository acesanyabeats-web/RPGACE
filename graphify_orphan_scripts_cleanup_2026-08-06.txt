------------------------------------------------------------------
THE BIGGER QUESTION — real evidence, not a fix, since it isn't one
------------------------------------------------------------------
Re-ran the full pipeline (--code-only rebuild, export, recolor,
river-group) and computed real connected components, not just degree:
950 nodes, 0 orphans (0-degree nodes fully gone), but **56 separate
connected components** — the biggest holds 239 nodes, then 63, 54, 45,
36... down to many small clusters. This is the real shape behind both
of Alex's examples: rebuild_daily_grid_v2.py forms its own tiny
2-node island (itself + its one internal helper); interconnection_map.md
forms its own ~25-node island (its own sections, cross-referencing only
each other).

Real, evidence-based cause — NOT a bug in this session's cleanup, a
structural limit of graphify's own AST extractor for THIS codebase's
own real conventions, already confirmed once this session
(graphify_restructure_paranoia_2026-08-06.txt):
1. `RPGACE.register('name', {...})` — this project's own standing
   module convention — is never extracted as a first-class symbol.
   Confirmed live, twice, including a fresh rebuild run specifically to
   test it.
2. Real dynamic dispatch the AST cannot statically resolve:
   `RPGACE.hooks.fire('name')` / `.on('name', fn)` pairs (string-keyed
   at runtime, not a direct call), and `RPGACE.modules.X.method()` /
   `RPGACE.utils.X()` (property lookups on a shared registry object,
   not a resolvable function call).
3. Docs and code are separate extraction domains — a markdown doc
   describing a module gets edges to its OWN sections, never to the
   actual code symbols it describes, unless an LLM-based semantic pass
   (not the free --code-only AST pass) explicitly draws that link.

A community-detection graph over AST-extracted references is not
designed to be a single-rooted tree in the first place — many separate
real components is the textbook-correct, honest output of this kind of
tool on a codebase with this many one-off utility scripts and doc files
that only reference themselves. Force-connecting them with fabricated
edges would misrepresent the codebase (same standing rule 1 reasoning
as round 1's "why not hook them up" answer).

Real, buildable path forward, NOT built this pass (put to Alex as a
scoped decision rather than started blind, given its real size):
a genuinely new companion script adding a SYNTHETIC edge layer on top
of graphify's real AST edges, grounded in real string-matched evidence
(never invented) — tracing `index.html`'s real script/boot sequence,
`RPGACE.registerBootTask()` registrations, and `RPGACE.hooks.fire()`/
`.on()` name pairs, plus `RPGACE.modules.X.method()`/`RPGACE.utils.X()`
call sites matched back to their real `RPGACE.register('X', ...)`
definition. This would close the SPECIFIC extraction gap causing the
fragmentation, not just recolor/reposition nodes like today's scripts
do — a real, substantially bigger build than anything done on graphify
so far this session.
