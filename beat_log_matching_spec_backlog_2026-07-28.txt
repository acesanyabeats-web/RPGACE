=====================================================================
REAL ROOT CAUSE (GODMODE evidence, not assumed) — why matches "kept
being the same"
=====================================================================
Read refCorpus.findMatches() and _searchArtists() in full, then queried
the real reference_tracks table directly (32 rows). Confirmed:
  - The table already HAS scale and genre columns, and findMatches()
    already SCORES scale (+2) - it just never had any data to score,
    because the corpus's own add-track UI (_addSingle/_bulkImport) never
    collected either field. Every one of the 32 real rows has
    scale=null and genre=null.
  - Real consequence traced against Alex's actual beat ("No Motivation":
    F Minor, 143 BPM, Energy 5, Aggressive): scoring the 32 real corpus
    rows by hand against findMatches()'s own formula (bpm-proximity +
    mood-match + energy-match, scale/genre contributing zero since both
    are null everywhere) produces an exact 5-way tie at the top: Headie
    One, Stormzy, Ghetts, Skepta, Digga D - all logged at ~138-140BPM/
    Energy 5/Aggressive in the corpus's own bulk-imported seed data. This
    is precisely the cluster that appeared in his screenshot. The corpus
    isn't broken or empty (hasCorpus was true) - it's just too thin and
    too flat on its own real discriminating dimensions for a beat that
    happens to sit in the most common BPM/energy/mood bucket.
  - This is a real, evidenced explanation, not "the corpus needs more
    rows" as a vague guess - it names the exact two dead scoring
    dimensions and the exact reason they went dead (a UI gap, not a
    scoring-formula bug).

the new reference_tracks.url column is the real fix for that, since
future corpus rows (added manually, or grown via the button above) can
carry a real specific-track link that a future match will surface.

REAL RESEARCH, NOT BUILT — audio-analysis AI (Aintergration-style
verdict, genuine Tier 3 spending/architecture fork for Alex)

Real web research (not recalled from memory, cited):

Cyanite.ai (https://api-docs.cyanite.ai/docs/audio-analysis-v6-classifier/,
https://cyanite.ai/faq/) - accepts direct MP3 upload of your OWN
unreleased audio (up to 15 min, any bitrate; wav/mp4/flac for catalog-
scale ingestion), returns genre, mood (aggressive/dark/energetic/etc,
scored 0-1), BPM, key, instruments, energy in one GraphQL call, analysis
in seconds. Real cost: EUR 290/month API fee (a free small test run is
possible with an existing account first). This is a real, substantial
recurring cost for a solo bedroom-producer project.

librosa (open source) - already name-dropped in refCorpus's own existing
panel copy as "Phase 2: librosa auto-analyses each track," i.e. this was
already on the roadmap before today. Free, runs locally via the existing
local_server.py Python script (already part of this project's real
infrastructure), gives reliable BPM/key/tempo via real deterministic
signal processing. Real limitation: no built-in genre/mood classifier -
that half of what Alex asked for ("distinguish all metadata") would need
real added ML work on top, not just calling a function.

Spotify/Soundcharts/Tunebat (also surfaced in research) - all catalog-
lookup tools (analyze/compare EXISTING released tracks), not upload-your-
own-unreleased-audio tools - not applicable to analyzing Alex's own
unmixed/unreleased FL Studio exports.

Verdict, per Aintergration's own two-lens procedure: NOT adopted this
session - a real Tier-3 spending decision (Cyanite) or a real added-scope

      in one call, zero infra, real recurring cost.

      now, genre/mood would need a real separate build (a classifier,

  (c) Do neither for now - keep manual entry, since Beat Log's filename-
      parser (_parseFilename) already extracts BPM/key/scale/mood/energy
      reasonably well from a sensibly-named export file.
Not decided here - genuinely Alex's call given the real cost/scope
