STAGE 3 — BUILD (Omnitrix, no Fable — real but bounded scope, not an
exhaustive audit)
=====================================================================
1. Supabase migration (phase_h_beat_deliverables): new bucket
   beat-deliverables (private). Real, deliberate DEVIATION from beat-
   audio's blanket anon_all precedent: anon gets INSERT+DELETE only, no
   SELECT — raw file bytes can only be read by the service-role key
   (inside the new endpoint) or via a signed URL it hands out. Reasoned,
   not silent: beat-audio holds disposable analysis samples; this
   bucket holds Alex's real sellable stems/bundles — a blanket anon-
   read policy would let anyone holding the public anon key (embedded
   client-side, effectively public) pull paid content directly. New
   content_productions columns: deliverable_files (jsonb array,
   default []), deliverable_bundles (jsonb object, default {}).
   Verified post-migration via direct information_schema + bucket
   queries, not assumed from the migration's reported success alone.
2. New api/bundle-deliverables.js: requireAuth-gated POST, real tier-
   ordering logic (lease < non-exclusive < exclusive, a file included
   at its tagged tier and every higher one), fetches applicable files
   from the private bucket with the service-role key, zips them with
   archiver (added to package.json — real first npm dependency, server-
   side/Vercel-function-only, does not touch the client bundle or the
   zero-build-step client architecture), uploads the zip back, signs a
   24h download URL, merges the result into deliverable_bundles (read-
   modify-write, preserves other tiers' previously-generated bundles).
   maxDuration 60s (per-file export, matching oracle.js's real, current
   convention). Client request/response payloads stay tiny by design —
   real file bytes only ever move Storage-to-function-to-Storage,
   never through this endpoint's own HTTP body either direction — which
   sidesteps Vercel's serverless payload ceiling as a structural
   property of the design, not a workaround bolted on after a failure.
3. contentProductionLive gained: _showDeliverablesManager (real popup:
   file list + delete, per-tier bundle status + disabled-with-reason
   Generate button when zero files apply, tier-tagged upload controls),
   _uploadDeliverableFiles (batched read-modify-write — one Supabase
   write per upload BATCH, not per file, so a folder-drop's several
   files don't race each other), _removeDeliverableFile (DB write first,
   best-effort Storage delete after — fails open on the Storage side
   since the DB record, what the UI reflects, is already correct),
   _generateBundle (calls the new endpoint, opens the signed URL),
   _fileAppliesToTier (small, explicitly-labeled rule-8 exception — the
   same tier-inclusion logic necessarily exists in both this file and
   the Node/ESM Vercel function, since this project has no build step to
   share a module between the two runtimes; named and reasoned in-code,
   not a silent duplication). New "📦 Manage Deliverables" button on
   ConID cards, same row.licence_type gate as the existing Beatstars
   listing button.
4. index.html cache-bust bumped (20260805h → 20260805i) — G7. Script-
   tag count re-confirmed exactly 2.
5. New beat_deliverables_autoport_backlog_2026-08-05.txt — full verbatim
   spec/answers per rule 5, including the deferred Option 2 (browser
   automation) and the honest Phase B revisit reasoning.

Honest residual risks, not hidden:
- Genuinely untested end-to-end, more so than most prior phases: this
  is the first build this session touching real binary file upload,
  real Storage bucket permissions, and a brand-new server-side npm
  dependency all at once — more real surface area for something to go
  wrong in ways `node --check` and a local zip-buffer smoke test (run
  during Stage 3, confirmed producing a valid PK-signed zip) cannot
  catch, since neither exercises the actual Supabase Storage round trip
  or a real multi-MB audio file.
- Vercel's real memory/duration ceiling for the zip endpoint is an
  honest open question at scale: typical stem packs (a handful of WAV
  files, tens of MB each) should comfortably fit within a 60s/default-
  memory Vercel function, but this was reasoned from typical file sizes,
  not measured against a real upload — a very large multi-GB stem pack
  could hit a real ceiling this pass didn't test.
- The anon-INSERT-only Storage policy means a file, once uploaded,
  cannot be directly re-downloaded by the client outside this feature's
  own signed-URL flow — a deliberate security trade-off (see Stage 3),
  but worth knowing if a future feature ever wants simpler direct file
  access.
- Signed URLs expire in 24h — the UI's "Regenerate" language on an
  existing bundle is intentional (clicking it re-signs a fresh URL
  rather than assuming an old one still works), but a bundle generated
  once and never re-clicked will have a dead link after a day if Alex
  tries to reuse an old browser tab.
