How this doc works

Brown is genuinely different from purple. error_log.html's purple tracks real CODE/FUNCTIONALITY regressions — something that worked, and real evidence now shows it broken. Brown tracks a real CLAIM going stale — a stated count, rule, or description in a live oversight doc was true, and a later real change (unrelated to whether the feature still works) made the STATEMENT false. The worked example this color was built from: TOTAL_ZONES = 16 in graphify_river_group.py was correct when written; adding River XVII (Aug 18, G49) made it 17, but nothing forced the constant to move with it — found stale 2 days later by a plain file-count check.

Never a guess — same evidence bar as every other /colourgradient color: a real OLD value (what the doc said), a real NEW value (what's actually true now), and a real, checkable reason the two diverged. When a brown finding lands, the live doc's own claim is corrected in the SAME pass (rule 6) — this page is the permanent record that it was once true, never a substitute for fixing the doc.

Backed by the real Supabase table achiever_archive — this HTML page is a snapshot rendering of that live data, refreshed whenever a /colourgradient, /paranoia, or /drift pass catches a real stale claim and pushes.

Full real pipeline logic (the detect → distinguish-from-purple → archive → fix → sweep-and-remove flow, as a Mermaid diagram): system_flow_map.md §13, added the same pass as G56 (Alex's own ask: "using md files to explain logic of many pipeline will also benefit galaxy map").

Grouping convention: archived claims are grouped by real category (a count constant, an architecture description, a rule) rather than a flat list — when a new claim is archived, find its real category home first. This deliberately does not follow future_integrations.html's Plan-first grouping (DD2, Aug 23) — the two docs sit at the same tier but answer different questions, and most archived claims have no ceo_plans row of their own to group under; a stale count in CLAUDE.md is not a plan item.

🌊 Galaxy Map river tag (DD8, Aug 23 2026): every archived claim carries the short river identifier for the claim's own subject — not the doc it happened to be written in — so a stale claim is cross-referenceable against the Galaxy Map, smoke_test.html and ceo_plan_items, all of which use the same galaxy_river vocabulary (RIVER_NAME in scripts/graphify_river_group.py). A blank tag is an honest value, not a missing one: a claim whose subject spans several rivers with no single owner is left untagged rather than force-classified.
